## 2. 发明背景与待解决问题

**技术领域**（[0001]）：本披露涉及 crossbar switch（交叉开关），更特别地涉及实现高带宽容量交换（high bandwidth capacity switching）的技术。

**应用场景**：交叉开关（crossbar switch）实现源端口与目的端口之间连接的排列（permutations）[0002]；在某些存储器子系统中，crossbar 具有路由灵活性：（特定）包可以在"目的端口子集"内的任意端口上发送，包到达最终客户端后再被重组（reassembled）[0003]。本专利旨在提供能利用这种灵活性的 Dynamic Destination Selection（DDS，动态目的选择）crossbar。

**待解决问题**：非理想负载下"one destination is stalled more compared to other destination(s)"（某个目的端比其他目的端更频繁地停滞），或源端流量偏向某个目的端口，都会拉低仲裁器效率、损失 crossbar 吞吐；即便所有目的端均衡受载的理想负载，仲裁效率仍有提升空间（[0004]）。

**现有技术的不足**：既有"pre-dispatch adaptive routing"（分发前自适应路由）设计在分发之前就用 port credit availability（端口信用可用性）、load（负载）、Round-Trip Time（RTT，往返时间）等端口级指标选定目的；其目的选择在 crossbar dispatcher（分发器）中不随网络状态变化，无法跟踪瞬态 crossbar  contention。本专利提出与 dispatcher 紧耦合的"at-dispatch adaptive routing"（分发时自适应路由）：利用仲裁时刻的瞬时目的可用性选择输出目的，选择可随网络状态逐周期（cycle to cycle）改变，且"much better suited for the small packet environment of a Graphics Processing Unit (GPU) crossbar"（更适合 GPU crossbar 的小包环境，[0005]）——这是说明书唯一明确点名 GPU 之处，也是本专利与本专题挂钩的锚点。

**部件对应关系**：FIG. 1 的 Routing Circuit 155 可对应/包含于 FIG. 2 的 Crossbar Circuit 205-a-p（[0032]、[0035]）；FIG. 3 架构可被称为 DDS crossbar 300、DDS dispatcher 300、DDS crossbar dispatcher 300 或 DDS crossbar circuit，其部件对应 Routing Circuit 155 的部件（[0044]）；Processor 140 可为 GPU、CPU、DPU 等（[0034]）。术语上，"crossbar switch""crossbar""crossbar circuit" 互换使用，"crossbar cell""sub-crossbar cell""sub-crossbar""sub-crossbar circuit" 互换使用（[0030]）；DDS dispatcher 300 也可对应为 Controller 120 执行 Instructions 130 的一种实现形态（[0045]）。

**DDS crossbar 300 内部数据流（FIG. 3，元件编号忠实原文）**：
- Receiver 308：内含 source request queue(s) 312（源请求队列），按 per-source、per-super destination group 维护，兼作 per-source 入口数据缓冲（按目的做 virtual output queuing，虚拟输出排队）；
- Mapper 316（映射器）：接队列 312 输出，图中 1:3 展开（S0SD0 → S0D0/S0D1/S0D2；S0SD3 → S0D9/S0D10/S0D11），把"源—super destination"请求展开为多条"源—目的"选项送仲裁；
- S-D Arbiter 320（source-to-destination arbiter，源选目的仲裁器）与 D-S Arbiter 324（destination-to-source arbiter，目的选源仲裁器）：二维仲裁，逐周期发出 grant（准许）；
- Remapper 328（重映射器）：把目的级 grant 按 super destination group 做 OR 归并，经 grant 线回送 Receiver 308 触发队列弹出。

### 3.2 关键机制详解

**1) Super Destination Group 与两类包**：多个目的端口被分组为 super destination group（超目的组），一个开关内可有多个组（[0052]）。包分 static destination routable packet（静态目的可路由包，只能路由到特定目的，[0012]）与 dynamic destination routable packet（动态目的可路由包，可路由到组内任意目的，[0013]）；Mapper 316 与二维仲裁器支持两类包混合（[0015]、[0053]）。

**2) 分发时动态目的选择（核心）**：自适应路由电路在"at a time of dispatching a packet"（分发包之时）跟踪 destination credit（目的信用）与 port availability（端口用性），在 super destination group 内做动态目的路由，并在收包/仲裁时刻用该组的信用与端口可用性选出输出目的（摘要、[0006]）；信用与端口可用性按 per cycle basis（每周期）重新判定（[0016]、[0065]），即目的选择可逐周期变化——这是与 pre-dispatch 方案的本质区别。

**3) 队列与 VOQ**：source request queue 312 是 per-source 入口 FIFO，按目的 threading 做 virtually-output queued；入队时动态包被推入"属于相应 super destination group 的最小编号线程"，出队（pop）时也从最小编号线程读（[0048]、[0056]）。

**4) Mapper 展开**：Mapper 316 基于收包时刻各目的的信用可用性，把一个动态包生成多条 source-to-destination 选项供仲裁（[0053]）；图中为 1:3，亦可 1:2、1:4、…、1:10；FIG. 3 为 12×12、4 个 super destination × 每组的 3 个目的，说明书另设想 16×16、4 组 × 4 目的（[0051]）。展开的作用是"maximize the number of source-to-destination arc options available to the arbiters"，提升仲裁器效率（[0050]）。

**5) 二维仲裁**：front fill 阶段为 round-robin 的 source-choose-destination（SCD）仲裁 320，后接 least recently used（LRU，最近最少使用）的 destination-choose-source（DCS）仲裁 324；可选 backfill 阶段用 Wave Front Allocator（WFA，波前分配器）（[0054]）。两个仲裁器顺序可互换，任何已知二维分配器（如 wavefront allocator）皆适用（[0050]）；仲裁器每周期查看可用 arc 并尽量多发 grant。

**6) Remapper 归并与释放**：Remapper 328 做 Mapper 的逆操作，对同一 super destination group 内的个别 destination grant 施加 OR 运算，生成 source-to-super-destination grant；该 grant 送往相应 source request queue 312 弹出包并触发其发往被选中的目的端口（[0055]）。

**7) 工作流程（FIG. 4，400）**：404 接收待分发包 → 408 保持在 source request queue → 412 把 super destination group 映射到多个目的端口 → 416 基于收包时刻的信用与端口可用性做 source-to-destination 指派 → 420 把多个目的端口重映射回 super destination group → 424 触发包从源请求队列释放 → 428 使包发往被选中的目的端口。

**8) 拓扑与顺序变体**：arbiter block 可居于 plurality of mapper blocks 与 plurality of remapper blocks 之间（[0020]、claim 17），S-D/D-S 两仲裁器顺序可互换（[0050]）；不同 source request queue 可映射到不同 super destination groups（[0021]）；mapper block、source request queue 均可按 per-source、per-super-destination 级提供（[0049]）。

**原文笔误标注**：[0052] "the receiver's 300 source request queue 312" 中 300 依图应为 Receiver 308；[0057] "DDS crossbar dispatcher 304" 依上下文应为 300；本文已据图与上下文校正。

## 4. 权利要求摘要

共 20 项权利要求，3 项独立权利要求（claim 1 DDS crossbar、claim 14 系统、claim 19 开关）。

**独立权利要求 1（DDS crossbar）**：一个或多个自适应路由电路，用于：在分发包之时跟踪目的信用与端口可用性；把多个目的分组为 super destination groups；在 super destination group 内执行动态目的路由；并在分发包之时用该组的信用与端口可用性选择包的输出目的。

**独立权利要求 14（分发包的系统）**：按 super destination group 维护、接收待分发包的源请求队列；接队列输出的 mapper block（把 super destination group 映射到多个目的端口）；做 source-to-destination 指派的 arbiter block(s)；接仲裁器输出的 remapper block（把多个目的端口映射回 super destination group）。

**独立权利要求 19（开关）**：具有自适应路由电路的 crossbar，其电路：把包保持在按 super destination group 维护的源请求队列中；把组映射到多个目的端口；基于收包时刻的信用与端口可用性做指派；把目的端口重映射回组；触发包从队列释放并使其发往被选中的目的端口。

从属权利要求按主题分组：

- 结构链逐级附加（claim 2–7）：2 加源请求队列；3 加 mapper block（基于分发时信用可用性映射）；4 加 arbiter block；5 仲裁器基于分发时目的端口可用性做指派；6 加 remapper block；7 remapper 触发包处理后从队列移除；
- 包类型（claim 8、9）：静态目的可路由包 / 动态目的可路由包；
- 缓冲与仲裁增强（claim 10–13）：10 per-source 入口数据缓冲；11 缓冲按目的虚拟输出排队；12 二维仲裁器同时支持静态与动态包；13 每周期重新判定信用与端口可用性；
- 系统权多实例拓扑（claim 15–18）：15 多个 mapper block 各映射不同组；16 多个 remapper block；17 仲裁器居于 mapper 群与 remapper 群之间；18 多个队列映射到不同组；
- 开关权附加（claim 20）：每周期重判定 + 支持静态/动态两类包的二维仲裁器。

## 5. 与专题主题的关系——WDU→Work Distribution Crossbar→GPC→SM 链路中的位置

**NVIDIA 侧**：在同目录 US11182207B2 解析所述的 PPU 架构中，Work Distribution Unit 236（WDU）把任务送往 GPC 208，而 GPC 内的 **Work Distribution Crossbar 330** 负责把工作分发到 GPC 内多个 SM 310——这正是本专利所抽象的"一个源、多个等价目的"分发场景。把 DDS 术语映射到该链路：super destination group ≈ 一个 GPC 内可承接同类工作的 SM 集合；source request queue 312 ≈ 分发源侧按组维护的派遣队列；mapper 316 把"发给组内某个 SM"展开为多条候选 SM 端口；二维仲裁器 320/324 依据实时信用与端口可用性（如某 SM 是否停滞、其入口是否有空位）在本周期决定实际发往哪个具体 SM；remapper 328 归并 grant 并触发队列弹出。[0005] 明示该机制更适合 GPU crossbar 的小包环境，[0004] 所述"一个目的比其它目的更停滞"正对应 GPC 内部分 SM 因长延迟操作停滞、其余 SM 空转等待的真实图景。因此本专利可视为专题核心部件 Work Distribution Crossbar 330 的微架构实现专利注脚：它把"分发时刻动态选择目的 SM"写成了 mapper—arbiter—remapper 硬件流水。需如实说明：说明书通篇使用通用交换术语（source/destination port），未显式点名 WDU、GPC、SM；上述对应是本文基于 GPU 语境与同目录架构的推断，但未超出专利语义覆盖范围。

**AMD 侧对应**：AMD GCN/RDNA 侧 SE 内的 SPI（Shader Processor Input）向下辖 CU 分发 wavefront 时面临同类问题：SPI 按 CU 组/SH 维护 wave 队列（对应按 super destination group 维护的 source request queue 312），并在分发时刻依据各 CU 的资源可用性（wave slot、VGPR/LDS 等信用）从"该 wavefront 可路由的 CU 集合"（等价于 super destination group）中动态选择目的 CU——即 AMD 侧的 at-dispatch 目的选择。差别在于：AMD 公开资料多将其表述为调度规则，而本专利把 mapper 展开→二维仲裁→remapper 归并固化为一整套硬件权利要求，并显式保护静态/动态两类包与每周期重判定。专题目录名中的"SPI SQ"（SPI 队列）与本专利 source request queue 312 可直接对照。

## 7. 评价与启示

**技术重要性**：
- 把自适应路由的决策点从"分发前"移到"分发时/仲裁时"，使目的选择能逐周期跟踪瞬态争用；对 GPU 这种小包、仲裁频繁、争用变化快的场景，这正是应有的决策时间粒度；
- super destination group + mapper/remapper 的两级结构巧妙：排队按"组"级（控制队列数目、避免全互连 VOQ 爆炸），仲裁按"端口"级（给二维仲裁器更多可选 arc、提高 grant 率），mapper/remapper 完成两级间的双向换算；
- SCD（round-robin）+ DCS（LRU）front fill 加 WFA backfill 是经典二维分配器组合，专利的增量贡献在于把"信用驱动的 mapper 展开"与"at-dispatch 选择"嵌入该经典框架，并以 claim 1–20 形成 crossbar/系统/开关三个层面的权利要求链；
- 静态/动态两类包与 per-source VOQ 的设计使 DDS 机制可以渐进式引入既有 crossbar：静态包走原定目的、动态包才启用组内动态选择（[0053]），对已在流的 GPU 互联设计是低风险的增量改造。

**局限性（基于文本可推断）**：
- 说明书以通用交换语言撰写，未绑定 GPU 实例，也无信用粒度、队列深度、mapper 扇出与面积/时序开销的量化数据；附图仅一个 12×12 示例；
- 静态包仅被"兼容支持"（[0053]），核心收益依赖动态包在流量中的占比；
- 原文存在若干疑似笔误（[0052] receiver's 300、[0057] dispatcher 304），引用时需以图与上下文校正；
- 与 Work Distribution Crossbar 330、AMD SPI 的对应系本文架构推断，专利原文未自认。

**对理解 GPU 前端互联的价值**：结合同目录 US11182207B2（TMU 预取）可见，NVIDIA 在 WDU→SM 链路上做了两端硬件化：前端把依赖解析与预取写进任务描述符，末端把"最后一跳"分发写进 crossbar 的 at-dispatch 动态目的选择。本专利为专题"16_WDU_to_SM_and_SPI_SQ"补齐了 NVIDIA 侧"工作从 WDU 分发到 SM 时如何选目的"的微架构视图，并与 AMD 侧 SPI→CU 分发形成镜像对照。
