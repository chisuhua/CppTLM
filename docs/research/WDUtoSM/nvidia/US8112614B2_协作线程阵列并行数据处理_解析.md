## 2. 发明背景与待解决问题

**技术背景**（按 BACKGROUND 部分表述）：并行处理把一个计算划分为多个 thread（线程，即"一个特定程序使用特定输入数据的一次执行实例"）。并行架构分两类：MIMD（每核独立取指发射，灵活但面积/成本高）与 SIMD（单一指令单元向多个处理引擎并行发射同一指令，面积省、成本低，代价是并行度受限于同一指令的并行实例数）。GPU 历来用很宽的 SIMD 架构做图像渲染（vertex shader / pixel shader 对大量顶点/像素执行同一程序），典型配置是一个 SIMD 核跑顶点着色、另一个同规模核跑像素着色。

**现有技术的不足**：并行架构通常要求并行线程彼此独立（不得使用其他线程产生的数据）；即使提供数据共享能力也很受限——部分 SIMD/MIMD 机器提供全局共享存储器或 global register file，一些架构（如 systolic array）只有局部共享寄存器。关键缺陷在于：在这些机制下，**程序员必须为每个线程单独编写数据共享代码，导致各线程不再执行同一程序**，丧失了 SIMD/数据并行"同一程序、不同数据"的根本优势。

**待解决问题**：提供一种并行处理系统与方法，让并发执行的线程之间能够方便地共享数据（包括中间结果），同时保持"阵列内所有线程执行同一程序"的性质，并使程序的写法与具体执行硬件解耦。

### 3.2 关键机制详解

**（1）CTA 定义与 thread ID 语义**。CTA（cooperative thread array，协作线程阵列）是"一组并发执行同一程序（CTA program）以把输入数据集变换为输出数据集的线程"。每个线程在 launch 时被分配阵列内唯一的 thread ID，用于决定：处理输入数据集的哪个部分、与哪些线程共享中间结果、产出/写出输出数据集的哪个部分。thread ID 支持多维索引（i0,i1,i2，位域编码，各维上限由位宽决定，如 D0≤2^16、D1≤2^10、D2≤2^6）；另有全阵列共用的 CTA identifier（可为多维，如 tile 在图像中的坐标），配合 thread ID 可算出全局坐标（屏幕坐标 = CTA ID 定 tile 位置 + thread ID 定 tile 内偏移）。由于所有线程执行同一程序，thread ID 的具体分配方式不影响结果，CTA 程序因此与硬件无关；多个 CTA 可组成 array/grid 解决更大问题（如 HDTV 滤波每帧约 8K tile、即约 8K CTA）。

**（2）三阶段控制流程与 thread ID 生成硬件（FIG. 10）**。core interface 128 按 state → load → launch 工作：① state 阶段（1002–1006）：接收并锁存状态信息（输入数据集大小、每线程 local register 用量、程序起始 PC、阵列维度 D0/D1/D2 等），状态只在变化时更新；收到新维度后，increment unit 506 从 (0,0,0) 起顺序生成前 P 个 thread ID（INIT_0…INIT_{P-1}）存入 state registers 406，step calculation unit 508 把 SIMD 组宽度 P 换算到三维索引空间得步进三元组 (S2,S1,S0)（S0 = P mod D0 或 P，S1 = (P/D0) mod D1 或 0，S2 = P/(D0*D1) mod D2 或 0，视 P 与各维大小关系而定）；② load 阶段（1010–1016）：收到 "begin CTA" 命令后把输入参数/数据装入 global register file 306；③ launch 阶段（1018–1026）：选择空闲 group index GID → 把一组 P 个 thread ID 并行写入 local register file 304 → 指示 core 126 以 SIMD group 启动这 P 个线程 → 用 P 个并行加法器 806 把 (S2,S1,S0) 加到当前组各 thread ID 上（带跨维进位：i0 超 D0 进位到 i1，i1 超 D1 进位到 i2）生成下一组 ID，循环直至全部 T 个线程启动完毕（组数 = T/P 向上取整，最后一组不满 P 时用 active mask 标记空闲引擎）。加法器 900 可在单时钟周期内算出新 ID（维度限为 2 的幂时模运算退化为截位），相邻 SIMD group 发射间隔可短至一个时钟周期。变体：初始 ID 与步进也可由 GPU 上游部件或 CPU 上的驱动程序预先算好作为状态参数下发。

**（3）SIMD group 执行模型（FIG. 3）**。core 126 含 P 个（如 8、16）同构 processing engine 302，每引擎最多并发 G 个（如 24）线程，单指令单元 312 每周期向全部 P 个引擎发射同一指令，故核内最多 P*G 个线程在飞（P=16、G=24 时为 384，部分实施例中 P*G 即 CTA 线程数上限）。SIMD group 是"每引擎一个线程"的至多 P 线程组，以 GID 作为上下文标识选择各引擎在 local register file lane 中的线程状态；组内线程分支发散时各引擎维护本地 PC，PC 不符即按 no-op 忽略，PC logic 314 负责跟踪发散并最终重同步；arbitration logic 320 每周期从 G 个组中任选一组取指发射（组内顺序、组间任意序）。"supergroup" 变体把两个以上 GID 关联，用连续周期发射同一指令，以减少每组状态开销，极端时可扩展至整个 CTA。core 126 还可运行在 2 倍于 core interface 128 的时钟上，等效加倍引擎数。

**（4）共享存储器寻址与数据共享**。输入数据集装入所有线程可访问的共享存储器（global register file 306 或 on-chip shared memory 308）；CTA 程序中的读写指令把目标地址定义为 thread ID 的函数（确定性函数即可，如 InputData[i1, i0+1]），每个线程用自己的 thread ID 计算地址，从而实现任意模式的线程间数据共享——生产者写到由自身 ID 决定的位置，消费者读由自身 ID 算出的同一位置；边界情形（如右边缘像素）可用条件分支处理。读前须与写者同步（semaphore、barrier 等）。

**（5）Barrier 同步（FIG. 11A/11B）**。在 CTA 程序中插入 barrier 指令定义同步点；barrier detection circuit 1112 从发射流中截获 barrier 指令交给 barrier synchronization logic 1100：首条 barrier 指令的立即数装载目标值（预期到达的 SIMD group 数）入 target register 1105，此后每收一条 barrier 指令 counter 1104 加一并置对应 GID 的 wait/go 位为 wait；selection logic 1110 不再为 wait 组选指（其余组继续执行，几乎不浪费周期）；comparison circuit 1106 发现计数达到目标即发 reset，清零计数器、复位目标寄存器并把所有 wait 位置 go，等待组最快一个周期内恢复执行。多 barrier 版本 1130 支持 B 个 barrier point（BarID 区分，B 套 counter 1134/target 1135/wait-go 1138），各 barrier 独立释放；barrier 资源还约束并发 CTA 数（如每 CTA 用 4 个 barrier、共 16 个则至多 4 个 CTA 并发）。指令变体：barrier arrival（到达不等待，适合纯生产者线程）与 barrier arrive-and-wait（到达并等待，适合消费者），可按 thread ID 奇偶等条件选择执行；目标值也可动态指定为"全部在飞线程"（如用特殊值 0 表示）。以 SIMD group 为到达计数单位简化硬件，条件 barrier 按"组内一线程到达视为全组到达"语义处理。

**（6）多核扩展与 CTA 分发（FIG. 12）**。GPU 122 含 N 个 processing cluster 1202，每簇由一个 core interface 128 控制 M 个 core 126，全芯片并发线程数 N*M*P*G（可达数千）。渲染时 geometry controller 1204 / pixel/CTA controller 1206 分别输送几何与像素数据；通用计算时 **pixel/CTA controller 1206 复用为 CTA 状态、输入数据与命令的传送通道**。CTA 到簇/核的分发给出两种机制：① 渲染管线中的数据源收集各 cluster（或各 core）的可接收能力（availability）反馈，为每个 CTA 选择目的；② CTA 数据沿 cluster 链依次转发，直到有余力的 cluster 接收。由于 CTA 线程间需要共享数据，**一个 CTA 限定在单个 core 126 内执行，不可跨核拆分**；增加核数只提高 CTA 并发度，不改变单 CTA 尺寸上限（P*G）。单核内可驻留多个 CTA（线程数不超 P*G/2 时可并发两个以上），受寄存器容量、barrier 数及状态参数管理方式约束。

**应用示例**：FFT 蝶形运算（每级经 global register file 交换中间值并 barrier 同步）、矩阵乘法与线性方程求解（多维 thread ID 天然支持行主/列主寻址与转置）、卷积滤波、可分离滤波（N 线程先算行向量、barrier 后再算列向量）。配套 API 由 CPU 侧驱动提供，应用只需定义 CTA 程序、阵列维度、CTA 个数与输入数据，执行细节对程序员透明。

## 4. 权利要求摘要

共 17 项权利要求，3 项独立权利要求（claim 1 方法、claim 9 处理器、claim 15 装置）。相较母案 7,861,060 的宽泛主题（thread ID 决定"处理行为"），本延续案的独立权利要求全部收窄到"**thread ID 作为输入计算共享存储器中待访问位置的标识符**"这一落点。

**独立权利要求 1（方法）**：定义线程阵列（各线程执行同一程序处理输入数据集的一部分）；处理器为每个线程分配阵列内唯一的 thread ID；并发执行全部线程，执行期间每个线程用其 thread ID 作为输入计算共享存储器中待访问位置的标识符，且该共享存储器的每个位置对阵列内每个线程可访问。

**独立权利要求 9（处理器）**：processing core（多个并发执行线程的 processing engine + 每个位置均可被所有线程访问的 shared memory）；耦合的 core interface logic，其 launch module 发起线程阵列的并发执行，并在指示 core 启动执行前为每个线程分配阵列内唯一的 thread ID；执行期间线程用该 ID 计算共享存储器访问位置。

**独立权利要求 15（装置）**：存储输入数据集的 system memory；耦合的处理器，含多个同构 processing engine（输入数据集对每个引擎可访问）与 on-chip shared memory（每位置对每个引擎可访问）；每个引擎用所执行线程的 thread ID 计算片上共享存储器中待访问位置的标识符。

从属权利要求按主题分组：
- 输入/输出定位（claim 2、3、10、11）：thread ID 决定读入输入数据的位置、产出输出数据的子集；
- 地址函数指令化（claim 4、5、6）：程序含"用 thread ID 计算函数"的指令，该指令为对共享存储器的写/读，位置是 thread ID 的函数；
- 线程间数据交接（claim 7）：第一线程按自身 ID 函数写入目标位置，第二线程按自身 ID 函数随后读取同一位置；
- 数据重叠划分（claim 8）：两个线程处理输入数据集中相互重叠的部分；
- thread ID 存放（claim 12、13、17）：ID 存于分配给该线程的 local register file 表项/不同 lane，执行时读出并参与地址计算；每 lane 仅一个引擎可访问；
- 状态驱动生成（claim 14）：state module 接收并保存含阵列尺寸信息的状态，launch module 据此计算各线程 ID；
- 共享存储器形态（claim 16）：on-chip shared memory 含共享寄存器文件。

## 5. 与专题主题（WDU→SM 分发链路）的关系

本专利在 NVIDIA「WDU → Work Distribution Crossbar → GPC → SM」链路中的定位可从两个层面理解：

**（1）CTA 是 WDU 分发到 SM 的基本工作单元，本专利奠定了这一概念基础。** 后世 NVIDIA 架构中，Work Distribution Unit（WDU）从 Task Management Unit 接收任务，把 grid 切分成一个个 CTA（软件层面即 CUDA 的 thread block），经 Work Distribution Crossbar 分发到各 GPC 内的 SM 执行。本专利（母案 2005 年提交）首次定义了 CTA 的全部核心属性：阵列内唯一的（多维）thread ID、全阵列共享的 CTA ID、阵列级共享存储器、阵列内 barrier 同步、以及"**CTA 是不可跨核拆分的最小工作单元，多个 CTA 可动态并发驻留**"——这正是后来 WDU→SM 分发语义的源头。CUDA 中的 threadIdx/blockIdx/gridDim、`__syncthreads()`、shared memory 均可一一对应到本专利的 thread ID/CTA ID/barrier/global register file。

**（2）FIG. 12 展示了分发链路的原型，只是当时尚无 WDU/GPC/SM 命名。** 按功能映射：pixel/CTA controller 1206 与 geometry controller 1204（向上承接渲染管线/CTA 命令流，向下馈送 core interface）≈ 后世 WDU 的上游工作交付路径；core interface 128（state/load/launch 三阶段、自动分配 thread ID）≈ SM 内的 CTA 装载/启动前端（今 SM 前端 launch 硬件接收的 "begin CTA" 类命令即源于此）；processing cluster 1202 ≈ 后世 GPC；core 126 ≈ 后世 SM；而文本给出的两种 CTA 分发机制——按 cluster 可用性反馈选择目的地、或沿 cluster 链转发直至被接收——正是 Work Distribution Crossbar 做负载均衡分发在概念上的前身。

**AMD 侧对应概念**：CTA ≈ workgroup（由命令处理器/图形前端分发到 Compute Unit，CU）；SIMD group ≈ wavefront（32/64 线程 lockstep 执行，GID 的角色由 wave 槽位承担）；global register file / on-chip shared memory 308 ≈ LDS（Local Data Share，片上共享存储）；local register file 304 的分 lane 组织 ≈ CU 内按 SIMD 通道划分的 VGPR 堆。值得注意的是，本延续案首页 References Cited 中出现了 AMD 相关文献——审查员引用的 Mantor et al.（US 2009/0300621 A1，AMD 架构专利）、AMD Developer Forums（"LDS: More info requested"，2008）、ATI Stream Computing 用户指南/技术概览等，说明该案审查时 AMD 的 workgroup/LDS 公开材料已作为对照文献进入审查档案，两侧概念的同构性在专利审查层面即有印证。

**在专利族中的位置**：母案 11/305,178（2005-12-15）→ US 7,861,060；本案为其 continuation（12/972,361，2010-12-17 提交，2012-02-07 授权），把权利要求收窄到"thread ID 计算共享存储位置"这一 AMD/OpenCL 语境下更具区分度的落点，并因此附有 terminal disclaimer。同日姊妹案 7,584,342（SIMD 发射）与 7,788,468（CTA 同步）分别覆盖执行与同步维度；四篇共同受让申请（11/554,5xx 系列等）构成 2006 年后续扩展。整体上本族是 NVIDIA 统一着色器/GPGPU 架构（约对应 G80 时代）的奠基性专利组合，本案是其中"工作单元定义"维度的授权文本。

## 7. 评价与启示

**技术重要性**：
- 本专利（连同母案与两篇姊妹案）从硬件层面定义了 CUDA thread block 的原型：CTA、多维 thread ID/block ID、片上共享存储、barrier 同步、"同一程序不同数据"的自动参数化（thread ID 由 launch 硬件自动分配、程序员免配置）。今天 CUDA/OpenCL 的 grid-block-thread 三级模型与 WDU→SM 分发语义，均可回溯至 2005-12-15 这一优先权日的三份申请；
- thread ID 生成硬件（初始 ID + 步进 + 并行加法器，单周期出下一组 ID）把"数千线程的编号与启动"从软件路径移入核接口硬件，是 CTA 能够作为低成本分发单元的前提——WDU 只需交付 CTA 级状态，SM 前端即可自行展开全部线程；
- barrier 以 SIMD group 为计数单位、arrive/arrive-and-wait 分离、多 BarID 独立释放等设计，直接预示了 `__syncthreads()` 及其硬件实现约束（barrier 数限制并发 CTA 数）。

**局限（基于文本可推断）**：
- CTA 被限定在单核内（因线程间需共享数据），尺寸上限为 P*G，核数增加只能提升 CTA 并发度而无法放大单 CTA；这一约束延续至今（thread block 仍不可跨 SM，跨 SM 协同需 grid 级机制）；
- 共享存储以 global register file/on-chip RAM 呈现，尚无后世 shared memory 与 L1 cache 的统一管理及 bank 冲突等细节；文本亦无 L2/显存层次化的 CTA 数据通路描述；
- 分发机制仅给出可用性反馈选路、簇间链式转发两种概念方案，未形成具体 crossbar 拓扑；WDU、GPC、SM 等术语与层级在本文中尚未出现；
- 提取文本存在多处 OCR 乱码/疑似笔误（如受让人 "Nila Corporation"、state registers "416" 应为 406、"core 310" 应为 core 126、首页一条引用文献编号乱码），均已如实标注，以说明书正文与专利号本身为准。

**对理解 WDU→SM 分发的价值**：要理解"WDU 往 SM 里到底分发什么"，必须回到本专利——分发的对象是自带唯一 ID 空间、自带共享存储语义、自带同步原语、且保证单核内完成的自包含工作单元；正因 CTA 具备这些封闭性，WDU/Work Distribution Crossbar 才能只做"按资源余量投递 CTA"这一件事而不必介入线程级调度。本专利提供了该契约的最早完整文本，是串联「任务描述符 → WDU → crossbar → GPC → SM」专题中"SM 端接收语义"一章的锚点文献；与本地目录中较晚的 TMU/任务描述符专利对读，可清晰看到 NVIDIA 前端分发体系"工作单元概念（2005）→ 分发与调度硬件化（2008+）→ 任务图/描述符化（2010s）」的三阶段演进。
