## 2. 发明背景与待解决问题

**应用场景**（[0001]、[0035]）：CPU 以 draw calls（绘制调用）在 GPU 上启动 kernel；GPU 用多个 compute unit（计算单元）以 SIMD 方式执行线程（work items），线程被分组为 workgroup（工作组），在相应计算单元上并发/并行执行。

**待解决问题**（[0025]–[0027]），三个层面：

1. **运行时负载不均**：传统 workgroup 负载均衡采用 round-robin（轮询）或基于静态参数的方法，隐含假设各 workgroup 消耗基本相同的 shader engine（着色器引擎）时间与资源；实际上不同 workgroup 消耗迥异（如不同的 memory/cache 冲突），使某些引擎延迟更高。
2. **制造物理不对称**：硅片制造差异与容差使"设计相同"的 shader engine 实际可用的 compute unit 数量不同，各引擎 active CU 数量与处理效率先天不齐。
3. **chiplet 化放大问题**：chiplet 式 GPU（计算逻辑分布于多个 active die、编程模型视为单一单体，[0028]）中，分布式 shader engine/ALU/CU 使上述静态分发安排"相对低效"。

**现有技术的不足**：round-robin/静态分发既看不见制造差异（active CU 数量），也看不见运行时差异（各引擎当前负载/进度）。

**方案目标**：command processor（命令处理器，CP）基于 "indications of available resources"（可用资源指示）——physical parameters（物理参数，如 active CU 数量）加 current status information（当前状态信息，如进度与空闲槽位）——动态地把每个 workgroup 指派给 shader engine，实现负载均衡。

### 3.2 关键机制详解

**两类决策输入**：

- 物理参数 268/368/468：指明各 SE（FIG. 3 实施例中还有各 shader array）的 active compute unit 数量，反映制造 harvesting 不对称；也可被 SE 上报动态更新（如 active CU 数量变化，[0042]、[0047]、[0051]）。
- 当前状态信息 270/370/470：包括 SE 的当前进度（已完成所指派 workgroup）与可用 workgroup 执输入/"slots"（槽位）的数量或比例（[0042]、[0051]）；CP 可维护各 SE 上 workgroup 分配队列的状态作为该信息（[0053]）。

**闭环分发流程（FIG. 4 例程 400，[0048]–[0054]）**：405 接收执行命令（如 CPU draw command）→ 410 生成待分配的多 workgroup → 415 结合 468 与 470 动态确定每个 workgroup 的 SE 归属（active CU 多的 SE 可获更多工作，[0051]）→ 420 把各 workgroup 指派给所确定的 SE → 425 从被指派 SE 接收可用资源指示并回写 470（上报可发生在指派前/处理中/完成时等多种时机，[0053]）→ 430 判定是否全部命令完成，"N" 回 415 继续分配剩余 workgroup，"Y" 回 405 等待新命令。

**执行路径与反馈路径（FIG. 2，[0038]–[0042]）**：dispatch controller 265 经 compute dispatch bus 201 把所指派 workgroup 的信息发送给对应 SPI 250（某些实施例中称 shader resource manager，着色器资源管理器，[0038]）；SPI 接收后由 SE 经"shader engine scheduler"（引擎内调度器，图中未示，[0041]）把 workgroup 分布到其 CU 集合 230 执行；SPI 同时经 201 向 dispatch controller 上报进度/槽位及物理参数更新，构成"上报→决策→指派→再上报"的闭环。

**制造不对称示例**：FIG. 2 中 225-1/225-2 拥有 N 个 active CU，而 225-0/225-3 因 inactive CU 230-1 少于 N——inactive 的成因可能是 die 的不可用部分，或虽可工作但因制造容差标准被"关掉"（[0039]）；FIG. 3 同理（[0046]）。round-robin 等静态策略会向这些"弱引擎"派发等量工作，本专利则把 active CU 数量变成一等分发参数。

**粒度与规模扩展**：FIG. 3 实施例把状态/参数从 SE 级细化到 shader array 级（SE/SA，[0047]）；系统层面，每个 graphics processing device 可以是一个 GPU chiplet，多设备经 PCI-E 等高性能互连，各设备的 dispatch controller 相互协调动态指派 workgroup，不同 workload 可在不同 chiplet 上以不同频率运行（[0013]、[0028]–[0029]、claim 15–16）。

**多 CP 协调**（[0036]）：GPU 可含多个 command processor，彼此合作协调 workgroup 到 SE 的指派，并可基于各 CP 所关联 shader engine 的能力，动态调整各 CP "拥有"（owned）的工作量——表明分发决策层本身也可水平扩展，与 claim 15 的跨设备协调互为表里。

## 4. 权利要求摘要

共 20 项权利要求，3 项独立权利要求（1、8、15）。

**独立权利要求 1（图形处理设备）**：多个 shader engine（每个 SE 含各自数量的 active compute unit）；耦合的 command processor；CP 的 dispatch controller——后者基于至少部分地来自"至少部分 SE 各自关联的可用资源指示"，把多个 workgroup 中的每个动态指派到相应 SE 执行。

**独立权利要求 8（方法）**：基于接收到的一个或多个命令，生成用于指派到多个 SE（每个 SE 含各自数量 active CU）的多 workgroup；并基于可用资源指示把每个 workgroup 动态指派到相应 SE 执行。

**独立权利要求 15（多设备系统）**：多个 graphics processing device，各含多 SE + CP + dispatch controller；其中每个设备的 dispatch controller 与一个或多个其他设备的 dispatch controller 协调以动态指派 workgroup——覆盖多 GPU/多 chiplet 联合分发的权利要求布局。

从属权利要求按主题分组：

- 物理参数类（2 / 9 / 17）：资源指示含物理参数，指明第一 SE 的 active CU 数量；
- SE 主动上报类（3 / 10 / 18）：dispatch controller 从第一 SE 接收其可用资源指示；
- SPI 路径类（4 / 11）：经各 SE 关联的 SPI 动态指派，且资源指示含 CP 从关联 SPI 收到的状态信息；
- 状态内容——进度类（5 / 12 / 19）：状态信息含 SE 处理所指派 workgroup 的当前进度；
- 状态内容——槽位类（6 / 13）：状态信息含一个或多个可用 workgroup assignment slots；
- 状态维护类（7 / 14 / 20）：CP 基于资源指示维护各 SE 的当状态信息；
- chiplet 类（16）：每个 graphics processing device 包含 GPU chiplet。

## 5. 与专题主题的关系：AMD CP→SPI→SQ→CU 链路中的位置与 NVIDIA 对应

**在 AMD 链路中的位置**：本专利的动态分发决策点在 CP 内部的 dispatch controller 265/365，属于链路前端的 SE 级宏观均衡层；但其信息源与执行落点都落在 SPI 分发层：(1) 信息源——SPI 250/350（又称 shader resource manager）是唯一运行时遥测出口，经 compute dispatch bus 201/301 向 CP 上报进度、可用槽位与 active CU 数量变化；(2) 执行落点——workgroup 指派由 CP 下达至 SPI，SPI 接收后由 SE 内经引擎内调度器（正文"shader engine scheduler（未示出）"，对应实际硬件的 SQ/sequencer 波前调度环节）分布到 CU。因此本专利覆盖链路中"CP 主导、SPI 上报与接收"的 CP→SPI 段，属于 SPI 分发层的 workgroup 向 CU 动态分发策略的上半环；SPI→SQ→CU 段交由 SE 自治。与同目录 EP3785113B1（反馈引导工作组拆分分发）、EP3803583B1（多内核波前调度器）、US10579388B2（着色器核心资源分配策略）等相比，本专利聚焦 CP 侧跨 SE 负载均衡而非 SE 内波前级调度，共同构成 AMD 多层分发专利布局。

**NVIDIA 侧对应**：对应环节是 TMU→WDU（Work Distribution Unit，工作分发单）→Work Distribution Crossbar→GPC/SM，以 CTA（Cooperative Thread Array，协作线程阵列，与 AMD workgroup 功能等价）为分发单元：US11182207B2 中 WDU 236 接收任务描述符指针并经 Work Distribution Crossbar 330 把任务分发到 SM 310 执行；同目录 US8112614B2（协作线程阵列并行数据处理）亦属 CTA 向 SM 并行分发脉络。差异：NVIDIA 的 WDU/crossbar 是中央全连接、直达 SM 的单层分发（反馈路径短），AMD 本专利是"CP 先均衡到 SE/SPI、SE 内调度器再分布到 CU"的两层结构（层级化、chiplet 可扩展）；两者面对同一问题域——运行时不均衡与硬件不对称下的负载均衡，只是分发粒度与遥测路径不同（NVIDIA 靠 WDU/crossbar 对 SM 的可见性，AMD 靠 SPI 逐 SE 的 slots/进度上报）。

## 7. 评价与启示

**技术重要性**：

- 把"制造不对称"（active CU 数量差异，即 harvesting）从隐含硬件事实提升为一等分发参数，契合 chiplet 时代多 die GPU 的现实；
- 以 SPI 为逐 SE 遥测与接收点，建立"上报→决策→指派→再上报"的硬件闭环，使负载均衡从 round-robin/静态转为运行时反馈式；
- 权利要求 15 把多设备 dispatch controller 协调写入独立权利要求，为 chiplet 组合与 PCI-E 互连下的跨卡协调铺设权利基础；
- 流程图 400 中 425→415 的回环表明这是一种持续运行的在线均衡循环，而非一次性静态映射。

**局限性（基于专利文本）**：

- 分发粒度止于 SE 级（FIG. 3 实施例细化到 SA），SE 内 CU 级分布依赖正文未示出的"shader engine scheduler"，闭环未达 wavefront 级；
- 文本仅称指派"based at least in part on"两类指示，未给具体算法/权重，权利要求偏框架性；
- 上报频率、compute dispatch bus 201/301 带宽开销、状态信息存储规模均无量化讨论；
- FIG. 3 的 CP 图面编号（260/265/268/270）与正文（360/365/368/370）不一致，系扫描件图注瑕疵，阅读以正文为准。

**启示**：与 NVIDIA WDU/crossbar 直达 SM 的脉络对照，可见两种工作分发哲学——中央全连接单层分发（NVIDIA）与层级化宏观均衡+局部自治（AMD）；在 chiplet 化与 harvesting 背景下，后者"逐 SE 遥测+中央均衡"的结构更具扩展性，而本专利正是该结构的权利要求化表达。
