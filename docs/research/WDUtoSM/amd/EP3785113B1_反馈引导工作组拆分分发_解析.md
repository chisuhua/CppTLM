## 2. 发明背景与待解决问题

**基本模型**（[0002]–[0003]）：GPU 以 work-item（工作项，即线程）为并行执行实例，以 global ID 与 local ID 区分；compute unit（CU，计算单元）是一组处理单元（SIMD 单元）的集合，同步执行多个 work-item；workgroup（工作组）内同时在 CU 上执行的 work-item 子集称为 wavefront（波前，亦称 warp/vector），其宽度由 CU 硬件决定；workgroup 是 wavefront 的集合，GPU 以 workgroup 为粒度底层计算资源分发工作。

**待解决问题**：传统分发规则要求**单个 CU 上同时具备支撑整个 workgroup 的全部资源**——至少包括 vector/scalar register（向量/标量寄存器）、wavefront slot（波前槽位）与 LDS（local data share，本地数据共享）空间——才允许分发。但硬件实际以 wavefront 为粒度执行，执行粒度小于分发粒度，因此经常出现"整组放不下、但其部分 wavefront 其实放得下"的局面，硬件却仍拒绝该分发请求。后果（[0003]、[0008]）：

1. workgroup 因资源不可用而停顿（stall）增多；
2. 应用的前向推进（forward progress）受阻；
3. GPU 的 wavefront level parallelism（WLP，波前级并行）与 thread level parallelism（TLP，线程级并行）被压低。

**现有技术**（[0004]）：US 2014/0156975（Sridharan et al.）披露冗余线程方法（同簇双 lane 复制计算并比对结果）；US 9,317,296（Rogers et al.）披露在分支发散时覆写 SIMD 执行掩码。两者均未解决"分发粒度大于执行粒度"导致的资源碎片与停顿问题。

### 3.2 关键机制详解

**机制一：拆分判定与适配策略（FIG. 5，control logic 500）**。workgroup allocation fail detection unit 502（分配失败检测单元）发现某 workgroup 无法装入单个 CU 时触发 split workgroup dispatcher 506 内的 scoreboard checker 508；后者查询 fits detection unit 510（可容纳性检测单元）判断全部 CU 的合计剩余资源能否装下该 workgroup 的各 wavefront。fits detection unit 510 支持三种策略：Max Fit 510A（尽量把多个 wavefront 塞进同一 CU，用最少 CU 数）、Equal Fit 510B（在各 CU 间均摊 wavefront）、Programmable Fit 510C（按可编程策略适配）。

**机制二：反馈引导的 CU 选择（FIG. 5–6）**。compute unit selector 512 在多个候选算法 516 中选择：① RR-FCFS（round-robin, first-come first serve，轮询先来先服务）；② FB-COMP（least compute stalled，依据性能计数器反馈选计算停顿最少的 CU）；③ FB-MEM（least memory stalled，选内存停顿最少的 CU）。算法可由软件/硬件动态调整，由管理员、用户应用（固定策略或按运行条件动态调整）、OS 或驱动选定。FIG. 6 给出实现 610：WG allocation request buffer 615 缓存待分配 workgroup 并把请求送给 performance monitor module 620；后者基于 wavefront 数与当前 CU 可用资源给出 fit/no-fit 指示；CU perf comparator 635 为给定 dispatch-ID（如 kernel-ID）计算每个 CU 的 load-rating（负载评级，可取 CU 占用百分比或某资源使用/分配百分比，各资源评级可加权求和）并据此选出首选 CU；**SPI-RA 640（Shader Processor Input Resource Allocation，着色器处理器输入资源分配单元）**在选中的 CU 上为该 workgroup 分配资源。性能计数器监控对象至少包括：VALU 执行带宽、SALU 执行带宽、LDS 带宽、Load Store Bus 带宽、VRF 带宽、SRF 带宽，以及 L1/L2/L3 cache 与 TLB 的容量与带宽。

**机制三：记分板跟踪与跨 CU barrier 同步（FIG. 7–8）**。拆分分发后，split WG dispatcher 715 在 split WG scoreboard 720 中为每个拆分 workgroup 分配一个条目 504，字段包括：VMID（虚拟机标识）、global workgroup ID、workgroup dimension、wavefront 总数、compute unit mask（CU 掩码，标记分到哪些 CU）、barrier count（到达 barrier 的 wavefront 计数）、barrier sync enable（至少一个 wavefront 已到达 barrier 的标志）。同步流程（FIG. 8 时间轴 820A→820F）：任一 wavefront 到达 barrier 指令时其所在 CU/SIMD 使该 wavefront 停顿并发送 barrier sync enable 消息，记分板置位 sync enable 字段；其后每有 wavefront 到达 barrier，对应 CU 发送 barrier count update，计数递增（示例中 2→4→6）；当计数等于 wavefront 总数，记分板向 CU mask 标明的全部 CU 发送 barrier taken 消息放行所有 wavefront，并清零 barrier count 与 sync enable 字段。

**机制四：方法流程（FIG. 9–12）**。method 900：905 收到装不进单 CU 的 workgroup → 910 判断拆分后能否装入多 CU（否→915 等待资源后重试）→ 920 拆分分配 → 925 记分板跟踪。method 1000：1005 分配记分板条目 → 1010 置 CU mask → 1015 启动执行 → 1017 是否需同步（否则 1018 各 wavefront 独立执行）→ 1020/1025/1030 barrier 到达上报与置位 → 1040 递增 barrier taken count → 1045 判定是否全员到达 → 1050 复位字段并通知放行 → 1055 判定是否最后一个 barrier，否则循环。method 1100：1105 监控资源利用与争用 → 1110 收到 workgroup → 1115 依争用与对 workgroup 行为的预测，在常规单 CU 分发与 split-workgroup 分发间决策，并套用 max-fit/equal-fit/programmable-fit 策略（programmable-fit 以最小化各 CU load-rating 为目标摊放 wavefront）。method 1200：1205 经可编程上下文设置寄存器（可由 kernel mode driver 更新）选定被跟踪资源 → 1210 性能计数器跟踪 → 1215 按可编程间隔采样 → 1220 按 dispatch ID 计算各 CU 各资源的 load-rating（dispatch ID 为命令处理器分发 kernel 的单调递增编号，每个 VMID 有独立计数器）→ 1225/1230 新 workgroup 到来时查各 CU 评级 → 1235 选各资源评级最低的 CU 作候选 → 1240 分发 wavefront。（注：[0049]–[0050] 将 "performance counters" 写作 "program counters"，系原文笔误。）

从属权利要求按主题分组：

- 跨 CU 拆分的具体形态（claim 2、7）：同一 workgroup 的第一、第二 wavefront 分别分发到不同的第一、第二 CU；

## 5. 与专题主题的关系（WDU→SM 与 SPI→SQ 分发层）

**在 AMD「CP→SPI→SQ→CU」链路中的位置**：本专利正是 SPI/SQ 工作组分发层的核心机制。链路对应关系为：command processor 235（CP，接收 host 命令、调度 compute task）→ control logic 240 + dispatch unit 250（分发决策层）→ SPI-RA 640（FIG. 6 明确命名为 Shader Processor Input Resource Allocation，即在选定 CU 上执行资源分配的 SPI 资源分配单元）→ CU 255 内的 SIMD 单元执行 wavefront（SQ 为 CU 内的 sequencer，负责 wavefront 调度/取指，专利文本未单独展开）。其解决的核心矛盾正是该层的结构性问题：**workgroup 是分发粒度、wavefront 是执行粒度**；当一个 workgroup 因寄存器、wavefront slot、LDS 等资源需求过大而无法整体放入任何一个 CU 时，传统 SPI 分发只能停顿等待，本专利让 SPI/调度器把 workgroup 拆分为多个 wavefront 段（split dispatch）分发到多个 CU，并用集中式 scoreboard + barrier count 反馈机制跟踪各段的到达/完成情况，再以性能计数器反馈（load-rating）引导段到段的 CU 选择。换言之，它把 SPI 的"整组全有或全无"分配改成了"按 wavefront 段的碎片化分配 + 集中同步"。

**NVIDIA 侧对应**：NVIDIA 的分发模型是 WDU（Work Distribution Unit）把 grid 中的 CTA（thread block，对应 workgroup）逐个分发到 SM（对应 CU）。与 AMD 传统行为一致，**CTA 必须整体驻留单个 SM**——其尺寸受限于单 SM 的寄存器文件、shared memory 与 warp slot；CTA 放不下时该 SM 无法接收，但不存在把单个 CTA 拆到多 SM 的机制，超大工作只能靠扩大 grid（更多、更小的 CTA）绕开。因此 AMD 的 split workgroup dispatch 在问题空间上的 NVIDIA 对应物是：① 超大 grid 由 WDU 经 work distribution crossbar 按 SM 资源可用性逐 CTA 分发；② Hopper 起的 **thread block cluster**（线程块簇）——把多个 CTA 编组、协同调度到同一 GPC 内的多个 SM 上执行并支持 distributed shared memory 互访。两者方向互补：AMD 把"一个 workgroup"拆到多个 CU 以获得更大单组规模；NVIDIA 把"多个 CTA"绑成跨 SM 的 cluster 以获得跨 SM 协作；都是对"单 SM 资源墙"的硬件回应。另可对照：本专利的集中式 scoreboard barrier 与 NVIDIA cluster 内跨 SM 同步、以及软件层 CUDA cooperative groups 的 grid 级同步属于同类"跨执行单元的组级同步"问题域。

## 7. 评价与启示

**技术价值**：
- 直击"分发粒度 > 执行粒度"这一 GPU 前端分发的结构性矛盾：资源碎片导致整组停顿，拆分分发把碎片资源利用起来，直接提高 WLP/TLP 与应用前向推进；
- "反馈引导"是区别于静态拆分的要点：性能计数器（VALU/SALU/LDS/VRF/SRF/cache/TLB 等）按可编程间隔采样，按 dispatch ID 计算各 CU load-rating，选停顿（计算或内存）最轻的 CU，避免把拆分段丢进已经很忙的 CU 造成二次拥塞；策略（RR-FCFS/FB-COMP/FB-MEM）与适（Max/Equal/Programmable Fit）均可由驱动、OS、应用动态选择，工程弹性大；
- 集中式 split WG scoreboard（VMID、global WG ID、CU mask、barrier count、sync enable）把跨 CU barrier 同步收归分发层硬件，是对 CU 本地 barrier 机制的必要补丁——workgroup 语义（尤其 barrier）在拆分后必须由全局机构维持；
- 双版本 kernel（227A barrier+scoreboard / 227B GDS 或 atomic 同步）运行时择优，说明 AMD 预见到跨 CU 的 LDS/barrier 语义需要软件配合，并以功耗/性能/争用为目标做在线权衡；
- DOE PathForward 资助背景（Lawrence Livermore）提示该机制面向 HPC 场景——大 workgroup、资源紧张、强同步的 kernel 正是拆分分发的受益者。

**局限与代价（基于文本可推断）**：
- 跨 CU 同步路径变长：barrier 需经中央 scoreboard 往返计数，延迟高于 CU 本地 barrier，同步密集型 kernel 收益可能被侵蚀；
- scoreboard 条目数量必然有限，可并发跟踪的 split workgroup 数受限（文本未给出具体深度）；
- workgroup 被拆到多个 CU 后，其 LDS 不再天然共享——文本以 kernel 227B（GDS/atomic）侧面印证这一点，跨 CU 共享数据需走更慢的全局路径；
- load-rating 依赖采样间隔与加权设置，反馈存在滞后；文本未给出量化收益数据，提取文本中还有若干标号笔误（如 command processor 240/235、program/performance counters），均以正文语义为准。

**对理解现代 GPU 分发硬件的启示**：本专利把 AMD 分发层的设计哲学讲得很清楚——分发决策不是"能不能"而是"怎么更划算"：可用性检测（fits detection）、负载评级（load-rating）、拆分策略（fit policy）、同步机制（scoreboard vs GDS/atomic）四个维度全部可编程/可反馈。与 NVIDIA 对照阅读可见两条路线：AMD 放宽"workgroup 必须驻留单 CU"的约束（向下拆），NVIDIA 放宽"CTA 间无法跨 SM 协作"的约束（向上簇）。两者共同指向同一趋势：在保持同步语义的前提下，让前端分发硬件在 CU/SM 粒度之上做更细粒度的资源拼装。
