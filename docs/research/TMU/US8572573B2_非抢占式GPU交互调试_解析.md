## 2. 发明背景与待解决问题

- 传统调试工具分软件调试与硬件调试两类。软件调试技术之一：修改程序将变量值写到备用位置或替换正常输出，再重跑收集结果。
- 该技术的缺陷（原文列举）：无法实时分析；非确定性程序重跑结果不一致；仅持有源码的可信方可调试；重跑需大量内存传输以复位状态变量，引入延迟与不一致；修改程序可能掩盖特定时序引发的错误或改变编译器指令顺序，导致完全不同的结果；无法分析未修改程序的处理瓶颈。
- 软件模拟器的缺陷：难以调试异步执行引发的瞬态错误；模拟器自身 bug 或性能/精度权衡使其行为偏离目标硬件，反而混淆调试。
- 硬件调试手段：hardware breakpoint（在特定指令处停程序等待 resume）；JTAG（Joint Test Action Group）调试端口访问片内调试模块。传统上须经软件模拟器或远程调试实现，因在同一平台暂停源程序会连带暂停调试器赖以运行的关键硬件——例如 CPU 上的断点会使操作系统停摆，无法查看 CPU 状态或用软件工具改内存。
- GPU 特有困境：PPU 202 为 non-preemptible（非抢占式），workload 启动后必须完成或被 flush 才能切换上下文；调试中 shader programs 412 触发 hardware trap（breakpoint/exception）会使 PPU 202 停止执行来自 application program 410、operating system 422 及其他应用 424 的一切操作，PP memory 204 中帧缓冲不再更新，"killing screen refresh"——程序员既无法在 display device 110 上查看中间数据，也无法经调试器 GUI 发出 resume 命令。
- 传统解法：双 PPU——第一块 PPU 202(0) 维持显示更新，第二块 PPU 202(1) 作调试目标，可经 communication path 113 共总线、第二条类似路径、或经 network adapter 118 远程接入。缺点：每个调试平台至少需两块 CPU/GPU，成本高；两套图形平台间管理多通道图形命令复杂。
- 待解决问题（原文归纳）："what is needed in the art is a system and method that allows for interactive debugging of a target GPU while also allowing the target GPU to continue normal screen drawing operations received from the operating system."
- 明示优点：单 GPU 同时用于硬件调试与屏幕更新；可调试非确定性应用；可调试无源码的程序。

## 3. 核心方案

### 3.1 整体架构（硬件单元与附图标记）

- FIG. 1 计算机系统 100：CPU 102、system memory 104、memory bridge 105（Northbridge）、通信路径 106（如 HyperTransport）、I/O bridge 107（Southbridge）、输入设备 108、显示设备 110、系统盘 114、switch 116、network adapter 118、add-in cards 120/121；parallel processing subsystem 112 经第二通信路径 113（PCIe、AGP 或 HyperTransport）耦合；device driver 103 实现图形 API（OpenGL、DirectX）。
- FIG. 2 parallel processing subsystem 112：一个或多个 PPU 202（U≥1，各配本地 PP memory 204）；PPU 202 内含 I/O unit 205、host interface 206、task/work unit 207、front end 212、processing cluster array 230（C≥1 个 GPC 208(0)–208(C-1)）、crossbar unit 210、memory interface 214（D≥1 个 partition unit 215，各直连一块 DRAM 220）。
- FIG. 2 命令流路径：CPU 102 将命令流写入 system memory 104 / PP memory 204 中的数据结构，以 pushbuffer 指针启动处理；PPU 202 异步读取 pushbuffer 执行，应用可经 device driver 103 为每个 pushbuffer 指定执行优先级；host interface 206 读取 pushbuffer 并把命令流输出至 front end 212。
- FIG. 2 任务路径：GPC 208 从 task/work unit 207 内的 work distribution unit 接收处理任务；任务编码为 task metadata（TMD）存于内存，pushbuffer 命令流携带指向 TMD 的指针；TMD 含待处理数据索引、状态参数与命令（含执行何种程序），可带调度优先级及控制插入队头/队尾的参数。
- FIG. 3A task/work unit 207 = task management unit 300 + work distribution unit 340（scheduler table 321、TMDs 322、task table 345；详见第 5 节）。
- FIG. 3B GPC 208：pipeline manager 305 向 M≥1 个 streaming multiprocessor（SM）310 分发任务并控制 work distribution crossbar 330 的输出目的地；texture unit 315、L1.5 cache 335（经 memory interface 214 取指令/uniform/constant 数据）、preROP 325、MMU 328（虚地址→物理地址）；SM 310 输出经 work distribution crossbar 330 到其他 GPC 208、L2 缓存、PP memory 204 或 system memory 104（经 crossbar unit 210）。
- FIG. 3C SM 310：instruction L1 cache 370、warp scheduler and instruction unit 312、local register file 304、N 个 exec units 302、P 个 LSU 303、unified address mapping unit 352、shared memory 306、L1 cache 320、uniform L1 cache 375、memory and cache interconnect 380；线程组织为 warp/thread group（k 线程）与 CTA/thread array（大小 m×k）。
- FIG. 4 调试系统：system memory 104 中的 application program 410（含 shader programs 412）、debugger 450、operating system 422、other applications 424；debugger 450 经 device driver 103 的 API 与单一 PPU 202 通信，亦可实现于 device driver 103 内部并外挂 GUI；PPU 202 硬件调试能力：运行期向 device driver 103 发送 hardware trap（breakpoint、exception、assertion 等）通知，允许 debugger 450 将 PP memory 204 部分内容 flush 到 system memory 104、允许 device driver 103 写 PPU 202 寄存器；PPU 202 同时渲染调试环境 GUI 到 display device 110。
- FIG. 5 调试器数据结构：三个线程清单——list 512 "logically complete"、list 514 "in-progress"、list 516 "not yet launched"（示例：Thread ID 0/1/4 完成、2/3 在途、6/7/8 未启动、一槽 empty）。
- FIG. 6 方法 600 流程图：步骤 610→612→614→616（Hardware Trap?）→626（End?）→618→620→622（Resume Execution?）→624→回到 616。

### 3.2 关键机制详解

1. 拦截与登记（步骤 610/612）：debugger 450 接收待调试的 application program 410 与 shader programs 412（C++/C# 应用 + Cg/GLSL shader；shader 为可在各 SM 310 上运行的二进制可执行体）；拦截应用发往 PPU 202 的 workload 命令并生成线程清单。图形 workload 由 Draw call 创建，compute workload 由 Kernel launch 创建；应用可在 PP memory 204 生成 TMDs 322 并发出指定 TMDs 322 的 Kernel launch。初始时全部待启动线程 ID 入 list 516，512/514 置空。替代跟踪方案：单清单+状态标记；或两个数组（in-progress / logically complete），不在任一数组即视为未启动。debugger 450 还可自行发射新 workload、flush 已发射 workload，以保证其他应用的 workload 得到处理。
2. 发射与停止事件（614/616）：workload 交 device driver 103 执行，debugger 450 进入 re-launch loop。workload 关联的 TMD 322 可含三维 grid 指针（示例：X=10、Y=10、Z=5，共 500 个 CTA）。任一线程触发 hardware trap（breakpoint、hardware exception、failed software assertion、illegal instruction）即 halt 所有 SM 310 上线程；PPU 202 经 device driver 103 通知 debugger 450，或由 debugger 450 轮询 driver/PPU。无 trap 则检查 workload 是否结束（626），结束则方法终止。
3. 状态保存与杀线程（618/620）：debugger 450 保存 list 514 中所有 in-progress 线程的状态——从 PPU 202 复制寄存器值、special registers，将 per-thread local memory 与 shared memory 从 PP memory 204 拷贝至 system memory 104；随后修改 PPU 202 全局状态（例如设置一个 special register），使恢复执行时杀死任何活动线程与新建线程（含依赖的 child threads）；resume 后当前 workload 全部线程被杀，PPU 202 腾出处理 OS 422/其他应用 424 的图形命令以更新 display device 110。
4. GUI 检查与恢复（622/624）：PPU 202 恢复正常后刷新 debugger 450 GUI，程序员检查保存的处理状态/变量数据、设置新断点并发出 resume 或 step 命令；debugger 450 重新发射原 workload，从上次 trap 点恢复执行直至下一个 stop event。原文概括："a debugger saves processor state and memory to enable the parallel processing unit to switch contexts even though the hardware does not support context switching while execution of a workload is stalled due to a hardware trap."
5. thread-entry routine：debugger 450 令每个线程在执行真实指令前先运行入口例程，依清单判定：线程 ID 在 list 512（已完成）→ 杀死该线程、SM 310 改跑其他线程（其输出已并入所存帧缓冲/处理器状态，无需重跑）；在 list 514（in-progress）→ 恢复线程状态、从上次被杀点续跑；仅在 list 516（未启动）→ 从 shader 首指令启动。
6. re-launch loop 的单步语义：已完成线程重发射时被终止，在途线程恢复至 halt 点，"in actuality, each step of the program is accomplished by re-issuing the original workload on the PPU 202 and halting execution at different points in the process based on where breakpoints are encountered"。
7. CTA grid 起始索引优化：PPU 202 可支持 debugger 450 为 CTA grid 各维指定 start index——若前 4 个 X 向 CTA 已在上一遍执行完，可令本遍从第 5 个 CTA 开始。
8. 不可恢复资源的处理：部分 special registers 只读（如硬件 thread ID），且 PPU 202 不允许指定线程落在哪个 SM 310；重放时线程若换到不同 SM 310，依赖这些寄存器的 shader 会算错中间地址/数据。解法一：用 PP memory 204 中 thread-local memory 虚拟化这些资源并改写线程指令改用虚拟位置；解法二：限制并行度使线程只在单一 SM 310 执行（缺点是 CTA 串行化，掩盖 race condition 等并行同步错误）。
9. 超时保护：PPU 202 可设 timeout limit，workload 超时被自动中断（视为一遍结束），防 shader bug 挂死。传统调试须禁用超时保护（硬件 halt 期间 OS 仍视 workload 为活动，断点检查时间计入超时）；本方案可保持超时开启（可适当调大以容纳 trap、状态保存与 resume 前的 CPU 延迟），用户可无限时长检查状态。
10. 仅恢复 in-progress 线程的变体：后续 pass 杀死一切 "logically complete" 或 "not yet launched" 状态的线程，防止未启动线程抢先运行、把下一次 trap 引到无关代码段而转移程序员注意力，并使 in-progress 清单不致无界增长；代价：当 in-progress 线程等待某个 not-yet-launched 线程时可能死锁。
11. 直接调试模式：debugger 450 亦可不经 CPU 102 运行 application program 410，而是直接向 device driver 103 发 API 调用把 shader program 412 装载到 PPU 202，并创建预定义 test workload 提供已知输入评估输出。
12. 时间尺度论证：workload 通常是一个 draw call（帧率约 30fps 时执行 <30ms）或物理计算等 compute workload，故即便调试期间短暂阻塞屏幕更新，PPU 202 也能很快完成或被中断、保存状态、杀线程后重新可用。

- 独立权利要求 9：non-transitory computer-readable storage medium 存储的 debugger，执行与权 1 相同步骤（介质镜像）。
- 独立权利要求 16：系统——system memory 含 debugger 与带 shader programs 的应用、耦合的 CPU、渲染调试 GUI 的 parallel processing unit、耦合的 graphics memory；debugger 经 CPU 执行权 1 步骤（系统镜像）。
- 从属权利要求分组：
  - 权 2：trap 触发源 = breakpoint、hardware exception、failed software assertion 至少其一。
  - 权 3/10/17：re-launch loop 细化——保存第一点各执行线程状态至 system memory；终止所有执行线程使 PPU 可处理更新显示设备的新 workload；后续 pass 恢复在途线程状态并自第一 pass 中断的指令处续跑。
  - 权 4/11：另保存 per-thread local memory（恢复回 parallel processing memory）、per-thread registers、shared memory（后续 pass 恢复）。
  - 权 5/12/18：跟踪各 pass 中每个被启动线程的状态。
  - 权 6/13/19：线程状态三态指示 = not yet launched / being executed / logically completed。
  - 权 7/14/20：线程启动时执行 thread-entry routine——已完成则终止；在途则恢复状态与 local memory 并自 shader 中途指令续跑；未启动则自首指令执行。
  - 权 8/15：后续 pass 禁止 not-yet-launched 线程启动，仅第一点处在执行的线程可继续。

## 5. 与 TMU（Task Management Unit）的关系

本专利与 TMU 专利族共享同一套 Kepler 风格 PPU 架构说明书文本，FIG. 3A 及 "Multiple Concurrent Task Scheduling"、"Task Processing Overview" 诸节完整披露了任务调度前端：

- 任务前端链路：host interface 206 → front end 212 → task/work unit 207 → GPCs 208。原文："GPCs 208 receive processing tasks to be executed from a work distribution unit within a task/work unit 207. The work distribution unit receives pointers to processing tasks that are encoded as task metadata (TMD) and stored in memory."
- task/work unit 207 职责："receives tasks from the front end 212 and ensures that GPCs 208 are configured to a valid state before the processing specified by each one of the TMDS is initiated."
- task management unit 300（FIG. 3A）："organizes tasks to be scheduled based on execution priority levels. For each priority level, the task management unit 300 stores a list of pointers to the TMDS 322 corresponding to the tasks in the scheduler table 321, where the list may be implemented as a linked list." TMDs 322 存于 PP memory 204 或 system memory 104；接收速率与调度速率解耦，可先积攒若干任务再按优先级或 round-robin 调度。
- TMU 300 细化（正文列 12–13）：以 scheduler table 321 中的 "TMD groups" 数组管理任务，每组同优先级（组数≥1）；组内链表每项存指向 TMD 322 的 task pointer 与下一项指针，另存 head/tail pointer，空组 head=tail 且 empty bit 置 TRUE；来自 host interface 206 的任务默认插入链表尾部，special TMD bit 可令其插入头部；同组内链表头部任务优先调度，位置越靠后优先级越低，故 TMU 300 可按输入顺序调度（未特标者）；TMD group 属 TMD 结构的一部分，执行期间不可更改。
- 缓冲与调度策略：先缓冲后选择使 TMU 300 可比来序更优地调度（如让后到的高优先级任务先出）；调度技术可选 round-robin、priority、partitioned priority；被选中的任务从所在 TMD group 移除；快速选取靠直接取对应组链表首项；重排只需改链表指针顺序，故调度/执行顺序可不同于 host interface 206 的接收顺序。
- work distribution unit 340：task table 345 槽位由正在执行的 TMD 322 占据；有空槽即调度；无空槽时不占槽的高优先级任务可 evict 占槽的低优先级任务——"When a task is evicted, the task is stopped, and if execution of the task is not complete, then a pointer to the task is added to a list of task pointers to be scheduled so that execution of the task will resume at a later time." 这是该架构中唯一的硬件级"停止-后恢复"任务机制。
- child task：任务亦可来自 processing cluster array 230；child task 由执行中的 TMD 322 动态产生，直接回 task/work unit 207 调度，不插入 pushbuffer、不经 front end、CPU 不被通知；pushbuffer 任务由应用定义，child task 运行时生成，支持嵌套并行（queue TMD、circular queue 存子任务数据）。
- front end 212 与调试的衔接点："Special registers are written during initialization in response to commands received via front end 212 from device driver 103 and do not change during execution of a processing task. The front end 212 schedules each processing task for execution."
- 调试与 TMU 的配合（依正文事实）：debugger 450 工作在 API/driver 层、位于 front end 212 之前——"debugger 450 is configured to intercept the creation of workloads by CPU 102, generate lists to track the threads launched to process the workloads, issue new workloads generated by the debugger 450, and flush workloads transmitted to PPU 202 to ensure that the additional workloads submitted by other applications will be processed."
- 即调试不修改 TMU 300 / work distribution unit 340 的调度逻辑：每次 re-launch 对 task/work unit 207 而言是一次全新任务提交；杀线程通过 device driver 103 写 PPU 202 寄存器/设置 special register 实现。正文未描述 TMU 300 直接参与 hardware trap 处理（trap 通知路径为 PPU 202 → device driver 103 → debugger 450）；work distribution unit 340 的 evict-重排机制与调试的"停止后重放"在任务状态管理思想上同构，但文中未将两者直接关联（此为分析性推断）。

## 7. 评价与启示

- 时代定位：申请于 2012-03-09、授权于 2013-10-29，正值 Kepler 世代——FIG. 2/3 即 Kepler PPU 架构描述（task/work unit 207、task management unit 300、work distribution unit 340、TMD 322 与 Kepler 公开架构一致）。彼时 GPU 无硬件抢占、无 workload 中途上下文切换，本专利用"拦截-保存-杀线程-重放"的 re-launch loop 在软件层模拟出抢占式单步调试语义，是"以软件状态机弥补硬件非抢占缺陷"的典型过渡方案。
- 工程价值（均为摘要/正文明示）：单 GPU 同时承担调试目标与显示输出，取消双机/双卡调试平台，使"几乎任何带显卡的计算机都能做硬件调试"；可调试非确定性应用；可调试无源码的 shader 二进制；无需关闭 OS 超时看门狗，断点驻留时间不受限。
- 架构启示：调试状态保存的最小集合 = special registers + per-thread local memory + shared memory；线程生命周期被抽象为三态机（not yet launched / in-progress / logically complete），配合 thread-entry routine 实现幂等重放——该模型与后来 CUDA 调试器（如 cuda-gdb 的 kernel replay 思路）一脉相承；CTA grid start index 可视为按 grid 维度的增量恢复；超时保护可保持开启是相对传统调试的实质改进。
- 与 TMU 演进的关系：本专利将 TMU 300 / work distribution unit 340 作为标准说明书模板嵌入调试主题专利，说明 NVIDIA 视其为 PPU 的标志性前端结构；work distribution unit 340 的 evict-重排队列（task table 345 槽位回收、被逐任务 stop 后重新入队恢复）为后续世代引入硬件抢占/上下文切换提供了设计先例；调试的"trap 后保存-恢复-重放"与抢占调度的"evict 后 stop-重排"共享"任务状态可中止、可恢复"的设计哲学。此为基于文本的分析性评价，非原文直接陈述。
- 局限（原文自述）：只读 special registers 不可恢复，需虚拟化或限制并行度（后者掩盖 race condition）；仅恢复 in-progress 线程的变体可能死锁；每遍重放整个 workload 带来额外开销（正文以 workload 通常 <30ms、帧率约 30fps 论证可接受）。
