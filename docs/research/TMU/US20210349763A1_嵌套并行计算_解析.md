## 2. 发明背景与待解决问题

- 传统 GPU 执行模型中，**只有 CPU 可以发起** GPU 上线程程序的执行；GPU 完成所有线程实例后必须通知 CPU 并等待下一个任务，这是一种阻塞式、串行化的操作，会使 GPU 内部资源暂时闲置，降低系统整体性能（[0003]）。
- pushbuffer 模式可将顺序计算任务排队，让 GPU 不必等待 CPU；但这只对**固定数据流（fixed data-flow）**流水线有效。对于**数据依赖（data-dependent）**的计算任务，GPU 结果 → CPU 任务管理 → 后续 GPU 任务执行之间仍存在顺序依赖，后续任务必须由 CPU 发起（[0004]）。
- 数据依赖型任务天然包含**条件执行（conditional execution）**，而条件执行决定了哪些后续任务需要运行——这又必须把结果传回 CPU 才能决定并发射新任务。涉及并行库函数复杂条件执行的算法无法完全由 GPU 完成，CPU 必须介入每一个流控决策点（[0004]）。
- 条件执行在已知算法中占比极大，传统 GPU 执行模型在此存在"根本且长期存在的局限"（[0005]-[0006]）。
- 本案要解决的问题：提供一种增强 GPU 计算通用性与性能的技术，使 GPU 能够自主完成嵌套/条件并行的任务发射与同步，摆脱 CPU 介入。

### 3.2 关键机制详解

**（1）嵌套并行的表达——child launch construct。** CUDA 语言规范扩展出子启动构造 "A<<<B>>>C"：A 为子程序（kernel）名，B 为 grid 启动参数，C 为输入参数（[0071]）。Table 1 示例：父线程程序 `foo()` 中 `malloc` 分配内存后执行 `A<<<1,1>>>(ptr)`，再调用 `cudaThreadSynchronize()` 同步屏障，随后 `do_stuff(ptr)`。

**（2）三类必备系统要素**（[0069]-[0070]）：硬件功能——从 SM 310 产生的请求排队到 task/work unit 207 并启动新的 grid/CTA、保存/恢复 SM 执行状态、维护父子任务间内存一致性；运行时功能——响应 SM 内线程请求启动新 grid、允许父线程对子 grid 执行同步屏障、保证前向计算进展的调度、保证父子执行语义；语言构造——子启动与同步屏障机制。

**（3）执行时序（FIG. 6，事件序列 600，[0075]-[0081]）：**
1. device driver 103 在 SM 310 内初始化 CTA（如 `foo()`），线程开始执行；
2. 线程执行 child launch（`A<<<1,1>>>(ptr)`），成为父线程；
3. 调用 `cudaThreadSynchronize()` 阻塞父线程——父 CTA 的执行状态被保存到 **continuation state buffer**（可位于 PP memory 204 / system memory 104），CTA 退出，SM 310 被释放、资源去分配，可承接其他任务——以此**避免死锁**并保证前向进展；
4. 内存一致性：子 grid 启动前执行系统内存屏障（membar.sys），把父线程所有挂起写数据刷入内存，使子 grid 中任意线程可在任意 SM 310 上安全读取父内存空间；
5. 子启动本身经 `cudaRTLaunch()` 排队新任务：向 MMU 328 发出 **posted compare and swap (PCAS)** 消息，MMU 把消息反射给 scheduler；PCAS 是 MMU 328 执行的阻塞式（posted）同步操作，原子比较并在匹配时覆写指定内存位置；
6. 子 grid 完成时，scheduler kernel 作为 **"AtExit"** 任务被调用，发现已完成/未完成的工作并决定下一步调度（重新发射父 CTA）；
7. **continuation process**：restoration kernel 作为 **"AtEntry"** 任务执行，从 continuation state buffer 恢复执行状态，失效（invalidate）SM 310 相关 cache 以避免陈旧数据，然后跳转到 `cudaThreadSynchronize()` 调用之后的指令继续执行。

**（4）独立发射与可组合性。** 每个线程独立执行：无条件发射时所有实例都会发射子 grid（Table 2：100 个 foo 线程 → 100 个 bar）；条件发射（Table 3：仅 threadIdx.x==0 的线程发射）；父 CTA 内可创建被所有线程共享的 CUDA stream（Table 4，[0082]-[0084]）。层级**可组合（composable）**：外部只看见父 kernel，父及其全部子 kernel 都完成，父才算完成（[0085]）。

**（5）典型应用。** 把外部库函数实现为子 kernel 调用；把应用级控制循环搬到 GPU 上执行，支持数据依赖算法、递归算法、多层嵌套条件循环（Table 5 传统写法 vs Table 6/7 用 `cuda_inner_loop`、`cnp_loop_i/j` 逐级条件发射子 grid 的写法，[0086]-[0089]）。

**（6）方法流程图（FIG. 8，method 800，[0095]-[0098]）：**
- 810：发射父 CTA（来自 CPU 的应用工作或来自上一级父任务）；
- 820：接收父 CTA 的子 grid 发射请求；822：将请求以 GTMD 形式排入 GTMD queue（752）；824：scheduler 710 取出 GTMD，distributor 720 把工作分配到 SM 730，加载可执行代码并启动；
- 830：接收父 CTA 的线程同步屏障请求（cudaThreadSynchronize）；832：父 CTA 执行状态存入 continuation state buffer 742（可由硬件单元或父 CTA 内的 continuation state function 完成）；834：父 CTA 退出、释放 SM 资源，可选执行 memory barrier 刷写保证子 grid 看到一致的内存视图；
- 840：接收子 grid 完成通知；842：scheduler kernel 将父 CTA 的 GTMD 条目重新加入 GTMD queue 752；844：restoration kernel 恢复执行状态并失效相关 cache；846：从屏障调用之后的下一条指令继续执行；890：结束。

**（7）队列结构（FIG. 7，[0091]-[0093]）：** 嵌套工作进入独立的 GTMD queue 752，与来自 CPU 的应用工作 GTMD queue 750 分离，scheduler 710 可据此区分并分别授予优先级以保证前向进展；scheduler kernel 排入 QTMD 754（Kernel7…KernelP），restoration kernel 可排入 QTMD 754 或独立的 QTMD 756（KernelQ）以获得更大调度灵活性。

## 4. 权利要求摘要

共 **20 项**权利要求，其中 **2 项独立权利要求**（claim 1 存储介质类、claim 11 处理器类），其余为从属。

- **Claim 1（独立，computer-readable storage medium）**：存储的指令使一个或多个处理器至少执行：在第一 multiprocessor 中执行父线程；在第二 multiprocessor 中发射子线程；响应于同步函数调用（synchronization function call），在等待子线程完成期间阻塞父线程的执行。
- **Claim 11（独立，processor）**：处理器包括 plurality of cores、register file、L1 cache、crossbar unit、instruction cache、scheduler；处理器执行指令以实现与 claim 1 相同的"父线程执行 / 子线程发射 / 同步阻塞"操作。
- **从属权利要求分组**（claim 2-10 与 claim 12-20 两组基本镜像）：
  - 处理器为 GPU：claims 2、7、8、12、17、18；第一/第二 multiprocessor 位于同一 PPU：claims 10、20；
  - 子线程完成后恢复父线程执行：claims 3、6、13、16；
  - 响应同步调用保存父线程执行状态：claims 4、7、14、17；
  - 保证父子线程间内存一致性（memory coherence）：claims 5、15；
  - 接收子线程完成通知并据此恢复父线程：claims 6、7、16、17；
  - 从同步函数调用之后的指令继续执行：claims 9、19。

## 5. 与 TMU（Task Management Unit）的关系

本案正文**直接命名并详述** task/work unit、task management unit、work distribution unit 与 front end，是 TMU 专利族的核心文献之一：

- **task/work unit 207**（FIG. 2）：GPC 208 的处理任务由其中的 work distribution unit 分发；任务被编码为 **task metadata (TMD)** 存于内存，TMD 指针随命令流经 **front end 212** 从 host interface 206 到达。task/work unit 207 从 front end 212 接收任务，并在按 TMD 启动处理前确保 GPC 208 处于有效状态；每个 TMD 可带优先级，还可用参数控制 TMD 插到任务链表头部还是尾部。**关键扩展**：处理任务也可以来自 processing cluster array 230（即运行中任务生成的子任务）（[0030]）。
- **task management unit 300**（FIG. 3A）：按优先级在 scheduler table 321 中维护指向 TMD 322 的链表；接收与调度速率解耦（[0037]）。
- **work distribution unit 340**：task table 345 槽位管理、高优先级驱逐低优先级、被停任务重新入队（[0038]）。
- **TMU 对嵌套并行的专门支持（[0038]-[0039]，重点引述）**：
  - "When a child processing task is generated, during execution of a task, a pointer to the child task is added to the list of task pointers eligible to be ... scheduled immediately by the Task Management Unit." 子任务可由正在 processing cluster array 230 中执行的 TMD 322 生成。
  - 一个实施例中，停在同步屏障的任务被放入**第一任务指针链表**，而作为子任务创建的任务被放入与之不同的**第二任务指针链表**；第二链表中的子任务可以**立即执行且优先级高于**第一链表中的任务——即"子优先于父"的调度策略，用于防止父等子、子等资源的死锁。
  - "Unlike a task that is received by the task/work unit 207 from the front end 212, child tasks are received from the processing cluster array 230. Child tasks are not inserted into pushbuffers or transmitted to the front end. The CPU 102 is not notified..."——子任务完全绕过 pushbuffer/front end/CPU 通路，这正是"device-side launch"的硬件通路定义。
- 其余职责呼应：硬件须支持"从 SM 310 产生并入队到 task/work unit 207 的请求启动新 grid/CTA"（[0070]）；子 grid 完成时"调度器（如 FIG. 2 的 task/work unit 207）被通知"并重新调度父 CTA（[0077]）；FIG. 7 中 scheduler 710 明确对应 task management unit 300、distributor 720 对应 work distribution unit 340（[0090]）。

## 7. 评价与启示（与 CUDA Dynamic Parallelism 的关联）

- **时间线吻合**：本案原始申请日 2012-05-02，与 NVIDIA 在 Kepler（2012）/ CUDA 5.0 时代推出 **CUDA Dynamic Parallelism（CDP，设备端 kernel 发射）** 的时间点一致。文中 "A<<<B>>>C" 子启动构造、`cudaThreadSynchronize()` 对子 grid 的屏障语义，正是 CDP 编程模型的硬件基础；该专利可视为 CDP 的底层实现专利。
- **硬件机制要点**： continuation state buffer（挂起父 CTA 的完整架构状态保存/恢复）、membar.sys 父子内存一致性、经 MMU 的 PCAS（posted compare-and-swap）消息向 scheduler 投递任务、AtExit scheduler kernel / AtEntry restoration kernel、分离的 GTMD/QTMD 队列——构成一套 GPU 内部的"任务上下文切换 + 设备端任务发射"机制，全部在 GPU 内闭环，无需 CPU 参与。
- **对 TMU 演进的意义**：task/work unit 207（task management unit 300 + work distribution unit 340）在此案中从"消费 pushbuffer 的图形前端调度器"扩展为"可接收 SM 运行期生成的子任务、支持双优先级链表、子任务即时优先调度"的通用任务管理器，是理解 NVIDIA GPU 任务管理前端从 Fermi/Kepler 时代演进（后续如 hyperqueue、GigaThread 等）的关键节点文献。
- **规避死锁的设计启示**：父线程在屏障处不占 SM 原地等待，而是"保存状态—释放资源—子任务高优先级即时调度—完成后经 restoration kernel 恢复"，这是 GPU 有限资源下实现任意嵌套深度（受 scheduling group 数量限制）的根本手段（[0069]、[0076]、[0099]）。
- **延续策略**：2012 年原始申请经四次 continuation 延续至 2021 年，权利要求从具体系统/方法改写为更抽象的"存储介质 + 处理器"形式（第一/第二 multiprocessor、同步函数调用、阻塞/恢复），扩大了保护面，便于对后续世代（含竞品 GPU 的设备端发射实现）主张权利。
- **局限**：说明书细节基于 Fermi/Kepler 代架构（GPC/SM 310、L1.5 cache 335 等），对现代架构的具体映射（如子 grid 深度限制、流/事件语义的演化）需结合后续专利与 CUDA 文档对照；文本中附图页 OCR 大量乱码，附图标记以正文描述为准。
- **权利要求抽象度提示**：独立权利要求仅覆盖"父线程在第一 multiprocessor 执行、子线程在第二 multiprocessor 发射、同步函数调用阻塞父线程"这一最小语义，未限定 continuation state buffer、PCAS、GTMD 队列等实现细节；说明书中的这些机制属于可选实施例，分析侵权或规避设计时应注意权利要求与实施例的落差。
