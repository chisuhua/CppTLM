## 2. 发明背景与待解决问题

**两类赖的区分（[0002]–[0004]）**：任务图中相邻任务之间存在两种性质不同的依赖。其一是 **scheduling dependency（调度依赖）**：规定第二任务（消费者）不得早于第一任务（生产者）启动的顺序约束，本质是"启动次序"问题；其二是 **data dependency（数据依赖）**：消费者读取的数据必须由生产者写入并对所有 SM 可见（通常需要 memory flush）才能访问，本质是"数据可见性"问题。

**待解决问题**：传统做法把两类依赖捆绑处理——消费者必须等待生产者**完整执行完毕并完成内存刷新**之后才开始启动流程，而启动本身还要串行经历任务描述符取回、指令取回、常量取回等步骤。于是生产者完成到消费者真正开始执行之间出现可观的启动延迟（launch latency），GPU 前端在此期间空转。对深度学习等由大量短任务构成的工作负载，该延迟占整体执行时间的比例很高。

**软件栈背景（[0038]）**：文本提到 CUDA graph 类 API 已允许应用同时指定这两种依赖，说明本专利面向的是 CUDA Graphs 时代的任务图执行场景，硬件需要提供与 API 语义匹配的低开销执行机制。

## 3. 核心方案

### 3.1 整体架构（FIG. 1–2）

- FIG. 2：PPU 内部框图，本专利的任务调度前端结构；
- FIG. 3：生产者/消费者两任务的执行时序图，标出关键路径 304 与可并行活动 306；
- FIG. 4：方法 400 流程图（步骤 402–424）。

**FIG. 2 数据流**：Host Interface Unit 210 接收来自主机的任务命令，经 Front End Unit 220 送入 **Work Scheduler/Distribution Unit 230（WSDU，工作调度/分发单元）**；WSDU 230 内部含 **Scheduling Dependency Logic 232（调度依赖逻辑）** 与 **Task Dependency Table 240（任务依赖表）**，是本专利全部新机制的执行主体；任务经 Intermediate Units/Crossbars 250（含多个 MPC，见 [0056]）分发到 SM 260(0)–260(N-1) 执行；SM 经 Memory Crossbar 280、Memory Interface 290 访问 PP Memory 140。

**值得注意的两点**：

1. 在更早的专利中，Task Management Unit 与 Work Distribution Unit 是分立单元（TMU 234 / WDU 236，或 TMU 300 + WDU 340）；本专利中二者合为单一 WSDU 230，代表新一代前端形态（见第 5 节）。
2. **[0050]**：WSDU 230 不仅接收主机侧任务命令，还接收**正在 SM 上执行的生产者任务所发出的消费者任务命令**——即设备端（device-side）直接向调度前端提交后续任务，这与嵌套并行（CDP）专利中的设备端提交路径一脉相承。

**任务描述符（[0045]）**：任务描述符可同时携带调度依赖信息与数据依赖信息，并记录关联的生产者/消费者数量，作为 WSDU 建立依赖跟踪条目的依据。

### 3.2 调度依赖与数据依赖解耦：pre-exit 触发

**核心思想（[0065]–[0070]）**：Scheduling Dependency Logic 232 把调度依赖从数据依赖中**解耦**出来分别处理。调度依赖不必生产者执行完毕，而是在检测到 **pre-exit trigger（提前退出触发）** 时即告解除；解除后 WSDU 立刻开始启动消费者任务（取描述符、分发线程块），使消费者的启动流程与生产者的剩余执行时间重叠。数据依赖则仍按数据可见性要求单独跟踪与解除（见 3.4）。

文本给出默认 pre-exit 判据（如生产者全部线程块均已启动/到达指定点），并允许任务描述符或软件指定**覆盖判据**（override），即提前退出的时机可按任务调优。

**PREEXIT 指令 330（[0071]–[0073]）**：pre-exit 触发的一种实现是在生产者任务程序中插入 **PREEXIT 指令 330**。其特征：

- 可指定解除对象为**特定消费者**或**全部消费者**；
- 由 API/runtime/驱动（必要时连同编译器）在程序中插入，位置可调——放得越早消费者启动越早，但必须位于生产者仍须保证启动次序的代码点之后；
- 执行该指令后，生产者线程继续执行其余代码，不阻塞。

### 3.3 Task Dependency Table 240 与依赖锁存器（FIG. 2）

**Task Dependency Table 240（[0075]–[0079]）**：位于 WSDU 内的**片上 RAM** 结构，每行对应一个**活跃**任务，行数有限（不跟踪未激活任务，以此控制硬件开销）。表的关键列是 **Wait On Latch** 与 **Arrive At Latch**：每对生产者/消费者依赖被实例化为一个**依赖锁存器**（文中示例记作 DL001），消费者行在 Wait On Latch 列登记要等待的锁存器，生产者行在 Arrive At Latch 列登记到达时要置位的锁存器。调度依赖解除（pre-exit）与数据依赖解除（flush 完成）分别通过锁存器的置位路径通知 WSDU，后者据此推进消费者的启动与继续执行。

**启动次序保证（ordering guarantee）**：硬件保证**生产者的最后一个线程块先于消费者的第一个线程块被启动（launch）**。这一保证使消费者可以在生产者执行末期就被分发，而不会破坏任务间语义顺序——它是"提前启动"安全性的基石，也对应公开 API 的语义（见第 6 节）。

### 3.4 ACQBULK 与消费者任务的三段结构（FIG. 3）

**bulk release/acquire（[0074]）**：依赖的解除采用"批量释放—批量获取"语义。生产者一侧批量释放（release）其对各消费者的数据依赖；消费者一侧用 **ACQBULK 指令 390** 批量获取（acquire）所等待的全部数据依赖。

**消费者任务的三段结构（[0080]–[0081]）**：

1. **数据无关部分 372**：不依赖生产者输出的指令，消费者线程块被启动后立即执行（与生产者剩余执行、memory flush 重叠）；
2. **ACQBULK 390**：同步点。线程在此等待，直到所等待的数据依赖全部满足（生产者输出对所有 SM 可见）；
3. **数据依赖部分 374**：读取生产者数据继续执行。

这样，消费者的"启动开销"（描述符取回、线程块分发、指令/常量就位）被折叠进生产者的执行尾部，而真正的数据等待被压缩到 ACQBULK 一点。

### 3.5 抢先式内存刷新与预取

**Preemptive Memory Flush 320（[0082]–[0084]）**：WSDU 在**启动生产者的最后一个线程块时**即向各 SM 广播 flush 请求 320，使内存刷新尽早开始，而不是等全部线程执行完毕才发起；理想情况下当消费者走到 ACQBULK 时 flush 已经完成或接近完成，数据依赖等待时间被 flush 的提前量掩盖。

**预取功能 352/354（[0085]–[0088]）**：WSDU 对消费者任务发起**指令预取 352** 与**常量预取 354**（写入 L1.5 层级缓存），可自动启用或按任务描述符逐任务指定。这与 US11182207B2 的指令/常量预取思想一致，但触发时机挂接在解耦后的新流程上。

### 3.6 关键路径分析（FIG. 3）与方法 400（FIG. 4）

**FIG. 3（[0090]–[0107]）**：时序图对比关键路径 304 与可并行活动 306。传统流程中"生产者完成 → flush → 消费者描述符/指令/常量取回 → 消费者启动"全部落在关键路径上；本方案中：消费者描述符取回、指令/常量预取 352/354、消费者线程块启动都移到生产者执行期间并行完成，生产者的 PREEXIT 330 一出现即触发消费者启动，flush 320 提前广播；关键路径上只剩下无法重叠的残余部分，从而显著缩短生产者完成到消费者执行之间的间隔。

**FIG. 4 方法 400（[0108]–[0116]，步骤 402–424）**：按流程组织上述机制——接收任务命令并建立依赖表条目；启动生产者任务；检测 pre-exit 触发（PREEXIT 指令或默认判据）；在触发后、生产者完成前启动消费者任务；消费者执行数据无关部分并在 ACQBULK 处等待；生产者 flush 完成后经依赖表解除数据依赖；消费者通过同步点执行数据依赖部分；任务完成后释放依赖表条目。

## 4. 权利要求摘要

共 20 项权利要求，3 项独立权利要求（claim 1 处理器、claim 11 方法、claim 20 系统）。

**独立权利要求 1（处理器）**：一种处理器，包含内存接口与耦合的工作调度/分发单元（WSDU）；WSDU 配置为：接收第一任务命令并启动第一任务，其中第一任务与第二任务之间存在调度依赖；**基于第一任务关联的 pre-exit 触发、在第一任务执行完成之前**解除该调度依赖；并基于调度依赖的解除启动第二任务。

**独立权利要求 11（方法）**：与 claim 1 对应的方法权利要求（启动第一任务 → pre-exit 触发解除调度依赖 → 在完成前启动第二任务）。

**独立权利要求 20（系统）**：存储任务描述符的存储器 + 耦合的 WSDU，执行上述解耦与提前启动动作。

从属权利要求（claim 2–10、12–19）按主题分组：

- **pre-exit 的指令化**：pre-exit 触发即插入生产者程序的调度依赖指令（PREEXIT），可指定解除对特定/全部消费者的调度依赖；
- **启动完成触发**：以生产者全部线程块启动完成作为 pre-exit 判据（对应 ordering guarantee）；
- **抢先 flush 广播**：在启动最后一个生产者线程块时广播内存刷新请求；
- **数据依赖解除**：基于任务依赖表（锁存器置位）解除数据依赖，随后消费者通过同步指令（ACQBULK）继续执行；
- **指令/常量预取**：启动消费者前预取其指令与常量数据；
- **启动次序**：保证生产者最后一个线程块先于消费者第一个线程块启动；
- **消费者三段结构**：消费者含数据无关部分、同步指令、数据依赖部分。

## 5. 与 TMU（Task Management Unit）的关系

1. **WSDU 230 是 TMU 谱系的第三代形态**。Kepler 时代为 Task/Work Unit 207 = TMU 300 + WDU 340；Volta/Ampere 时代为独立的 TMU 215/234 与 WDU 并列；本专利（2022，Hopper 世代）中二者合并为 Work Scheduler/Distribution Unit 230。名称虽不再出现 "TMU"，但其位置（Host Interface 与 SM 阵列之间）、职责（任务接收、依赖判定、分发）与 TMU 完全对应，且把依赖判定逻辑显式化为 Scheduling Dependency Logic 232 + Task Dependency Table 240。
2. **TMU 职责的进一步扩张**：在 US11182207B2 中 TMU 获得了预取引擎与依赖计数器；本专利进一步赋予其**片上依赖锁存器表**（Task Dependency Table 240，只跟踪活跃任务、行数有限的 RAM）与**两类依赖的差异化解析**能力，并支持 SM 端直接提交消费者任务命令（[0050]），任务前端越来越接近"任务图硬件执行引擎"。
3. **发明人连续性**：Gentaro Hirota 是 US11182207B2（描述符预取）的共同发明人，两案在预取机制上直接衔接；Jack Choquette 与 Ronny Krashinsky 是 Hopper 架构白皮书作者，印证本案对应 Hopper 世代前端。

## 6. 与 NVIDIA PDL（Programmatic Dependent Launch）的关系

本节为机制对照分析：专利文本通篇未出现 "PDL"/"Programmatic Dependent Launch" 字样，下述对应关系由本解析基于机制比对给出。

CUDA 11.8（2022 年发布，Hopper 支持）引入 **Programmatic Dependent Launch（PDL，编程式依赖启动）**，公开接口有三要素：

| PDL 公开接口 | 语义 | 本专利对应机制 |
| --- | --- | --- |
| `cudaLaunchAttributeProgrammaticStreamSerialization`（启动属性） | 允许消费者 kernel 在生产者尚未结束时就被调度发射；硬件保证生产者最后一个线程块先于消费者第一个线程块启动 | 调度依赖解耦 + 启动次序保证（3.3，[0075]–[0079]） |
| `cudaTriggerProgrammaticLaunchOrdering()`（生产者设备端） | 生产者 kernel 在输出就绪点主动提前释放启动次序约束，不必等 kernel 结束 | **PREEXIT 指令 330**（[0071]–[0073]） |
| `cudaGridDependencySynchronize()`（消费者设备端） | 消费者 kernel 中的数同步点，阻塞至上游数据可见 | **ACQBULK 指令 390** 与三段结构中的数据无关/依赖分界（[0074]、[0080]–[0081]） |

**时间线吻合**：本案申请日 2022-01-25，早于 CUDA 11.8 正式发布；发明人含 Hopper 架构核心成员。结合此前整理的 7 件 TMU 专利均未提及 PDL 的事实（US11182207B2 的"完成前预取"是最接近的前驱机制），**本申请可视为 PDL 特性的硬件侧披露**：它解释了 PDL 之所以能让相邻 kernel 重叠启动的底层支撑——WSDU 内的调度/数据依赖解耦、pre-exit 触发、依赖锁存器表与抢先 flush。

## 8. 评价与启示

**技术重要性**：

- 直击任务图执行的结构性瓶颈：把"启动次序"与"数据可见性"拆成两条独立可优化的依赖通道，是比 US11182207B2 更激进的一步——后者仍在"生产者完成"之后启动消费者，只是提前备好了材料；本案直接让消费者**在生产者完成前启动**。
- 消费者三段结构 + ACQBULK 把同步开销集中到一个可预测的点，使前端分发、指令/常量预取、flush 三者都能与生产者尾部执行重叠；FIG. 3 的关键路径分析直观展示了延迟削减来源。
- Task Dependency Table 240 采用"片上 RAM、只跟踪活跃任务、行数有限"的实现策略，把依赖跟踪硬件成本控制住；依赖锁存器（Wait On / Arrive At）给出了批量 release/acquire 的具体硬件形态。
- 该专利与 CUDA Graphs + PDL 的软件栈共同构成理解 Hopper 及以后 GPU 任务前端的关键一手资料。

**局限性（基于专利文本可推断）**：

- PREEXIT 的位置需要开发者/编译器判断：放得过早，消费者会在 ACQBULK 处长时间空等（占用 SM 资源）；放得过晚，收益递减。文本承认位置可调但未给出自动放置策略；
- Task Dependency Table 行数有限，高度并发的活跃任务数可能触及表容量（文本未描述溢出处理细节）；
- 本地 PDF 为扫描件、无文本层，个别附图标记与段落细节依赖视觉阅读，正式引用前建议核对 USPTO 官方文本。
