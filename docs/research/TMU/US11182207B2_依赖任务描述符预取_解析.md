## 2. 发明背景与待解决问题

**应用场景**：PPU 通过 API 124 支持把工作负载表示为 Task Graph 128（任务图，有向图）：节点是 Task（任务），边表示 Producer Task（生产者任务）与依赖它的 Consumer Task（消费者任务）之间的关系；依赖可以是数据依赖和/或执行依赖（"happens before"）。依赖多个生产者的任务称 join task，被多个消费者依赖的任务称 fork task；任务的全部线程完成后，依赖它的消费者任务才能开始执行。

**待解决问题**：生产者任务完成到消费者任务开始执行之间存在 "dependency resolution latency"（依赖解析延迟），它直接增加执行整个工作负载的总时间。文本列出其主要来源：

1. 把生产者产生的数据写入所有 SM 310 可访问的共享缓存/存储器（memory flush）；
2. 从存储器读取消费者任务的描述符（task descriptor fetch）；
3. 从存储器读取消费者任务的指令（instruction fetch）；
4. 从存储器读取消费者任务的常量数据（constant fetch）。

文本强调：依赖解析延迟与任务本身执行时长基本无关、相对恒定；因此对含大量短任务的工作负载（明确点名 deep learning workloads），该延迟可与任务执行时间相当甚至超过它；且 "strong scaled" 工作负载随处理器性能提升，单任务执行时间越来越短，问题愈发突出。

**现有技术的不足**（按文本表述）：传统任务管理单元用 current count 跟踪依赖——软件应用把每个任务的 current count 初始化为生产者总数，生产者完成后递减，减到零即启动任务；若任务位于循环（loop）中，下一次迭代前必须由软件应用重新初始化 current count，而软件与 PPU 之间的交互耗时，显著增加复杂任务图的总执行时间。此外，消费者任务启动信息（描述符、指令、常量）在生产者完成时不可用，只能串行取回，造成延迟。（注：用户模板中提到的"信号量、轮询"在本专利提取文本中并未出现，文本对现有技术的批评集中于上述软件初始化开销与串行取数延迟。）

### 3.2 关键机制详解

**TMU 234 内部结构（FIG. 4）**：Dependency/Prefetch Unit 410、Active List 420、Consumer Task Descriptor Cache 480、Scheduling/Launch Unit 490。Task Descriptor 430（图中示 430(1)…430(L)）是描述一个任务的数据记录，字段包括：

- Task Configuration 450：配置 PPU 组件执行任务所需数据（CTA program start address、以 CTA 计的 grid dimensions、以线程计的 CTA dimension、寄存器与共享内存需求等）；
- Dependency Count 442：该任务所依赖的生产者任务总数（join task 至少为 2）；
- Current Count 444：尚未满足的依赖数；
- Self-Reset Flag 446：为 true 时触发依赖计数的自动复位（文本此处另有一处写作 "self-reset flag 426"、"dependency count 422"，系原文明显笔误，应为 442/446）；
- Consumer Task Descriptor Pointer 470(1)-470(2)：指向本任务各消费者任务的描述符（可为 NULL；替代实施例中可为任意正整数 N 个）；
- Consumer Flags 460(1)-460(2)：与每个指针 470(y) 一一对应，含 Descriptor Prefetch Flag 462、Instruction Prefetch Flag 464、Constant Prefetch Flag 466；为 true 时分别触发对相应消费者任务的描述符预取、指令预取、常量预取。

**初始化**：执行工作负载前，软件应用对每个任务发送 dependency initialization command，Dependency/Prefetch Unit 410 把 Dependency Count 442 拷贝到 Current Count 444；随后软件把根任务描述符 430(1) 的指针传给 PPU 202，其 Current Count 为零，依赖视为满足。

**预取时机（三类预取并行于生产者的不同阶段）**：

1. Task Descriptor Prefetch 522：当 Scheduling/Launch Unit 490 发起生产者任务 X 的 Task Launch 530 时，Dependency/Prefetch Unit 410 对每个 Descriptor Prefetch Flag 462 为 true 的消费者发起描述符预取——解引用 Consumer Task Descriptor Pointer 470(y)，把取回的描述符存入 Consumer Task Descriptor Cache 480，且至少一部分预取与任务 X 的启动过程并行；预取通常在生产者任务执行完成前完成，使描述符取数不再贡献依赖解析延迟。缓存容量有限，预取时机是"缩短消费者描述符在缓存中的驻留寿命"与"最小化依赖解析延迟"之间的权衡。
2. Instruction Prefetch 542 / Constant Prefetch 552：生产者任务 X 执行完成、SM 310 执行 Memory Flush 510 的同时，对相应 flag 为 true 的消费者并行发起指令预取与常量预取，写入指令缓存/常量缓存（或合一的 instruction/constant cache）。时机选择的理由：若在生产者执行完成前预取会引发 cache thrashing（指令/常量缓存正被任务 X 使用）；而 memory flush 及后续活动足以掩盖（subsume）预取开销。

**依赖计数递减与就绪判定**：Memory Flush 510 完成后（确保任务产出数据对所有可分配任务的 SM 可见；一种实现是各 SM 把 L1 数据经 Work Distribution Crossbar 330 写入 L2），Dependency/Prefetch Unit 410 执行 Count Update 518：对任务 X 的每个消费者描述符递减其 Current Count 444；若递减后为零，则把该消费者描述符加入 Active List 420。若任务 X 的 Self-Reset Flag 446 为 true，则同时把其 Dependency Count 442 拷贝回 Current Count 444，实现依赖跟踪的自动复位（支持 Conditional Loop 610 反复执行，无需软件重发初始化命令）。随后把生产者描述符 430(x) 移出 Active List 420（可在 memory flush 完成后任何时刻进行）。

**命中缓存路径**：若任务 X 的描述符已因先前预取驻留在 Consumer Task Descriptor Cache 480，则直接从缓存加入 Active List 420，跳过 descriptor fetch；同理指令/常量若已缓存则跳过相应 fetch，使消费者任务得以"无延迟"启动。文本示例：预取可使某些 PPU 202 的依赖解析延迟减少一半以上。

**工作流（FIG. 7A–7B，method 700）**：702 判定任务 X 依赖满足 → 704 描述符是否已缓存？是→706 缓存描述符加入 Active List 420；否→708 执行 Task Descriptor Fetch 520 后加入 → 710 按描述符发起 Task Launch 530 → 712 对每个为 true 的 Descriptor Prefetch Flag 462 发起消费者描述符预取 → 714 启动完成 → 716/718 指令未缓存则执行 Instruction Fetch 540 → 720/722 常量未缓存则执行 Constant Fetch 550 → 724 发起 Task Execution 560 → 726 执行完成并发起 Memory Flush 510 → 728/730 对为 true 的 Instruction/Constant Prefetch Flag 并行发起相应预取（注：FIG. 7B 中步骤 730 的框内文字被提取为 "instruction prefetch"，与说明书所述"常量预取 552"不符，原文提取不清/疑为图内笔误）→ 732 flush 完成 → 734 对每个 Consumer Task Descriptor Pointer 470 更新对应 Current Count 444 → 736 Self-Reset Flag 446 为 true？是→738 拷贝 Dependency Count 442 至 Current Count 444 → 740 将生产者描述符移出 Active List 420 → 742 工作负载完成？否→回到 702。

**实施例变体**：
- 软件可经 API 124 / PPU Driver 122 发送 "task descriptor prefetch command"，主动预取指定任务描述符（CTA 程序直接启动消费者时可先行发出）；
- "decrement dependency" 命令：使任务可依赖任务图外部事件（如 CPU 102 的信号 K、网络报文 V；示例 dependency count 为 3），软件在事件到达时代替硬件递减计数；
- 若消费者 Dependency Count 442 小于 2（非 join task），可不必使用 Current Count，生产者的 count update 时直接把消费者描述符加入 Active List 420；
- 条件分支/迭代条件可由软件、硬件或其组合求值（如任务 A、B、C 顺序执行后评估任务 C 的收敛条件，未收敛则把任务 A 的描述符重新加入 Active List 420 形成循环）；
- prefetch 与 self-reset 功能可由 Host Interface Unit 232、TMU 234、Dependency/Prefetch Unit 410、Scheduling/Launch Unit 490、Work Distribution Unit 236 的任意组合实现；Active List 420 可与 PPU 任意层级缓存配合实现；
- FIG. 6 示例：任务图含任务 A–F（430(1)–430(6)）与 Conditional Loop 610（F→A）；B 为 fork task（消费者 C、D），E 为 join task（Dependency Count=2）；Consumer Flags "111" 表示三项预取全开，任务 D 的描述符对消费者 E 配置 "000"（同一消费者 E 不被重复预取），演示了标志位配置与自动复位如何使循环无需软件干预执行。

**独立权利要求 10（系统）**：存储一个或多个任务描述符的存储器；及耦合到该存储器的电路（circuitry），执行：确定第二任务依赖于正在启动的第一任务；确定第一任务的任务描述符指定了对第二任务的预取功能已使能；在第一任务执行前发起取回第二任务描述符；至少在第一任务执行后基于该描述符启动第二任务。

**独立权利要求 15（系统）**：存储任务图的存储器；耦合的处理器，除 claim 10 的判定/预取/启动动作外，还"执行第一任务"（即显式涵盖任务执行环节），再基于预取的描述符启动第二任务。

从属权利要求按主题分组：

- 指令/常量预取（claim 2、3 / 11、12 / 16、17）：在启动第二任务前，发起取回第二任务的指令、常量数据；
- 依赖跟踪自动复位（claim 4、5、7 / 13、14 / 18）：第一任务执行完成后重新初始化其依赖跟踪器以支持再执行；复位方式为把总依赖计数拷贝到当前计数；复位前先确认第一任务描述符指定了再初始化功能已使能；

## 5. 与 TMU（Task Management Unit）的关系

TMU 234 是本专利方案的唯一执行主体，本专利显著扩展了 TMU 的职责边界：

1. **从"调度器"到"预取引擎"**：传统 TMU 只负责任务就绪判定与分发；本专利在 TMU 内设置 Dependency/Prefetch Unit 410，使其在生产者任务启动/执行/flush 期间并行取回消费者的描述符、指令、常量，TMU 直接驱动跨层缓存（Consumer Task Descriptor Cache 480、指令/常量缓存，最终落到 L1.5 Cache 335 层级）的数据搬运。
2. **依赖跟踪硬件化**：Dependency Count 442 / Current Count 444 存于任务描述符内并由 TMU 维护，count update、就绪判定（加入 Active List 420）全部在 TMU 内闭环。
3. **循环依赖的自复位**：Self-Reset Flag 446 让 TMU 在任务完成后自动把 dependency count 拷回 current count，替代软件每次迭代重发初始化命令，把控制流循环的开销从 host 软件路径移入硬件。
4. **软件旁路接口**："task descriptor prefetch command" 与 "decrement dependency" 命令把 TMU 能力暴露给应用/驱动，使软件能做负载级调优并接入任务图外部事件。
5. 结构上 TMU 234 位于 Host Interface Unit 232 与 Work Distribution Unit 236 之间，接收三方（host、WDU、SM）任务来源，本专利的全部新增逻辑都落在该位置，说明 NVIDIA 把 TMU 定位为"任务图硬件执行引擎"而不仅是命令转发器。

## 7. 评价与启示

**技术重要性**：
- 精准命中任务图执行的结构性瓶颈——依赖解析延迟与任务执行时间无关，随任务粒度变小（深度学习、强扩展负载）其占比急剧上升；文本称预取可把依赖解析延迟削减一半以上；
- 把三类取数（描述符/指令/常量）分别锚定到生产者生命周期的不同空隙：描述符预取搭"task launch"的空隙，指令/常量预取搭"memory flush"的空隙，是典型的"用硬件空闲窗口掩盖内存延迟"设计；
- Self-Reset 机制消除了循环任务图对 host 软件的往返依赖，是"任务图硬件自治化"的关键一步；decrement dependency 命令则把硬件计数器开放给外部事件（CPU 信号、网络报文），为跨设备/跨域同步预留接口。

**局限性（基于专利文本可推断）**：
- 预取由生产者描述符中的每消费者 3 bit 标志静态配置，文本未描述基于运行时行为的动态预取策略（软件可用 prefetch command 手工补偿）；
- Consumer Task Descriptor Cache 480 容量有限，预取时机依赖对生产者执行时长的预判，过早预取会挤占缓存、过晚则收益不足，文本承认这是权衡；
- 描述符中消费者指针默认仅 2 个（替代实施例才扩展为 N），高度扇出的 fork task 需依赖更宽的实施例；
