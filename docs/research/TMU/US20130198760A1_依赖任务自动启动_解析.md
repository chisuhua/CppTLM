## 2. 发明背景与待解决问题

**发明概要**（ABSTRACT / SUMMARY，[0007]–[0010]）：在第一任务执行完成时自动启动其依赖任务，以降低两者切换延迟。依赖任务的信息被编码进第一任务的元数据（metadata）中；第一任务完成时，task scheduling unit 得到通知并直接启动依赖任务，**无需任何信号量的 release/acquire**。该信息包括使能标志（enable flag）与指向依赖任务的指针；依赖任务启动后，第一任务即被标记为完成，其元数据所占内存可复用于新任务。由于依赖任务信息在第一任务编码时就已写入，执行时刻天然可用；依赖任务还可再指向第二依赖任务，形成自动执行的链。

说明书 BACKGROUND（[0004]–[0006]）指出依赖任务（dependent task）的传统同步方式及其代价：

- **信号量（semaphore）同步开销**：依赖任务的执行通常依赖信号量协调——第一任务释放（release）信号量，依赖任务获取（acquire）后才能开始。由于依赖任务需要第一任务计算出的值/数据，必须等待第一任务完成。
- **延迟问题**：release/acquire 通过内存读写完成（第一任务写内存释放、依赖任务读内存获取），在"第一任务执行完成"与"依赖任务可以开始"之间引入显著延迟（若干时钟周期）。
- **带宽消耗**：信号量操作需要一次内存写和通常若干次内存读，消耗内存带宽；在可用带宽受限时降低整体处理性能。
- **获取位置的补充披露**（[0067]）：在某些实施例中，semaphore acquire 在 host interface 206 或 front end 212 执行——即信号量等待落在 GPU 前端，进一步加重前端任务切换的开销。
- 因此本领域需要一种改进的依赖任务启动机制，特别是在多线程执行中降低从第一任务切换到依赖任务的延迟（[0006]）。

说明书同时给出对照方案（[0067]）：TMD 的 execution parameters 415 本可存储多个 semaphore release含内存屏障类型、信号量数据结构地址、大小、payload、reduction 操作的 enable/type/format 等），但用信号量保证两个 TMD 串行执行的切换延迟高于使用 dependent TMD 机制。

### 3.1 整体架构

**附图清单**（[0012]–[0018]）：FIG. 1 计算机系统的框图（computer system 100）；FIG. 2 并行处理子系统（parallel processing subsystem 112）的框图；FIG. 3A FIG. 2 中 Task/Work Unit 207 的框图；FIG. 3B 一个 PPU 内某个 GPC 208 的框图；FIG. 4A TMD 322 内容的概念图；FIG. 4B 一个 original task 与两个 dependent task 的示意图；FIG. 5 自动启动依赖任务的方法流程图。

说明书 [0024]–[0035] 给出 PPU 202 的总体结构，[0038]–[0042] 给出 Task/Work Unit 207 的细化结构：

- **数据流**：CPU 102 将命令流写入 pushbuffer；PPU 202 的 I/O unit 205 接收命令，host interface 206 读取 pushbuffer 并将命令流输出给 Front End 212；Front End 212 将任务送入 **Task/Work Unit 207**；Task/Work Unit 207 将任务分发给 Processing Cluster Array 230 中的各 GPC 208（FIG. 2、FIG. 3A）。
- **Task/Work Unit 207 的组成**（FIG. 3A，[0038]）：
  - **Task Management Unit 300（TMU）**：按执行优先级级别（execution priority levels）组织待调度任务；每个优先级，在 **Scheduler Table 321** 中保存指向 TMD 322 的任务指针链表（linked list）。TMU 接收任务的速率与其调度任务的速率解耦（decoupled），从而可按优先级信息或其他策略调度。
  - **TMD Cache 350**：缓存一个或多个 TMD 322 的（相对较小的）调度所需部分。TMD 322 是大结构（如 256 Bytes 或更多），通常存于 PP memory 204，全量访问带宽代价高；TMD 的其余部分在任务被调度（转入 Work Distribution Unit 340）时才从 PP memory 204 取回（[0040]）。
  - **Work Distribution Unit 340**：含 **Task Table 345**，其槽位（slot）可被正在执行的任务的 TMD 322 占据；有槽位空闲时 TMU 方可调度任务执行。更高优先级任务可将占据槽位的低优先级任务逐出（evict）：被逐任务停止，若未完成则重新挂回 Scheduler Table 321 的链表（[0039]）。
- **任务来源**：GPC 208 从 work distribution unit 领取任务；任务指针指向以 TMD（Task Metadata）形式编码并存于内存的计算任务，指针包含在 pushbuffer 命令流中、经 front end 212 到达。Task/Work Unit 207 确保各 GPC 208 在每个 TMD 指定的处理开始前处于有效（valid）状态。每个 TMD 可带优先级；TMD 还可含参数控制其被加到链表头部还是尾部，提供另一层优先级控制（[0030]）。处理任务也可来自 Processing Cluster Array 230（FIG. 3A 中 "From/To Processing Cluster Array 230"）。
- **GPC 208 内部**（FIG. 3B）：Pipeline Manager 305 将任务分发给 SM 310，并控制 Work Distribution Crossbar 330；GPC 内还有 Texture Unit 315、L1.5 Cache 335（附图标提取作 "1.5 Cache 335"）、preROP 325、MMU 328 等。FIG. 3B 标注 Work Distribution Unit 340 与 Crossbar Unit 210 及各 GPC 208 相连，并经 Crossbar Unit 210 从 Memory Interface 214 取数（部分附图标记原文提取不清）。

### 3.2 关键机制详解

**（1）依赖任务 vs 子任务**（[0037]）：子任务（child task）在父任务执行期间动态生成；依赖任务在父任务定义时即已定义，父任务开始执行时其信息已知且可用。Task/Work Unit 207 动态调度普通任务与子任务，并在指定了依赖任务的任务执行完成后**自动调度该依赖任务**。

**（2）TMD 322 的参数内容**（[0058]–[0064]）：Initialization Parameters 405 用于在 TMD 启动时配置 GPC 208，可含起始程序地址、queue 425 大小、各缓存（texture header/sampler/data cache、data cache、constant cache 等）是否在启动时无效化的位、CTA 的线程维度、TMD 版本号、指令集版本号、以 CTA 宽/高/深表示的 grid 维度、memory bank mapping 参数、应用可见的 call stack 深度与 call-return stack 大小。Scheduling Parameters 410 含 grid/queue 类型位：grid TMD 启动固定数量的 CTA（数量 = grid 宽×高×深），queue 425 被替换为指向待处理数据的 queue pointer；queue TMD 则以 queue 425 中的条目为 CTA 输入数据，条目可代表其他 TMD 执行期间生成的子任务（嵌套并行），CTA 数量随写入条目数动态变化，且含参数 N（每 CTA 处理的条目数，写满 N 条即启动一个 CTA）与 coalesce waiting time（队列近空且条目不足 N 时的等待时间，用于避免 producer-consumer 死锁）。Task/Work Unit 207 可据此构造以带队列的 TMD 为节点的 directed graph of processes。Execution Parameters 415 可存储多个 semaphore release 描述（见第 2 节）。

**（3）TMD 回收与 TMD Cache flush 竞争**（[0041]）：TMD 322 在软件控制下写入，计算任务完成后可回收以存储新任务信息。因 TMD 可能驻留 TMD Cache 350，完成任务的条目必须 flush；但新任务信息的写入与 flush 引发的 write-back 相互解耦——软件先写新任务信息到 TMD 322、再将其作为 pushbuffer 的一部分提交给 front end 212，期间软件收不到 cache 已 flush 的确认。若 flush 的回写晚于新写入，旧数据可能覆盖新任务信息。为此划出 hardware-only 区域：只有 TMU 300 可访问该区域，软件可访问其余部分；旧任务的残留信息只会存在于 hardware-only 区域，配合启动命令中的"首次载入 TMD Cache 350 时拷贝位"选项，即可保证回收后的 TMD 只承载新任务信息。

**（4）TMD 322 的结构**（FIG. 4A，[0056]–[0067]）：TMD 322 存储 Initialization Parameters 405、Scheduling Parameters 410、Execution Parameters 415、CTA State 420、Hardware-Only Field 422、（可选）Queue 425，并含 **Dependent TMD Field 424**（附图标签中 "40"/"45" 等数字原文提取不清，以正文编号为准）。要点：

- Scheduling Parameters 410 含 grid TMD / queue TMD 类型位、TMD group ID、链表插入位置（head/tail）位、下一 TMD 指针、SM 使能掩码，以及"调度依赖 TMD 时是否同时将字段拷贝到 hardware-only field 422"的位。
- **Dependent TMD Field 424** 包含：使能标志（enable flag，置位表示原 TMD 完成后应启动依赖 TMD）；指向依赖 TMD 的 task pointer（一实施例中为依赖 TMD 40-bit 虚拟地址的高，如高 32 位）；依赖 TMD 的类型指示（grid 或 queue）；以及"依赖 TMD 启动（或载入 TMD Cache 350）时是否向其 hardware-only field 拷贝数据"的标志。

**（5）字段拷贝机制（TMD Field Copy Enable）**（[0042]，[0078]）：基于（3）所述的回收竞态，当 TMD 322 携带依赖 TMD 信息时，该信息含一个标志，指示依赖 TMD 被载入 TMD Cache 350 并启动时是否应把位拷贝进依赖 TMD 自己的 hardware-only 区域。自动启动流程的 Step 525/530 即执行该判断与拷贝：将依赖 TMD 中非 hardware-only 部分的位拷贝到其 hardware-only 条目，确保 TMU 300 在调度依赖任务时能访问其所需字段（FIG. 4B 中由 453/463/473 三个标志逐级控制）。

**（6）Original Task Grid (2,2) 450 示例**（FIG. 4B，[0069]–[0074]）：三级任务链——

- **Original Task 450**：grid TMD，grid (2,2)，由 4 个 CTA 执行；其 dependent TMD field 含 **Dependent TMD Enable 451 = TRUE**、**Dependent TMD Pointer 452**（指向 460）、**TMD Field Copy Enable 453 = TRUE**。
- **Dependent Task 460**：grid TMD，grid (1,1)，仅 1 个 CTA 执行；**Dependent TMD Enable 461 = TRUE**、**Dependent TMD Pointer 462**（指向 470）、**TMD Field Copy 463 = FALSE**。
- **Dependent Task 470**：queue TMD（附图标注 Queue (depth)）；**Dependent TMD Enable 471 = FALSE**，链条终止，其 Dependent TMD Pointer 472 与 TMD Field Copy 473 被忽略（原文写作 "462/463 are ignored"，疑为笔误，按上下文应为 472/473）。
- 依赖任务 460/470 **不出现在 pushbuffer 中**：其 TMD 在原任务执行前写入内存，执行信息编码在各级 dependent TMD field 内。
- 用途示例：批处理型功能（batch-type processing），如内存碎片整理（memory defragmentation）、内存分配/释放；或配置为高优先级的 scheduler task——同一时刻只执行一个 scheduler CTA，负责判定 grid 何时完成并发起后续（continuation）任务的启动。
- 通过相对 grid 尺寸可控制依赖任务相对原任务的执行频率（原任务 4 CTA 对应依赖任务 1 CTA，反之亦然）。

**（7）自动启动流程（method 500，FIG. 5，[0075]–[0080]）**：

1. **Step 505**：TMU 300 接收 Processing Cluster Array 230 发来的通知：编码为 TMD 322 的第一任务已执行完成；
2. **Step 510**：TMU 300 读取第一任务元数据中的 dependent task enable flag（该标志及编码依赖任务的 TMD 均在第一任务执行前写入，依赖任务不在 pushbuffer 中）；
3. **Step 515**：判断 enable 是否 TRUE；否则 **Step 520** 将原 TMD 标记为 done；
4. **Step 525**：判断 TMD field copy enable 是否 TRUE；若是，**Step 530** 将依赖 TMD 非 hardware-only 部分的位拷贝到其 hardware-only 区域，保证 TMU 可访问所需字段；
5. **Step 535**：读取 dependent TMD pointer；
6. **Step 540**：将原 TMD 标记为完成（其元数据内存可复用于新任务）；
7. **Step 545**：将依赖 TMD 加入 Scheduler Table 321，从而由 Processing Cluster Array 230 启动执行。

全程**无需任何信号量的 release/acquire**。依赖任务自身还可携带第二依赖任务信息，实现任务链自动连续执行（FIG. 5 中部部分标号原文提取不清，步骤以正文 [0076]–[0079] 为准）。

## 4. 权利要求摘要

权利要求共 **21 项**：方法权项 1–12，系统权项 13–20，非暂态计算机可读存储介质权项 21；独立权项 3 项（1、13、21）。

**独立权项 1（方法）**：一种自动启动依赖任务的方法，包括：在多线程系统中接收第一处理任务已完成执行的通知；读取编码该第一任务的 first task metadata 中存储的 dependent task enable flag（该标志在第一任务执行之前写入）；当第一任务执行完成时，确定该标志指示应执行依赖任务；并将该依赖任务排入多线程系统执行。

**独立权项 13（系统）**：一种可自动启动依赖任务的多线程系统，包括：存储 first task metadata 的内存；配置为执行第一任务并在其完成时产生通知的 general processing cluster；与该 cluster 耦合的 task management unit，配置为接收完成通知、读取执行前写入的 dependent task enable flag、确定应执行依赖任务、并为该 cluster 调度依赖任务。

**独立权项 21（CRM）**：非暂态计算机可读存储介质，存储使处理器执行与权项 1 实质相同步骤的指令。

**从属权项分组**：

- **指针读取与位置**（2、3、4、14、15）：读取指向依赖任务元数据的指针；该指针包含在第一任务元数据内；指针在第一任务执行前写入。
- **字段拷贝（field copy）**（5、6、16、17）：判断是否启用向依赖任务元数据的 hardware-only 区域的拷贝；启用时将依赖任务元数据第一区域的数据拷贝至其 hardware-only 区域。
- **原任务收尾**（7、18）：读取指针之后，将第一处理任务标记为已完成。
- **任务类型与链式依赖**（8、9、19、20）：依赖任务的任务类型（grid/queue）包含在第一任务元数据中；依赖任务元数据指示其还指定了第二依赖任务（链式自动启动）。
- **依赖任务的角色与执行频率**（10、11、12）：依赖任务可配置为执行任务调度功能（scheduler task）；可配置为对第一任务的所有执行只执行一次，或对每次执行执行多次。

## 5. 与 TMU（Task Management Unit）的关系

本专利在 NVIDIA 公开专利文献中首次较系统地披露了 GPU 前端中 **Task Management Unit（单元 300）** 的组织结构与职责，是理解 TMU 演进的奠基性文本：

- **结构定位**：明确 Task/Work Unit 207 = Task Management Unit 300 + Work Distribution Unit 340 的二分结构（FIG. 3A），TMU 位于 Front End 212 与 Work Distribution Unit 340 之间，上承 pushbuffer 命令流，下接各 GPC 208。
- **职责披露**：按优先级组织任务（Scheduler Table 321 按优先级分层的指针链表）；接收与调度速率解耦；管理 TMD Cache 350（含 flush/write-back 竞态及 hardware-only 区域对策）；在任务表有空槽时调度、支持高优先级逐出与回挂；接收处理集群的完成通知并自动启动依赖任务。
- **术语与数据结构**：确立了 TMD（Task Metadata）322 作为 GPU 硬件任务描述符的核心地位——含初始化/调度/执行参数、CTA 状态、hardware-only field、dependent TMD field——后续 TMU 系列专利（task descriptor、active list、dependency count 等）均可视为该结构的演进。
- 在本系列（12_Task_Management_Unit）中，本件是理解 NVIDIA GPU 前端调度硬件化的起点文档：它把原本由驱动/信号量完成的依赖同步下沉为 TMU 硬件行为。

## 7. 评价与启示

**历史地位**：本申请提交于 2012-01-27（Kepler 时代），是最早把"依赖任务自动启动"从驱动层信号量语义下沉到 GPU 前端硬件（TMU 300）的公开文献之一。其 FIG. 2/FIG. 3A 对 host interface 206 → front end 212 → Task/Work Unit 207 → GPC 208 通路的完整披露，使之成为研究该时期 NVIDIA GPU 前端调度硬件的一手资料。

**对理解 TMU 演进的价值**：

- 提供了 TMU 的"零号样本"：Scheduler Table 321 + 优先级链表 + TMD Cache 350 + hardware-only field + 依赖字段，构成了后续 TMU 专利（US 8,572,573、US 9,535,815、US 9,928,109、US 10,552,202、US 11,182,207、US 2021/0349763 等系列成员）演进的参照系；
- 揭示了两条持续演进的主线：其一是依赖关系的表达（dependent TMD field → task graph 的 dependency count），其二是元数据访存延迟的隐藏（TMD Cache 350 → Consumer Task Descriptor Cache 480 与 descriptor/instruction prefetch）；
- "依赖任务可作 scheduler task"（[0074]）的披露，暗示了 GPU 上自托管调度（device-side scheduling/continuation task）的早期构想。

**局限性**：

- 依赖关系为静态单链（每个 TMD 至多一个 dependent TMD pointer），不支持扇出/扇入的 DAG 依赖，条件依赖与多 producer 同步仍需信号量（[0066] 明言 semaphore 为备选手段）；
