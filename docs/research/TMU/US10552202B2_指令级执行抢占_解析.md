## 2. 发明背景与待解决问题

- Preemption（抢占）用于在多个应用之间对处理器做 time-slice（时间片）：多个应用需要同时使用处理器时，让每个应用轮流运行短时间片以保证所有应用前进。
- 传统时间片要求处理器流水线完全排空（drain），待处理器空闲后切入另一应用，即 "wait for idle" 抢占。
- 局限一（排空延迟不可控）：当处理器排空在跑工作耗时很长时，wait-for-idle 机制失效。原文举例：运行时间很长的 graphics shader 程序，最坏情况是带无限循环的 shader 程序。
- 为使各应用都能前进，每个应用的时间片必须受限，而长任务会实际挤占其他应用可用的时间片。
- 局限二（全量快照开销大）：另一种被考虑的思路是 stall/freeze 处理器，保存处理器内所有寄存器和流水线 flip-flop 内容，之后再全部恢复。
- 该方式的状态保存/恢复量非常大，存取状态所耗时间侵蚀了各应用在每个时间片内的实际执行时间。
- 因此本领域需要：抢占时**不必保存应用的全部状态**，且**不必等待处理流水线变为空闲**的系统与方法。
- 这本质上是"抢占粒度的权衡"：排空流水换小状态量（慢但省存储）vs 全量快照换低延迟（快但状态巨大）；本案方案介于两者之间并新增软件辅助路径。

## 3. 核心方案

### 3.1 整体架构（附图标记）

- 计算机系统（FIG. 1）：CPU 102、system memory 104、memory bridge 105、I/O bridge 107、parallel processing subsystem 112、display device 110。CPU 102 向 pushbuffer 写入命令流指针，PPU 202 异步读取执行，pushbuffer 可指定执行优先级。
- PPU 202（FIG. 2）：I/O unit 205 → host interface 206 → front end 212 → task/work unit 207 → processing cluster array 230（C 个 GPC 208）；crossbar unit 210、memory interface 214（D 个 partition unit 215）、DRAM 220、PP memory 204。Host interface 206 把 pushbuffer 中的命令流交给 front end 212。
- Task/work unit 207（FIG. 3A）：内含 **task management unit 300** 与 **work distribution unit 340**（task table 345）。Task management unit 300 按执行优先级组织任务：每个优先级在 scheduler table 321 中维护指向 TMD 322 的链表；接收任务入表的速率与调度速率解耦。Work distribution unit 340 有空闲槽位时任务才被调度；无槽位时高优先级任务可驱逐（evict）低优先级任务，被驱逐任务回到 scheduler table 321 链表；子任务（child processing task）亦加入链表。
- GPC 208（FIG. 3B）：**pipeline manager 305** 向 SM 310（M 个）分发任务并控制 work distribution crossbar 330；L1.5 cache 335、preROP 325、MMU 328、texture unit 315。
- FIG. 4 为抢占相关数据通路：host interface 206 → front end 212 → task/work unit 207（task management unit 300 / scheduler table 321 → work distribution unit / task table 345）→ pipeline managers 305 → GPCs 208；图中明确标注两级粒度：**CTA Level Preemption** 与 **Instruction Level Preemption**。
- 抢占触发源：host interface 206 可发起 channel preempt（清除 channel ram entry 的 valid bit、把 channel id 写入 preempt register）或 runlist preempt（写 runlist register 指针）；也可在某 context 耗尽 methods 而其他 context 在等待时、时间片未到期即抢占。时间片可不均等，按 method stream 密度分配。

### 3.2 关键机制详解

**五阶段抢占框架**（由 front end 212 控制）：Phase 1 停止当前 context（CTA 级 = 停在 CTA 任务边界；指令级 = 停在 SM 310 指令边界；若期间有 interrupt/fault 先等其清除）；Phase 2 将当前 context 状态保存到内存；Phase 3 复位引擎；Phase 4 加载新 context 状态；Phase 5 重启此前被抢占的工作。完成后 front end 212 向 host interface 206 发 ACK。Host interface 206 维护 ctx_reload 标志判断被选 context 是否曾被抢占；front end 212 则报告抢占时 context 是否已 idle（idle 则无需 reload）。context freeze 信号自 Phase 2 开始至 Phase 4 结束保持 assert。Context buffer 由 CPU 102 上的程序在抢占前分配，大小基于 PPU 202 配置与 SM 310 数量。

**实施例一：硬件指令级抢占**（FIG. 5A method 500 / FIG. 5B method 560）：
- 卸载路径（method 500）：
  - 505 host interface 206 发出指令级抢占命令，启动卸载当前 context；510 若流水线已 idle 直接跳到 545。
  - 515 front end 212 停止为当前 context 发射新 work；520 向 task/work unit 207 输出 preempt command。
  - 525 task management unit 300 停止向 work distribution unit 340 发任务；work distribution unit 340 停止 launch CTA，把 preempt command 传给 pipeline managers 305；pipeline managers 305 把指令级 preempt command 发给 SMs 310；SMs 310 停止发射指令并进入 trap handler。
  - 530 等待所有 outstanding memory transaction 完成（读请求数据未返回、或显式要求确认的写请求未收到 MMU 328 的 ack 均算 outstanding）。
  - 535 SM 310 内的指令级 context state 与 pipeline manager 305 内的 context state 写入 context buffer（含 SM/GPC 寄存器、shared memory；L1.5 cache 335 的写被强制刷出并 invalidate；trap handler 随后 exit 所有活跃线程使 SM/GPC 空闲）。
  - 540 pipeline managers 305 向 work distribution unit 340 报告指令级部分已 idle → work distribution unit 340 保存 CTA 级状态 → 报 task management unit 300 → 保存任务级状态 → 报 front end 212。
  - 545 front end 212 保存自身状态（registers 与 ramchains）；550 标记被抢占并复位流水线。ACK 沿 work distribution unit 340 → task management unit 300 → front end 212 逐级上报。
- 恢复路径（method 560）：565 发起恢复；570 assert context freeze；575 恢复 task/CTA 级状态。
  - 580 pipeline manager 305 令 SM 310 进入 "preemption-restore-begin" 模式、送回被抢占的 CTA 与 thread group、再退出 "preemption-restore-end" 模式；SM 恢复寄存器、barrier、program counter、stack pointer、active mask。
  - 582 negate context freeze；585 **按被抢占顺序** launch CTA（回到同一物理 CTA slot / 物理 thread group ID，保证资源不超限）；590 ACK host interface 206，恢复执行。
- Pipeline manager 305 保存每个 thread group "已退出/被抢占"的状态信息，仅恢复被抢占的 thread group。
- 摘要所述：抢占命令之后仍在流水线中的 in-flight 指令被捕获存入 processing task buffer，恢复时该 buffer 被指定为高优先级任务，确保被抢占指令先于该 context 的任何新指令重新发射。

**实施例二：CTA 级抢占 + 定时器回退**（FIG. 6A method 600 / FIG. 6B method 660）：
- 605–625 与指令级流程相同，但 GPC 208 被排空（drain），下游不留状态；630 等待 GPC idle；635 若定时器（可编程时钟周期数）到期 GPC 仍未 idle，则转 FIG. 5A 步骤 520 **回退为指令级抢占**；GPC idle 则 640 保存 CTA/任务级状态 → 645 → 650。
- 恢复（660）：670 assert context freeze；675 恢复 CTA/任务级状态；682 negate；685 由 task/work unit 207 按被抢占顺序重新 launch CTA；690 ACK。
- 粒度可按 context 单独指定：长时运行 context 用指令级抢占以避免长延迟；状态量大的 context 用 CTA 级抢占以减少保存量。

**实施例三：软件辅助指令级抢占**（FIG. 7A method 700 / FIG. 7B method 760，本案核心）：
- 前提机制：task management unit 300 把计算任务组织为 scheduler table 321 中的 TMD group 数组（同优先级一组、组内链表，默认尾插、特殊 TMD bit 头插，链表头优先调度，从而组内按输入顺序调度）。
- 软件辅助机制与硬件 CTA 级抢占组合实现指令级抢占：利用 GPC 208 在执行任务期间可生成 child processing task 的能力，把执行恢复编码为一个 **preemption TMD**，插入**最高优先级 TMD group 链表头部**，保证恢复时先于任何其他 TMD 被调度。Preemption TMD 含 preemption-restore kernel 与指向 context buffer 的指针；同一 TMD 的所有被抢占 CTA 共用一个 preemption TMD。Preemption TMD 与 context buffer 由 CPU 102 上的程序预先分配，大小在抢占前已知（取决于流水线、SM 310 数量与 TMD 大小）。
- 卸载（700）：705 host interface 206 发 **CTA 级** preempt 命令；715/720/725 停发新 work、preempt command 下行；730 各 CTA 调用 **preemption-save kernel**（trap handler 内）；735 为每个 SM 310 内的指令级状态分配 context buffer 分区；740 保存指令级状态（可通过读体系结构寄存器、memory-mapped 寄存器、特殊指令或组合访问；保存内容包括 preemption-restore 指令的起始 PC、context buffer 分区指针、constant buffer 值、寄存器数、shared memory 用量等）；742 把 preemption TMD 优先级设为最高；745 通知 task/work unit（原文写 "task / work unit 307"，疑为 207 笔误）生成了 preemption TMD，然后 exit 指令使 CTA 退出 SM 310、GPC 空闲——"看起来"像正常 CTA 级抢占已排空；748/750/755 保存 CTA 级/前端状态、标记被抢占并复位。Preemption TMD 不会立即被调度（task/work unit 207 正在执行抢占流程），它与其他抢占后到达的附加 work 一起被缓存，由 front end 212 作为 task/work unit 207 的 context state 保存。
- 恢复（760）：770 assert context freeze；775 恢复 CTA 级状态（含 preemption TMD）；780 按被抢占顺序 launch CTA；785 negate freeze、恢复执行并 ACK（此时指令级状态尚未恢复）；790 task/work unit 207 调度 preemption TMD（因其最高优先级），各 CTA 调用 **preemption-restore kernel**；795 从 context buffer 读回每个 CTA 的指令级状态至对应 SM 310；797 设置调用栈使 CTA 正常退出时触发 **AtExit** 例程（释放 preemption TMD 与 context buffer 分区），preemption-restore kernel 退出，用户代码从被抢占点继续执行。

## 5. 与 TMU（Task Management Unit）的关系

TMU 是本案抢占机制的关键参与者和被利用的调度基础设施：

1. **结构定位**（原文引述）：

> "The task / work unit 207 includes a task management unit 300 and the work distribution unit 340. The task management unit 300 organizes tasks to be scheduled based on execution priority levels. For each priority level, the task management unit 300 stores a linked list of pointers to the TMDs 322 corresponding to the tasks in the scheduler table 321."

2. **抢占发起路径上的闸门**：front end 212 的 preempt command 直达 task/work unit 207。原文引述：

> "At step 525 the task management unit 300 within the task / work unit 207 stops issuing tasks to the work distribution unit 340 and outputs the preempt command to the work distribution unit 340."

——TMU 是任务发射停止的第一级，work distribution unit 340 随后停止 launch CTA 并把 preempt command 下传 pipeline managers 305。
3. **状态保存链**：保存顺序为 SM 310 / pipeline manager 305（指令级）→ work distribution unit 340（CTA 级）→ task management unit 300（任务级）→ front end 212（前端寄存器/ramchains），逐级上报完成后由 front end 212 复位流水线。
4. **ACK 与缓存职责**：抢占 ACK 沿 work distribution unit 340 → task management unit 300 → front end 212 反向逐级上报；TMU 保存自身任务级状态，并缓存抢占期间 GPC 208 新生成的附加 work，交由 front end 212 作为 task/work unit 207 的 context state 保存。
5. **调度属性被软件辅助机制复用**：原文 "The task management unit 300 schedules each processing task for execution as either a grid or queue"。软件辅助抢占正是利用 TMU 的 TMD group 优先级链表——preemption-save kernel 生成的 preemption TMD 被置于最高优先级组链表头，使 preemption-restore kernel 在 context 恢复后先于一切新任务被 TMU 调度。
6. **TMU 的接收/调度速率解耦**（原文）：

> "The rate at which the task management unit 300 accepts tasks and stores the tasks in the scheduler table 321 is decoupled from the rate at which the task management unit 300 schedules tasks for execution"

这使抢占期间任务入队（含 preemption TMD 与附加 work）与调度可分别受控。

## 7. 评价与启示

1. **三级抢占粒度体**：本案给出 CTA 级（硬件、排空、状态少）、指令级（硬件、不排空、状态多但快）、软件辅助指令级（借 CTA 级硬件通道 + kernel 软件保存，GPC 无需硬件支持指令级快照）三档，且可按 context 配置、可用定时器在 CTA 级等待超时时自动降级为指令级——是"抢占延迟 vs 状态保存开销"权衡的工程化答案。
2. **对 TMU 语义的巧妙复用**：软件辅助方案没有改动 TMU 的调度器，而是利用其既有特性（优先级链表、头插位、child task 通道）把"恢复"伪装成一个最高优先级计算任务（preemption TMD），并用 AtExit 完成资源回收；这种"把抢占恢复编码为普通任务"的思路对任何基于 TMD/task descriptor 的前端都有借鉴意义。
3. **权利要求与说明书的落差**：独立权利要求落在"按执行时间长度选择 CTA 级抢占技术 + SM idle 后保存状态"，软件辅助的 preemption TMD / save-restore kernel 等核心细节未进入权利要求，保护范围主要覆盖抢占策略选择与定时器回退（claims 8/22）；续案策略相对母案 9,652,282 明显收窄，推测为规避审查引用文献所做的调整。
4. **可靠性细节值得关注**：按被抢占顺序恢复 CTA 并回到同一物理 CTA slot/thread group ID（保证资源预算不超限）、context freeze 覆盖保存/恢复事务窗口、仅恢复未退出的 thread group、pushbuffer 时间片按 method stream 密度加权——均为可落地于 GPU 前端微架构的具体设计点。
5. **文本瑕疵记录**：FIG. 2 标记提取不清（"PPU 2020 )"、"20810/20811/2081C-1" 应为 PPU 202(0)、GPC 208(0)…208(C-1)）；正文 "track which thread groups are preempted per ???" 原文提取不清；正文两处编号笔误（"task / work unit 307" 应为 207；"GPCs 308" 应为 208）；claim 19 引用于 "claim 1"（按原文记录，疑为引用 claim 15 之排版/笔误）。
