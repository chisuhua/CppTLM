## 2. 发明背景与待解决问题

程序员依赖调试/profiling 工具分析源代码以生成更高效的程序。现有技术包括：

- **硬件 trace/采样**：Intel x86 的 Performance Monitor、ARM 的 ETM（Embedded Trace Macrocell）等，按固定周期（如每 10,000 cycles）或事件计数（每 100 次 cache miss、每 50 次 branch call）对活动线程的 program counter（PC）采样。
- **软件插桩（instrumentation）**：驱动向源代码插入指令收集函数/基本块的调用计数与时间信息；或修改已编译二进制。

这些手段用于 GPU 时的缺陷：

1. 嵌入式 trace 工具只采集**当前发射的活动线程**（每核 1–2 个），无法覆盖 GPU 任一时刻成百上千个**stalled 线程**；现代 GPU 每周期可发射多达 120 条指令，全量 trace 需要巨大内存带宽。
2. 软件插桩影响代码生成、增大程序体积、降低性能，导致与未插桩执行结果偏离。
3. 并行处理单元架构缺少处理中断而不干扰程序性能的优化。
4. 线程状态（PC）通常不驻留在核的硬件 PC 中，而由 scheduler unit 维护，仅在线程被选中发射的周期才载入 PC/控制寄存器——传统手段无法随时读取。

待解决问题：以**透明（transparent）、基于硬件**的方式，为并行处理单元上执行的海量线程（活动与非活动）收集执行统计（trace 信息），并精确关联回源代码行，定位 hotspot/bottleneck 及其 stall 原因。

## 3. 核心方案

### 3.1 整体架构

方法总流程（FIG. 1A，method 100）：102 编译源代码生成 program → 104 传送 program 至 parallel processing unit → 106 launch workload → 108 收集一条或多条 trace 信息记录 → 110 将记录关联到源代码中对应指令。

**PPU 200 架构（FIG. 2）**——本专利的 PPU 框图与 TMU 系列专利同源：

- I/O unit 205：经 system bus 202 与 CPU 通信，可实现 PCIe 接口。
- Host interface unit 210：解码命令并转发给 **task management unit 215** 或 memory interface 280 等单元；负责在 PPU 各逻辑单元间路由通信，并向 TMU 215 提供一个或多个 stream 的指针。
- **TMU 215（task management unit）**：macro-scheduler 角色，组织 pending grid 池（详见第 5 节）。
- Work distribution unit 220：耦合于 TMU 215 与 SM 250 之间，管理 active grid 池，选择并 dispatch active grid 到 SM 250 执行。
- SM 250 ×X（例 15 个）：每个 SM 多线程，可并发执行来自 thread block 的 32 线程（每核最多 2048 线程）；经 crossbar 260 连接共享 L2 cache 265，再经 memory interface 280（16/32/64/128-bit 数据总线）连接 memory 204（例多 6 个 GDDR5 SDRAM 设备）。
- 多级存储层次：片外 memory 204 → 片上共享 L2 cache 265 → 各 SM 私有 L1 cache。

**SM 250 内部（FIG. 3）**：instruction cache 305、scheduler unit 310（含两个 dispatch unit 315，可每周期自同一 warp 发射两条不同指令）、register file 320、processing core 350（例 192 个全流水线单精度核，含 FP ALU + INT ALU，IEEE 754-2008）、DPU 351（例 64 个双精度单元）、SFU 352（例 32 个）、LSU 353（例 32 个，负责 shared memory/L1 cache 370 与 register file 320 间 load/store）、interconnect network 380（可为 crossbar）、texture unit 390（例 4 个）。（附图 Sheet 3–5 的 OCR 文本提取不清，标记编号以正文描述为准。）

**trace 采集硬件位置**：每个 SM partition（即分配给某个 scheduler unit 310 的后端资源）实现一个 **trace cell 420**（FIG. 4），含 logic 421（门电路、寄存器、计数器）与 buffer 425（FIFO，可存 16 条记录）。变体：单 trace cell 服务多个 partition，或 trace cell 功能完全并入 scheduler unit 310。scheduler unit 310 内含选择发射逻辑 410 与 **thread state table 430**（16 个 slot，如 slot 0 431、slot 1 432），保存其管理的每个 thread block 的：thread block ID、stall vector、PC 地址（下一条待发射指令）、调度所需其他信息（如 0–31 的优先级值）。

**PC 值 + scheduler state 记录机制**：trace cell 周期性从 scheduler unit 采样；GPU 为 latency hiding 架构（小 cache、长访存延迟、无分支预测/乱序执行），线程 PC 由 scheduler 维护而非硬件 PC 寄存器，本方案直接从 thread state table 读取所有 warp 的 PC 与 stall 状态，覆盖 active 与 stalled 线程。

### 3.2 关键机制详解

**采样触发（FIG. 1B，method 150）**：152 激活 thread block → 154 每周期判断是否采样 → 156 收集记录 → 158 判断是否继续。两种触发方式：(a) CLK 计数器每 N 周期达到阈值；(b) 事件计数（function call、cache miss、branch 指令等）。采样频率经可编程寄存器设定，主机处理器可通过 memory-mapped I/O 写入 memory 204 特定地址、由 PPU 监控总线拷入特殊寄存器。

**记录格式**：每条记录至少含 thread block 所分配的核标识、PC 地址、stall vector（指示 stall 原因的向量；也可指示 eligible——本周期被选中发射）。一个实施例：每采样周期 128 字节 = 16 条 × 8 字节记录（4 字节 PC 地址 + 22-bit stall reason + 4-bit processor identifier + 6 reserved bits），对应 512 线程（每 micro-scheduler 管理最多 16 个 thread block/warp，每 warp 32 线程）。另一实施例用 4 或 6 bit 编码最高优先级 stall reason 的索引。stall reason 包括：等待 dependency barrier（memory 请求未完成、thread block 间同步）、ready 但未被仲裁选中、dispatch unit stall（无可用执行资源）、等待 texture unit 产生 texture/memory 值等。

**带宽控制**：round-robin 模式——trace cell 内置计数器每采样周期递增，仅对计数器指定索引的单个 thread block 生成记录，M 个采样周期（M = 管理的 thread block 数）覆盖全部 thread block 各一次，降低 micro-scheduler 与 trace cell 间带宽。

**可编程过滤**：按 SM（16-bit 向量指示哪些 SM 启用采集）、按 thread block ID、按 workload（task identifier）、按时间范围（基于系统时钟或自 workload 开始的 elapsed time 的 start/end time）过滤。

**输出与关联**：buffer 425（FIFO）暂存后经 LSU 353 / 辅助互连透明写入 memory 204 中由开发平台/驱动分配 event buffer（指针传给 trace cell）；也可复用既有 performance monitor 的 streaming interface，且 trace 信息可附带既有 PM counter 采样值。关联方式：开发平台/驱动生成 **line table**，将编译后二进制指令映射到源代码或中间表示（如 PTX）的行号；配合 program relocation information（program 基地址表），用记录中 PC 值减去基地址得偏移，查表定位到 assembly / IR / 高层源码（HLSL、CUDA C/C++）行。还可做跨 thread block 因果分析：对比 stall 与解 stall 时刻，隔离引发/解除 stall 的具体指令（如哪条 texture 指令导致等待）。

**Replay 机制（可选，FIG. 5A–5B，method 500）**：driver 或 application shim 在 API stream 起点保存 PPU 初始状态，捕获应用产生的 API stream 并重复回放（每次迭代间恢复初始状态），以增大执行统计样本量、提高准确性。步骤 502 编译（驱动可经 IR 两级编译）→ 504 分配 event buffer → 506 启用 replay（可选）→ 508 launch workload → 510 记录流入 event buffer → 512 是否 replay 追加采样 → 514 收集源码/debug/relocation 信息 → 516 关联 → 518 经 GUI（如 NVIDIA Nsight for Visual Studio）显示给程序员。

**统计信息类型汇总**：PC 值/地址、thread block ID、stall vector（多种 stall reason）、核/processor ID、时钟周期索引等 timing 信息、一个或多个 performance counter 值、SM active/inactive 周期数、SM launch 的 task/thread 数（PM counter 既有统计）。

## 4. 权利要求摘要

共 **19 项**权利要求；独立权利要求 3 项（claim 1 方法、claim 14 非暂态计算机可读存储介质、claim 16 系统），三者核心要素一致：

> **Claim 1（方法，概括翻译）**：编译源代码生成程序；launch 由并行处理单元执行的 workload（workload 含一个或多个 task，至少一个 task 执行被配置为执行该程序的 thread block）；收集与配置为执行该程序的多个线程相关联的一条或多条 trace 信息记录；将这些记录关联到源代码中一条或多条对应指令；其中每条记录包含 program counter 的值、thread block 标识符、以及 scheduler state——该 scheduler state 包含至少两个 bit 的 stall vector，每个 bit 代表 thread block 被 stall 的一个不同原因。

从属权利要求分组：

- **SIMT 限定**：claim 2、15、18 —— 记录关联的 thread block 为 SIMT 架构中的相关线程组（warp）。
- **事件缓冲与 replay**：claim 3（在内存中分配 event buffer 存储记录）；claim 4–5（launch 前启用 replay 机制；判定需重跑时回放捕获的 API stream 重新 launch workload）。
- **源代码关联**：claim 6–8（生成程序指令↔源码指令映射表；PC 值映射到程序指令后查表定位源码指令；映射通过计算 PC 值与程序在内存中基地址的偏移实现）；claim 19（driver 生成该映射表）。
- **trace cell 硬件限定**：claim 9（记录由耦合至 scheduler unit 的 trace cell 生成，scheduler unit 维护多个 thread block 的 thread state）；claim 10（trace cell 含暂存记录的 buffer 与采集逻辑）；claim 11（可编程变频采样）；claim 12–13（基于事件采样；事件包括 cache miss、function call、branch 指令执行至少之一）。
- **系统类**：claim 16（硬件并行处理单元 + 管理多个 thread block 的 scheduler unit + 生成记录的 trace cell）；claim 17（host processor 上运行开发平台执行编译/传送/launch/收集/关联）。

## 5. 与 TMU（Task Management Unit）的关系

本专利正文**明确使用 "task management unit (TMU)" 术语**，是 TMU 专利系列中对 TMU 定位描述最完整的 profiling 侧文献之一。

**1. 术语桥接——macro-scheduler = TMU**：正文（column 5，FIG. 1B 说明处）写道："In one embodiment, the thread blocks are assigned to an available core by a **macro-scheduler (i.e., task management unit)**, and a **micro-scheduler (i.e., scheduler unit)** manages the execution of up to 16 thread blocks substantially simultaneously for a given partition of a core." 这一括号等价表述确立了 NVIDIA 文献中两级调度的正式命名：TMU 负责 grid/task 级的宏观调度（core 分配），SM 内的 scheduler unit 310 负责 warp 级微观调度（每 micro-scheduler 每周期对每个 thread block 可发射至多 2 条指令）。

**2. TMU 215 在 PPU 200 中的位置与职责**（FIG. 2 说明，column 7）：

- Host interface unit 210 解码命令，转发给 TMU 215 或 memory interface 280 等单元；向 TMU 215 提供一个或多个 stream 的指针。
- TMU 215 选择 stream，将其组织为 **pending grid 池**——包含尚未被选中执行的新 grid，以及部分执行后被挂起（suspended）的 grid。
- **Work distribution unit 220** 耦合于 TMU 215 与 SM 250 之间，管理 **active grid 池**，选择并 dispatch active grid 至 SM 250。
- pending grid 一旦 eligible（无未决数据依赖）即由 TMU 215 转入 active 池；active grid 若被依赖阻塞则转回 pending 池；grid 完成后由 work distribution unit 220 从 active 池移除。
- **动态 grid 入口**：TMU 215 除接收来自 host interface unit 210 和 work distribution unit 220 的 grid 外，还接收 **SM 250 在 grid 执行过程中动态生成的 grid**（对应 CUDA Dynamic Parallelism 类 GPU 自发起工作负载），并入 pending grid 池。
- 图形管线场景中："the TMU 215 may configure one or more SMs 250 to execute a vertex shader program"，并可配置不同 SM 子集并发执行不同 shader（vertex/pixel shader 流水并行）。

**3. 对确认 TMU 芯片位置的价值**：本专利申请于 2014-06-04，其 PPU 200 实施例参数（15 SM、192 单精度核/SM、64 DPU、32 SFU、32 LSU、4 texture unit、GDDR5、每 warp 32 线程）与 Kepler GK110 世代高度吻合，可视作该世代前端工作分发路径的同期佐证：**host interface（命令前端）→ TMU 215（pending grid 池 / 宏观调度）→ work distribution unit 220（active grid 池 / dispatch）→ SM 250（scheduler unit 310 微观调度）**。TMU 同时是动态生成 grid 的汇聚点，说明其不仅处理 host 发起的 stream，也承接 GPU 内部递归/动态启动的工作。对本 TMU 专利系列而言，本文档证明：TMU 这一术语与两级调度架构在 2014 年前后已稳定写入 NVIDIA 专利文献，且 profiling/可观测性机制（trace cell 按 task identifier 过滤、PM counter 按 GPU context 统计）依赖 TMU 所建立的 task/grid 层级抽象。

## 7. 评价与启示

**技术贡献**：

1. **从"只采活动线程"到"全 warp 状态快照"**：传统 CPU trace（ETM/PMU）只记录当前发射线程；本专利直接从 scheduler unit 的 thread state table 周期性快照全部 warp（含 stalled），配合 stall vector 将 profiling 维度从"哪里热"扩展到"为何停"，这正是 Nsight/CUDA profiler 中 stall reason 分析的硬件基础。
2. **透明性与低扰动的工程化**：硬件采样 + FIFO 流式写出（可复用 PM streaming interface），不经中断、不改二进制；round-robin 单 warp 采样、事件/频率可编程、SM/block/task/时间窗过滤，系统性解决"每周期 120 条指令"量级的带宽矛盾。
3. **端到端源码闭环**：line table + relocation 基地址使 PC → 汇编 → PTX IR → HLSL/CUDA 源码行三级回溯成为可能，并支持跨 warp 的 stall 因果归因。
4. **权利要求策略**：独立权利要求刻意宽泛（仅要求 PC + thread block ID + ≥2 bit stall vector），从属项逐层加固 trace cell 结构与事件采样，覆盖方法/介质/系统三主体。

**对 TMU 研究的启示**：本专利证明 TMU 的 task/grid 抽象已成为 NVIDIA GPU 前端的标准组织方式（pending/active 双池 + 依赖挂起/恢复 + 动态 grid 注入），并且可观测性机制（按 task identifier 过滤 trace、PM counter 按 context 统计）构建在该抽象之上；"macro-scheduler (i.e., task management unit)" 的显式等价表述可作为 TMU 术语考据的关键引文。局限：正文对 TMU 的描述集中于 FIG. 2 段落，trace 机制本身作用于 SM partition 级，TMU 并非采集路径上的直接参与者；附图 Sheet 3 的 TMU 框图标记（215）OCR 提取不清，需对照 PDF 原件核对。
