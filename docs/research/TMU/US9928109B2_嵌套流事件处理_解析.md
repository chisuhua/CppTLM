摘要（ABSTRACT）：公开一种在并行处理子系统（如 GPU）中强制 cross stream dependencies（跨流依赖）的技术：将 waiting events 入队以建立跨流依赖，用 signaling events 向等待事件指示完成（原文 "indicated"，原文如此）。scheduler kernel 检查对应 stream 的 task status 数据结构，并更新 stream 内 tasks 与 events 的 dependency counts；当某 waiting event 的各 task dependency 被满足时，关联任务可执行。

## 2. 发明背景与待解决问题

传统 CPU+GPU 系统中，由 CPU 决定 GPU 执行哪些计算任务及顺序：

- **串行阻塞模型**：CPU 选定线程程序并命令 GPU 执行一组并行线程实例；GPU 须等全部线程实例完成、通知 CPU 并等待下一任务。该阻塞式、串行化操作使 GPU 资源间歇空闲，降低整体性能。
- **pushbuffer 改进**：顺序计算任务排入 pushbuffer，GPU 自行取走工作而不必等 CPU。对固定数据流水线任务有效；但**数据依赖型任务**仍保留 "GPU 结果 → CPU 任务管理 → CPU 再发射 GPU 任务" 的串行依赖。
- **流与跨流依赖**：多线程计算模型把工作组织成必须按定义顺序完成的有序 task streams；简单串行依赖可直接排入一个 pushbuffer 高效执行。但某些模型允许 **cross stream dependencies**——一个 stream 中的任务依赖两个或更多不同任务、可能跨两个以上不同 stream。此时由 **CPU 调度任务以避免死锁**，这种等待/调度在 CPU 与 GPU 执行间引入额外串行依赖，降低效率。

嵌套场景的进一步困难：

- 嵌套并行（nested parallelism）使线程组内的线程可独立 launch 一个或多个子线程组，并对子组执行 thread synchronization barriers；这要求 GPU 内部有完整的任务图/队列管理能力。
- CUDA 的 `cudaEventCreate()`、`cudaEventRecord()`、`cudaStreamWaitEvent()` 三个调用在先技术中由运行在 CPU 102 上的 GPU driver 管理与实现，由 CPU 显式调度任务执行以避免跨流依赖导致的死锁。

待解决问题：提供一种技术，使 GPU 以语义完备、高效、**无 CPU 介入**的方式处理含嵌套场景在内的 stream 事件与跨流依赖，即上述三个 CUDA 调用须有能在 parallel processing subsystem 112 内执行的对应实现。

## 3. 核心方案

### 3.1 整体架构

- **计算机系统 100（FIG. 1）**：CPU 102、system memory 104、device driver 103、memory bridge 105、communication path 106、I/O bridge 107、parallel processing subsystem 112、display device 110、system disk 114、switch 116、network adapter 118、add-in cards 120/121。CPU 102 将指向命令数据结构的指针写入 pushbuffer 以启动处理，并可经 device driver 103 为每个 pushbuffer 指定执行优先级。
- **PPU 202 前端结构（FIG. 2）**：I/O unit 205 经 communication path 113（如 PCIe）与主机通信；**host interface 206** 读取每个 pushbuffer，把其中命令流输出给 **front end 212**；PPU 202 还包括 **task/work unit 207**、processing cluster array 230（C 个 GPC 208）、crossbar unit 210、memory interface 214（D 个 partition unit 215 对应 DRAM 220）、本地 PP memory 204。
- **task/work unit 207（FIG. 3A）**：由 **task management unit (TMU) 300** 与 **work distribution unit 340** 组成。
  - TMU 300 按执行优先级组织待调度任务：每个优先级在 scheduler table 321 中保存指向 TMD 322 的指针链表（可存于 PP memory 204 或 system memory 104）；TMU 接收/存储任务的速率与调度速率解耦，可攒批后按优先级或 round-robin 等方式调度。
  - work distribution unit 340 含 task table 345，槽位被正在执行任务的 TMD 322 占据；无空槽时高优先级任务可驱逐低优先级任务，被驱逐任务重新入队待恢复。

- **GPC 208 / SM 310（FIG. 3B/3C）**：pipeline manager 305 向 SM 310 分发任务并控制 work distribution crossbar 330；SM 310 含 warp scheduler and instruction unit 312、instruction L1 cache 370、local register file 304、exec units 302、LSU 303、shared memory 306、L1 cache 320、unified address mapping unit 352、memory and cache interconnect 380；GPC 内另有 texture unit 315、MMU 328、L1.5 cache 335、preROP 325。（FIG. 3C 附图页 OCR 局部乱码，标记以正文为准。）

### 3.2 关键机制详解

**（a）嵌套深度与 TMDQ。**

- 层级执行图按 nesting depth 组织：CPU 线程深度 0；其 launch 的 grid 深度 1；grid 内线程再 launch 的 grid 深度 2，依此类推。一实施例中嵌套深度受 scheduling groups 数量限制，child 执行可在调度组内获得高于 parent 的优先级。
- 每个 stream 对应一个 **task metadata descriptor queue (TMDQ)**。FIG. 7：thread group 710（深度 0）含 TMDQ 712(0)–712(N)；TMDQ(0) 712(0) 指向第一 stream 的 task 720(0)，TMDQ(1) 712(1) 指向第二 stream 的 tasks 730(0)–730(1)，TMDQ(2) 712(2) 指向第三 stream 的 tasks 740(0)–740(2)。
- 同一 TMDQ 内任务严格顺序执行（task 730(0) 完成后 730(1) 才开始）；不同 TMDQ 之间无顺序依赖（task 730(1) 可先于、后于或并行于 task 740(1)）。
- 深度 1 执行图 780 由深度 0 的 task 740(1) launch，深度 2 执行图 790 由深度 1 任务 launch；嵌套图内全部任务及 launch 任务自身其余命令完成后，launch 任务的后续任务才可开始——从而在任意嵌套深度保持 stream 内顺序语义。
- context 定义：CPU 线程为与 CUDA context 关联的线程集合；GPU 线程为 CTA 或处于同一嵌套深度、同一 device 的线程集合；同 context 线程可创建与共享 TMDQ。

**（b）GPU 上 stream 的创建 / 销毁与 TMDQ 复用（FIG. 8）。**

- GPU 通常无法动态分配内存，故为每个可同时执行的 context **预分配固定数量 TMDQ**，grid 执行期间数量不可变；`cudaStreamCreate()` 返回指向预分配 TMDQ 的整型索引，无需动态分配；stream 内任务全部完成后 `cudaStreamDestroy()` 因无可归还内存而直接返回。
- FIG. 8 实施例（thread group 810，深度 1，执行图 880/890 位于深度 2/3）：当所有 TMDQ 812 已被占用而线程又想创建新 stream 875 时，新 stream 的 tasks 860 直接排入已被 stream 870 使用的 TMDQ(0) 812(0)。
- 交替入队（860(0)→820(1)→860(2)…）引入不必要的依赖、性能下降，但两个独立 stream 各自的顺序性（stream 870 的 tasks 820、stream 875 的 tasks 860）得到正确保持。

**（c）跨流依赖的 WE/SE 图变换（FIG. 9A/9B）。**

- FIG. 9A 层级执行图 900：tasks 910/920/930/940 分属四个 stream；task B 910(1) 依赖 task A 910(0) 与 task D 920(0)（跨流依赖）；task G 930(1) 跨流依赖 B 910(1)、E 920(1)、F 930(0)；task J 940(1) 依赖 B 910(1)。
- FIG. 9B 等价图 902 引入两个新构造：**wait event (WE)**——阻塞直至所有输入条件满足；**signaling/firing event (SE)**——被触发时产生一个或多个事件。
- 依赖 B 对 A、D 用 WE 0 950(0) 与 SE 0 952(0) 表示；依赖 G 用 WE 2(1) 950(2) 与 WE 1 950(1) 表示。WE 0 950(0) 等待 task A 910(0) 完成并等待 SE 0 952(0) 触发；因 SE 0 952(0) 依赖 task D 920(0) 完成，B 对 A 与 D 的跨流依赖被正确强制。
- 等价图 900 与 902 实现完全相同的执行顺序；902 **无需锁**，可在并行处理子系统内高效实现且无需 CPU 102 介入。

**（d）event 内存管理。**

- GPU 仅在空闲时才能分配/释放内存，故设**预分配 event 结构池**（signal/wait 复用，用完归还 free pool），由 sub-allocator 管理：分配成功返回结构引用。
- 分配失败（out-of-memory）时，**把所有新工作串行化到单一 stream**：对含事件的嵌套 stream 安全、语义等价、结果正确，仅性能可能降低；销毁事件即归还 free pool。
- `cudaEventRecord()` 将 SE 排入 stream；若同一 event 已被 record，则分配新 event 并跟踪为 most recent event record。

**（e）事件语义与依赖计数。**

- 每个 SE 维护等待它的 WE 列表（初始为空）；SE 触发（其前方无 stream 工作）时遍历该列表，标记 SE 已 fire 并通知各 WE；一个 WE 被通知即满足其一项或多项依赖，使对应 stream 得以推进。
- `cudaStreamWaitEvent()` 将 WE 排入目标 stream：WE 先查找被引用 SE 的最近一次 `cudaEventRecord()`；若无物可等则 WE 直接完成；找到后 **WE 被原子地加入相应 SE 的 waiting list**；WE 加入与 SE 同一 stream 时视为 null operation。
- 每个 WE 带 **dependency count**（0/1/2）：0 表示已 fire；1 表示等一个 task 或 event；2 表示同时等一个 SE 与本 stream 内的另一 task/event。计数以原子方式递减，保证只有一个 scheduler kernel 试图调度 stream 的下一任务或处理 WE 依赖列表；计数归零时可遍历其 StreamNext 指针并递减相关依赖计数。
- SE 触发时须遍历整个 EventWaitingList 递减每个 WE 计数；对无剩余依赖的事件逐一遍历其 stream next 指针，SE 自身的 streamNext 亦须遍历；为避免维护遍历状态栈，树遍历**扁平化为非递归**技术（线程本地栈空间受限的 PPU 上尤有意义）。

**（f）任务入队 / 完成的无锁衔接（FIG. 10，Table 8）。**

- thread group context 1020 为每个 TMDQ 保存 **last task pointer 1040**（PB(0)–PB(N) 各一），并有 **work counter 1050**。
- 入队（Table 8）：`FormerStreamEnd = atomicExchange(&StreamEnd, NewTask)`；若 FormerStreamEnd 非零则置 `FormerStreamEnd->StreamNext = NewTask`；否则 TMDQ 为空、新任务立即 launch。整个操作置于临界区内，避免线程已投递任务却被换出、尚未 launch 而等待其完成所致的死锁。
- 完成：scheduler 读该 TMDQ 的 last task pointer；若不指向完成任务则令下一任务执行；若指向完成任务则执行 `currentEnd = atomicCAS(&StreamEnd, finishedTask, NULL)`。
- currentEnd 等于 finishedTask 表示 stream 全部任务完成且无新任务；否则说明新任务已 launch、context 已更新，scheduler 读完成任务的 StreamNext：非零则令其执行；为 NULL 则新任务状态尚未写入，scheduler **监视 StreamNext 直至其变为新任务指针**再令其执行。

**（g）scheduler kernel 与 restoration kernel（嵌套执行支撑，FIG. 4/5/6 及 Table 1–7）。**

- 子 grid 完成后触发调度机制：一实施例中 scheduler kernel 作为 grid 完成时执行的 **"AtExit" 任务**被调用，查明已完成与未完成工作并决定下一步调度（如重新 launch 父 CTA foo()）。
- 父 CTA 因 `cudaThreadSynchronize()` 挂起时执行状态存入 continuation state buffer 642（可驻留 PP memory 204/system memory 104），CTA 退出并释放 SM 310 资源以避免死锁、保证 forward computational progress。
- 恢复由作为 **"AtEntry" 任务**的 restoration kernel 完成：从 continuation state buffer 恢复执行状态，invalidate SM 缓存以排除陈旧状态，然后跳转至 `cudaThreadSynchronize()` 调用之后的指令继续执行。
- 内存一致性：子 launch 前执行系统内存屏障 `membar.sys` 冲刷父线程的全部待写数据；子 launch 经 `cudaRTLaunch()` 向 MMU 328 发送 **posted compare and swap (PCAS)** 消息（阻塞式 posted 同步操作，原子比较并按条件覆写内存）实现向 scheduler 的入队。
- 语言构造：child launch 构造 "A<<<B>>>C"（子程序名 A、grid launch 参数 B、输入参数 C，见 Table 1）；嵌套使条件/递归等复杂算法高效映射到 GPU（Table 5–7 展示多重条件嵌套循环改写为条件性 child launch）。层级执行图可组合（composable）：只有 parent 与其全部 child 完成，parent 才算完成（FIG. 4 中 task 420(1) 须等 tasks 430(0)–430(2) 全部完成；正文 "task 20 ( 0 )" 疑为 "task 420 ( 0 )" 的提取错误）。

**（h）方法 1200（FIG. 12；附图页 OCR 局部乱码，步骤号以正文为准）。** 由 scheduler kernel 执行，处理 TMDQ 队首条目：

- **1210** 取下一条目（task metadata descriptor / waiting event descriptor / signaling event descriptor）。
- **1220** 若是任务 → **1222** 令其在 SM 310 执行。
- 否则 **1230** 判断是否 WE：是则 **1232**——若其前驱对应任务已执行，则递减该 WE 的 dependency count（WE 同时依赖任务与 SE 时初始化为 2）。
- **1234** 计数为 0 → **1236** 从 TMDQ 移除该 WE，回到 1210；计数非 0 → 结束 1290。
- 若 1230 判定非 WE，则 **1240** 判断是否 SE：是则 **1242** fire/执行该 SE，并递减与其 event ID 关联的依赖计数——该计数来自由历次 `cudaStreamWaitEvent()` 生成的关联事件列表（signal event status 1122 经 event next 1154 链接的 wait event status 1124 链表，递减各条目的 dependency count 1164）；递减可级联使更多任务可执行或触发更多更新。
- **1244** 归遍历依赖节点的 StreamNext 指针逐节点更新状态（可递归执行方法 1200，亦可扁平化非递归遍历）。
- **1246** 从 TMDQ 移除 SE 条目；**1290** 结束。
- 三种可入队条目（task status 1120 / signal event status 1122 / wait event status 1124）：**任务启动计算，事件强制计算顺序**。

**（i）状态数据结构（FIG. 10/11A–11C）。**

- task status 1120：task ID 1140（指向关联任务）、stream next 1142（指向 TMDQ 中下一任务；若为队尾则为 null）、thread group context ID 1144（任务完成时 scheduler 据此找到 thread group context 1020，执行更新 work counter、关闭 TMDQ、关闭 context 等收尾步骤）。
- signal event status 1122：event ID 1150（唯一标识可被不同任务依赖的事件）、stream next 1152（与 1142 语义相同）、event next 1154（指向下一依赖事件）。
- wait event status 1124：event ID 1160（语义同 1150）、stream next 1162（语义同 1142）、dep. count 1164。

## 5. 与 TMU（Task Management Unit）的关系

本专利是 NVIDIA TMU 专利族中处理 **stream/event 依赖语义**的一环，正文多处直接涉及 TMU、front end 与 work distribution：

1. **TMU 300 明确出现于 FIG. 3A 及正文**："The task / work unit 207 includes a task management unit 300 and the work distribution unit 340." TMU 300 按优先级在 scheduler table 321 维护 TMD 322 指针链表，接收与调度速率解耦，可攒批后按优先级或 round-robin 调度；child task 由 processing cluster array 230 直接送回 task/work unit 207 动态调度。
2. **FIG. 6 实施例中 scheduler 610 即 TMU**："In one embodiment, scheduler 610 comprises task management unit 300 of FIG. 3A, distributor 620 comprises work distribution unit 340." 即嵌套 kernel 执行子系统的调度器就是 TMU，负责接收 GTMD 队列 650（应用工作）/652（嵌套工作）、QTMD 654（scheduler kernel）/656（restoration kernel），并按保证前向进度的优先级策略调度。
3. **front end 212 与 work distribution**："GPCs 208 receive processing tasks to be executed from a work distribution unit within a task / work unit 207"；命令流中携带编码为 TMD 的任务指针，由 front end 212 从 host interface 206 接收后转交 task/work unit 207；"The front end 212 schedules each processing task for execution"；special registers 亦经 front end 212 从 device driver 103 接收的命令初始化。
4. **分工定位**：TMU 300 / work distribution unit 340 负责 grid/TMD 级硬件调度与 GPC 分发；运行在 SM 上的 **scheduler kernel（软件调度层）**在 TMDQ 层面处理 stream 内与跨流的事件依赖，任务完成后按方法 1200 决定流内下一任务。二者配合实现正文所列优点——GPU 无 CPU 介入地正确高效强制跨流执行顺序，并支撑层级执行图的可组合性（子 kernel 对外表现为父 kernel 的一部分）。

## 7. 评价与启示

1. **CUDA stream/event 硬件化的关键拼图**：本专利把 `cudaEventCreate/cudaEventRecord/cudaStreamWaitEvent` 从 CPU 驱动职责下沉为 GPU 内部（scheduler kernel + TMDQ 状态结构）可执行的机制，与 dynamic parallelism（child launch、continuation/restoration kernel、AtExit/AtEntry 任务）配套，构成 "GPU 自调度" 语义闭环；正文明确宣称的优点即无 CPU 介入地强制跨流执行顺序、层级执行图可组合。
2. **无锁依赖表示**：以 dependency count + StreamNext/EventNext 链 + 原子 exchange/CAS 替代锁来解析依赖；OOM 时退化为单 stream 串行化以保证正确性——体现 "正确性优先、性能次之" 的优雅降级；也解释了实现上规避 GPU 动态内存分配的约束（预分配 TMDQ/event 池、`cudaStreamCreate` 仅返回索引）。
3. **软硬件分层清晰**：TMU 300 / work distribution unit 340 处理 TMD/grid 级硬件调度；运行在 SM 上的 scheduler kernel 在 stream 级处理事件依赖，方法 1200 是该软件层的算法表达；claim 23 将其落到 streaming multiprocessor 上执行。
4. **对逆向理解现代 GPU 前端有价值**：TMDQ、last task pointer 1040、work counter 1050、WE/SE 状态结构（FIG. 10/11）给出 stream 队列在 GPU 内存中的具体布局线索；"spin 监视 StreamNext 由 NULL 变非 NULL"、临界区内 atomicExchange 防死锁等细节揭示了投递—链接竞态的处理方式；可与同族嵌套执行专利对照，还原 Kepler 时代以来 CUDA stream 硬件实现的演进脉络。
5. **局限与文本质量**：独立权利要求仅聚焦 "取 SE—执行—递减 WE 计数—出队" 的最小流程，未把 TMDQ 预分配、event 池、spin-wait 等实现细节纳入保护范围；附图 OCR 多处乱码（FIG. 3C、FIG. 12 流程图标注、首页顶部），相关标记均以正文记载核对；摘要原文 "indicated" 为原文用词，未做改写。
