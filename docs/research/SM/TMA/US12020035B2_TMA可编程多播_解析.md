## 2. 发明背景与待解决问题

**strong scaling 诉求（FIG. 1A–1C）**：用户要的是单一应用在不增大 workload 的前提下随处理器数量提速（strong scaling），而非 weak scaling 式"每人多干活"。strong scaling 使每 SM 的 tile 变小，而小 tile（如 64×64）对 L2→SM 带宽的需求随 SM 数/L2 slice 数增加而陡增（FIG. 1D）。靠堆处理器、堆 L2 slice、堆每周期传输块数或提频来满足，会遭遇线数增加、crossbar 成本随端口数二次escalation、额外 RAM bank 等物理困难。

**数据取回冗余（FIG. 1E，视觉核对）**：4×1 向量 A × 1×4 向量 B 的 GEMM 中，结果矩阵第一行每个单元都要用 A1、第一列每个单元都要用 B1；"In previous NVidia GPUs, the A1 element was separately fetched from the memory (typically from the L2 cache) for calculating each element in the first row"。同一元素被重复取回 = 内存带宽、crossbar（NoC）带宽与功耗三重浪费。

**需求**：利用用算法冗余，让一份数据只从 L2 读一次，再同时交付给多个 CTA/SM——即 programmatic multicast。

## 3. 核心方案

### 3.1 多播引擎架构：LRC 跟踪 + 分叉点复制（FIG. 2A/2B）

- **leader/follower 模型**：CGA（cluster）内某 CTA 的 leader thread（source SM 204）代表多个 SM 上的 follower 生成 multicast request packet 224，经 request crossbar 208 发往 **L2 Request Coalescer (LRC) 212**；请求方可以完全不在接收方名单内（纯"代理取数"）。
- **L2 对多播无感知**：LRC 的 L2 Req Generator 238 把多播信息（接收方列表等）存入 **tracking circuitry and metadata storage 222**，只发出普通 L2 request 226；L2 slice 220 按单播请求处理并返回 unicast response 228；Mcast Rsp Generator 240 将响应与跟踪元数据匹配，重新附上接收方列表，生成 **LRC multicast response packet 230**。
- **单包传输、分叉点复制**：230 在 response crossbar 210 上以单一包沿所有接收方的公共路径传输，仅在路径分叉点（separation point）按需复制为 232/234；若接收 SM 不在同一 TPC，分叉点更早。
- **ack 回路**：非请求方接收 SM 206 向 source SM 204 回 acknowledgment 236（经 request crossbar 208、interconnect crossbar 209、response crossbar 210）。
- FIG. 2B 视觉核对与说明书一致：LRC 212 = L2 Req Generator 238 + Tracking Circuitry and Metadata Storage 222 + Mcast Rsp Generator 240，端口 Mcast Req / L2 Req / L2 Rsp / Mcast Rsp。

### 3.2 目的掩码 / CTA mask 与随包元数据

- **指令格式**（TMA 上的 multicast load）：`UTMALDG.dim{.IM2COL}{.MULTICAST} [URb], [URa], URc`。{URb,URb+1} 位域：DataOffset[23:0]、CTA_ID-Data[31:24]、BarrierOffset[55:32]、CTA_ID-Barrier[63:56]；URa = tensor descriptor 的全局地址；URc[31:16] = **16-bit Multicast CTA_ID mask**（每位对应一个 CTA ID），[15:0] = im2col offsets。
- CGA 最多可含 32 个 CTA，但**仅 [0:15] 范围的前 16 个 CTA 可参与 multicast**。
- 目的共享内存偏移对所有目的 CTA 对称（same offset）；同步实体以 barrier offset 表示，同样对称。
- **随包元数据**（接收 SM 本地无这些状态，必须随请求走）：SM ID mask（source SM 依映射表由 CTA ID 换算）、CGA ID、Data SMEM Offset、Barrier Address Offset、Source SM ID（供回 ack）、ACK phase ID（MEMBAR 协议两相位之一）、实现特定参数（swizzle、z-fill 等 TMA 结果处理参数）。
- **接收侧落点**：每个 SM 维护 {CGA-ID, CTA-ID-in-CGA}→{SMEM Base Address} 表；数据写入 {SMEM Base, SMEM Offset}，写前/写中可做 swizzle、z-fill。

### 3.3 与 TMA 描述符的配合

- 新 load 操作建立在 CGA 的 launch/同步/distributed memory 能力之上，底层内存访问服务由 **TMA** 提供（姊妹案 17/691,276 / 17/691,422）；亦可扩展到非 TMA 指令如 LDGSTS（16/712,083）。
- FIG. 11A 明确 GPC 1050 内**每个 SM 1140 都耦合一个 tensor memory access unit**——multicast 是 TMA 指令族的多播变体，源地址/形状由 tensor descriptor 给出，im2col 模式可与 multicast 叠加（URc 低 16 位携带最多三个坐标偏移）。

### 3.4 事务计数 / 到达通知 / MEMBAR

- 接收 SM 按**收到字节数**递增 barrier 的 arrive count（barrier 体系见 SYNCS 姊妹案 17/691,296），随后向 Source SM ID 发 Ack；barrier 在"全部数据到达 + 期望字节数被编程完成"时 clear，期望字节数可由 sender 或 receiver 在数据返回前/中/后编程——数据到达与同步融合为一条硬件路径。
- **计数器布局不对称**：sender SM 只维护总数计数器（sync/async 两类 × 两相位），不按 receiver 细分；receiver SM 则对每个潜在 source SM 各设一组计数器。多个 ack 可合并为 count 发送（count 够大且总线空闲时）。
- 错误发 NACK（out of range、CTA already exited、offset/barrier 越界等）；ack/nack 保证 context switch、CGA 退出、trap 处理前无 in-flight 事务。
- MEMBAR.CTA/GPU 不等异步多播；**MEMBAR.ASYNC** 显式等待当前相位全部 Ack 后翻转相位，使新多播可与旧多播的完成等待重叠。

### 3.5 传输硬件：multidrop 与多播信用（FIG. 7–9B）

- FIG. 7：GPU 700 含两个 μGPU 702；crossbar 706 由 6 primary + 6 secondary switch 构成，接 6 个 FBP × 8 slice × 2 port；GPC 708 内 CPC 710（物理设计优化的 TPC 集合），每 CPC 两个 GPCARB 714、每 GPC 24 输入端口；multidrop 输出到各 CPC 仲裁器。
- FIG. 8：crossbar 将包 multidrop 到单线 802，GXC 804 内各 GXC_CPC 806 用包的 **cpc_id bitmask** 过滤，命中者经 GNIC 808 转发到 GPCARB。
- FIG. 9A：crossbar multidrop switch 900（input queue 910、creditor 904、vc credit logic 912、dispatcher 906 用 NSLIP/WFA、switch fabric 908）；**multicast 包整体取信用——任一目的无信用即整包 stall**。
- FIG. 9B（视觉核对）：GPCARB multicast switch 920 = input queue 922 + creditor 924（dst-vc unicast creditor、vc multicast creditor 934、vc credit manager 932）+ dispatcher 926（unicast frontfill/backfill NSLIP/WFA、multicast prefill 1:M FPLRU、starvation breaking mechanism 936 侧的 pc credit manager）+ 2D fabric 928 + multicast grant 930；**multicast creditor 优先于 unicast creditor**，因其"全有才算有"的信用特性更易阻塞。

### 3.6 带宽与能耗收益

L2 只读一次、响应在公共路径上以单包传输、仅在分叉点复制，直接削减 L2 带宽、NoC 带宽与功耗；使 64×64 级小 tile 的 strong scaling 不必伴随 crossbar 端口二次扩容。受益典型：GEMM/GEMM-like、卷积核。

## 5. 与专题主题的关系

- **Hopper TMA multicast 的硬件原文**：PTX 层面对应 `cp.async.bulk.tensor` 的 multicast 变体（shared::cluster / multicast::cluster）及其 ctaMask 操作数（专题线索；专利文本给出底层硬件指令 UTMALDG…MULTICAST 与 16-bit CTA mask）。FIG. 3 的 "Grid with Clusters" 即 thread block cluster 编程模型。
- **cluster/DSMEM 场景的数据侧支柱**：multicast 与 CGA 共调度（姊妹案 215）、跨 SM 共享内存（DSMEM，姊妹案 189）、字节计数 barrier（SYNCS，姊妹案 242）构成 Hopper cluster 三件套；接收方写入的正是对方 CTA 的 shared memory，barrier 即 cluster 级 mbarrier 的硬件实现。
- **GEMM 权重/A-B 矩阵广播**：FIG. 1E 场景下 A1/B1 一次读取交付最多 16 个 CTA，L2 流量近似降为 1/16，是 cluster 切分 GEMM tile 后共享操作数的标准路径。
- **与 Blackwell tcgen05 的潜在关联（推断，文本未载明）**：Blackwell 的 cluster 级操作数供数（双 SM 协作 GEMM/UMMA）复用同一条"LRC 单包 + 分叉复制 + DSMEM 落点"数据通路；"请求方可不在接收名单内"与 16-bit mask 为 producer/consumer 解耦的供数模式留下硬件基础。本案申请日早于 Blackwell 公开，文本不含 tcgen05 术语。

## 7. 评价与启示

**设计精髓**：把多播状态完全推出 L2、集中于 LRC 跟踪结构 222，L2 slice 逻辑零改动即可获得感知的"一次读取、多处交付"；分叉点复制使 NoC 上多播流量逼近理论最小；"请求方≠接收方"+ 元数据随包，把取数与用数彻底解耦。

**可编程性**：目的集合是指令级 16-bit mask（软件定义），而 CGA 硬件共调度保证接收方在飞，硬件无需猜测存活性；字节计数 arrive 把数据到达与 mbarrier 同步熔为一条通路，是 Hopper "异步复制 + 屏障消费" 编程范式的硬件根。

**局限（基于文本）**：multicast 仅限 CGA 前 16 个 CTA（CGA 上限 32）；multidrop/multicast 整包信用（FIG. 9A/9B）使任一接收方缺信用即整包 stall，存在尾延迟；接收域受 CGA 共调度约束（通常同 GPC）；sender 总数计数器无法分辨落后接收方。

**谱系位置**：与 US9594599B1（WDU 按使能 SM 比例分发，需求侧均衡）互为补集——本案解决交付侧带宽；Tenstorrent/Qualcomm 的审查员引用表明 NoC 级 multicast 已成行业参照。对 17_Blackwell_SM_Internals 专题，本案是理解 Hopper/Blackwell cluster 级操作数供数（含 tcgen05 multicast 推断）与 LRC/GPCARB/cpc_id bitmask 等 NoC 微架构编号的第一手文献。
