## 1. 这件专利在 NVIDIA 术语史上的地位

**"Operand Collector" 这个词，NVIDIA 在专利标题层面只用过这一次**。这件 US7834881B2 是该术语的**源头专利**，也是本次调研中唯一一件把该结构写成"标题级"公开文献的 NVIDIA 专利。

它与另外两件的关系：

- **US8555035B1**（2010 申请）—— NVIDIA 内部的**对立路线**：去掉 crossbar 与 staging register，改由编译器保证 conflict-free + aligned。该专利的 "Other Publications" 栏**直接引用了本件的先行公开 `US 2008/0109611 A1 (5/2008 Liu et al)`**，证明这是针对本件提出的反向方案。
- **US8639882B2**（2011 申请）—— 在本件基础上把 Collector Unit 升级为带 **cache table** 的复用缓存。

## 2. 摘要（逐字引用）

> An apparatus and method for simulating a multi-ported memory using lower port count memories as banks. A collector units gather source operands from the banks as needed to process program instructions. The collector units also gather constants that are used as operands. When all of the source operands needed to process a program instruction have been gathered, a collector unit outputs the source operands to an execution unit while avoiding writeback conflicts to registers specified by the program instruction that may be accessed by other execution units.

**三个要点**：

1. **目标是用低端口数存储器"模拟"多端口存储器**——不是为了省面积而砍功能，而是为了**在面积/功耗与端口数之间取折中**。
2. **Collector Unit 同时收集"源操作数"与"常量"**（常量来自 bank 之外的常量缓存）。
3. **收集齐了才输出给执行单元**，且输出时要**避开写回冲突**（目的寄存器可能正被其它执行单元占用）。

## 3. 发明动机（BACKGROUND OF THE INVENTION）

原文（逐字）：

> Conventionally, a register file includes a multi-ported memory so that two or more locations, each location storing an operand, may be read in a single clock cycle. Therefore, all of the operands needed for at least one program instruction may be acquired and output to an execution unit in a single clock cycle.
>
> Compared with a single ported memory, a multi-ported memory requires more die area and uses more power. However, unlike a multi-ported memory, only a single location may be read in each clock cycle. Therefore, **two or more clock cycles are needed to acquire the operands needed to execute one program instruction**, reducing performance compared with a multi-ported memory.

**这段话是整个 OC 设计的"原罪与补偿"**：

| 方案 | 面积/功耗 | 收集延迟 |
|------|----------|---------|
| 真多端口 RF（4R4W） | 高 | 1 拍拿齐所有操作数 |
| 单端口 RF + OC（本件） | 低 | **1 拍只能拿 1 个操作数**（每 bank） |

这个"延迟可变"的代价是**贯穿 NVIDIA 后续二十年架构演化的主线矛盾**——详见 [arXiv:2503.20481 解析](arXiv2503.20481_现代NVIDIA核心无操作数收集器_解析.md)。

## 4. 结构解析

### 4.1 SM 层级定位（FIG. 2）

```
Programmable Graphics Processing Pipeline 150
└── Streaming Multiprocessor 200
    ├── Thread Control Unit 220
    ├── Instruction Unit 230          ← 按 bank 分组 round-robin 选指令
    ├── Register Address Unit 240     ← 发读/写请求
    ├── Register File Unit 250        ← ★ 本件主体
    └── Execution Unit(s) 270
```

关键流程（说明书原文）：

> Register Address Unit 240 outputs requests for each program instruction. Examples of requests include a read request for a specific operand or a Write request for a specific operand. In one embodiment ... for a load instruction (LD), one (1) Write request is output ... for a multiply-accumulate (MAD) instruction, **3 read requests (one for each source operand) and 1 Write request** are output.

> Register File Unit 250 schedules processing of the requests, **avoiding writeback conflicts and cycle based conflicts**. In some embodiments ... **uses a scoreboard unit** to track the status of operand writes to registers.

> **注**：scoreboard（数据冒险）与 bank arbitration（端口/周期冲突）在专利里就是**两个并列机制**——这与 GPGPU-Sim 中 Scoreboard 与 OC 互不引用的分层完全一致（见 [gpgpu-sim 剖析](gpgpu-sim_操作数收集器实现剖析.md) §3）。

### 4.2 Register File Unit 250 内部（FIG. 3）★核心

```
        Register File Unit 250
 ┌──────────────────────────────────────────────┐
 │  Bank Request        Bank 320   Bank 320     │
 │  Arbitration Unit 310  (1R + 1W)  (1R + 1W)  │
 │        │                │            │       │
 │        └── Selector 325 ┘            │       │
 │                     │                 │       │
 │              Collector Unit 330       │       │
 │                     │                 │       │
 │              Execution Unit 365       │       │
 └──────────────────────────────────────────────┘
```

原文（逐字）：

> Each Bank 320 includes a **read request port** for receiving requests from a Bank Request Arbitration Unit 310. Each Bank 320 also includes a **Write request port** for receiving Write requests from Execution Unit(s) 270 ... Therefore, **2 banks of lower port count memories (1 Write port and 1 read port) are used to simulate a multi-port memory with 2 Write ports and 2 read ports.**

> Each Bank Request Arbitration Unit 310 also arbitrates between the different Collector Units 330 and **outputs one request per clock cycle** to the Bank 320 coupled to the Bank Request Arbitration Unit 310.

> **During a clock cycle, each Bank 320 may output an operand specified by read request to a corresponding Collector Unit 330 via a Selector 325. Therefore, when a program instruction specifies 3 operands for source data, at least 3 clock cycles are needed to gather the operands when they reside in the same Bank 320.**

> Each Collector Unit 330 may also gather source data, such as **constants and immediate data that are stored in registers outside of Banks 320** (not shown). Selectors 325 receive source data not stored in Banks 320 from inputs (not shown). **When all of the operands are gathered by a Collector Unit 330, the program instruction is ready to be dispatched.**

> When all of the operands for a program instruction have been gathered by a Collector Unit 330, the program instruction and operands are output by the Collector Unit 330 to the Execution Unit 365 coupled to the Collector Unit 330 for processing.

**Collector Unit 330 的三个职责**（从原文归纳）：

1. **接收与筛选**：从 Register Address Unit 240 接收请求 + 指令，判断该指令是否属于与自己耦合的 Execution Unit 365；是则接受；
2. **汇集**：把来自不同 bank 的操作数 + 常量汇聚到一起，全部到齐才"ready"；
3. **输出与避冲突**：把指令 + 操作数交给耦合的执行单元，且要避开写回冲突。

**多执行单元的分配策略**（原文）：

> In some embodiments of the present invention, each Execution Unit 365 is identical and a **priority scheme** is used to determine which Execution Unit 365 will execute the program instruction. Alternative embodiments ... assign the instruction to the **least-loaded** Execution Unit 365. In some embodiments ... two or more Collector Units 330 are coupled to a single Execution Unit 365 and a priority scheme is used to choose which of the two or more Collector Units outputs operands to the single Execution Unit 365.

### 4.3 加入 Crossbar 的变体（FIG. 5）

```
Bank 320 × N ──► Crossbar 525 ──► Collector Unit 330 × N ──► Dispatcher Unit 540 ──► Execution Unit B 575
                              └──► Collector Unit 330（直连）──► Execution Unit A 565
```

原文（逐字）：

> **Crossbar 525 is configured such that an operand output from any Bank 320 may be routed to the input of any Collector Unit 330.** Therefore, all of the operands specified by a program instruction may be collected by a single Collector Unit 330. When Crossbar 525 is used thread scheduling and register allocation (fat or thin) may proceed more efficiently than when the number of Banks 320 is equal to the total number of Collector Units 330.

> A **Dispatcher Unit 540** is coupled between a set of Collector Units 330 and an Execution Unit B 575. Dispatcher Unit 540 may receive program instructions and corresponding operands ... from each Collector Unit 330 within the set, therefore **Dispatcher Unit 540 arbitrates between the Collector Units 330 within the set**. In some embodiments ... arbitrates in a **round-robin** fashion. In other embodiments ... each Collector Unit 330 within the set has a corresponding **priority** and Dispatcher Unit 540 accepts inputs ... based on the priority. For example, one Collector Unit 330 may have higher priority than the other Collector Units 330 and **Dispatcher Unit 540 will always accept inputs from the one Collector Unit 330 if a program instruction and operands are available**.

> A single Collector Unit 330 is directly coupled to an Execution Unit A 565. Execution Unit A 565 may be configured to execute specific instructions that Execution Unit B 575 is not configured to execute.

**这个变体是理解"OC 是可配置的"的关键**：Collector Unit 与 Execution Unit 之间是 **1:1 直连（专用）** 或 **N:1 + Dispatcher 仲裁（共享）** 两种形态；GPGPU-Sim 的 `opndcoll_rfu_t` 正是这两种形态的混合（`num_units_*` 专用 set + `num_units_gen` 通用 set + `dispatch_unit_t` 仲裁）。

### 4.4 寄存器分配：thin / fat / phase（FIG. 4A–4F）★降低 bank 冲突的分配期手段

这是本件最有工程价值、也最被学术界低估的部分。OC 在运行时被动挨 bank 冲突；本件同时给出了一套**分配期主动规避**的方法。

| 策略 | 做法 | 图 |
|------|------|-----|
| **thin allocation** | 一个线程的全部寄存器分在**同一个 bank** | FIG. 4A |
| **fat allocation** | 一个线程的寄存器分在**多个 bank**（每 bank 一个操作数） | FIG. 4B |
| **fat + 上下反向填充** | fat 从 bank 顶部向下分配、thin 从底部向上分配，提高同型打包效率 | FIG. 4D |
| **顺序分配（sequential）** | fat 分配时操作数按顺序分配，操作数 400A 在 Bank 0、400B 也在 Bank 0 → **可能 bank 冲突** | FIG. 4E |
| **phase value 错位** | 用相位值把同指令的多个操作数**错开到不同 bank** | FIG. 4F |

原文（逐字，FIG. 4F 段）：

> A **phase value** may be used during the register assignment process so that threads processing the same program instruction **will not have their corresponding operands specified by the program instruction assigned to registers that are in the same bank**.

> In an alternate embodiment ... With 4 Banks, **the lower two bits of an assigned register number may be exclusive ORed (XOR) with a unique phase value** corresponding to the thread that the register is allocated to. An alternative method ... is to take **modulo the number of Banks of the sum of the assigned register number and the phase value**.

> When a fat allocation is used for registers, it is possible that two or more operands needed to process a program instruction will be assigned to registers in two or more different banks. For example if a program instruction for thread A specifies Operands 414A and 415A, **read requests will be queued in two different Request Queues 310** ... LikeWise, Operand 414A will be output to the Collector Unit 330 coupled to Bank 0 and Operand 415A will be output to the Collector Unit 330 coupled to Bank 1. **Since a single Collector Unit 330 gathers the operands for each program instruction, a mechanism is used to permit the transfer of operands between the different banks and Collector Units 330.**

**注意最后一段**：这就是 FIG. 5 的 Crossbar 525 存在的理由——**一条指令的 3 个操作数天然会落在不同 bank**（fat 分配下），所以 bank→collector 是多对多的，必须有 crossbar 或 selector 网络。

### 4.5 读请求仲裁方法（FIG. 8）★对应权项 1

SUMMARY OF THE INVENTION 中的方法描述（逐字）：

> Various embodiments of a **method of the invention for arbitrating read requests for a memory bank** include:
> - receiving a first read request for a first operand that is stored in the memory bank and specified by a first program instruction to be executed by a first execution pipeline,
> - receiving a second read request for a second operand that is stored in the memory bank and specified by a second program instruction to be executed by the first execution pipeline,
> - **selecting the first read request** for output to the memory bank,
> - determining whether a **cache miss has occurred for a constant read request** associated with the first program instruction,
> - **discarding the first read request when a constant read cache miss has occurred** for the first program instruction, and
> - **selecting the second read request** for output to the memory bank when a constant read cache miss has occurred for the first program instruction.

**这条方法的核心是一次"投机 + 回退"**：

```
bank 上有两条读请求（A、B）争用
  │
  ├─ 选 A（先到先得）
  ├─ A 附带常量读 → 查常量缓存
  │    ├─ 命中 → A 正常读，A 的操作数就位
  │    └─ 未命中 → 丢弃 A 的读请求（让出 bank 端口！）改选 B
  │                → 等常量取回后，再补读 A
  └─ 结果：B 先拿到数据，A 延后 —— 用一次重排避免常量 cache stall 卡住整个 bank
```

FIG. 8 流程图元素（附图 OCR 提取）：`Receive a program instruction 800` → `Cache Read request? 805` → `SFU request? 810` / `MAD request? 815` → `Cache miss? 820` → `Another bank? 825` → `Discard the selected request 840` / `Output the read request 830`。

**跨线程常量索引不一致**的处理：原文在 FIG. 8 段落的说明中指出，当同一指令内不同线程的常量索引不同，常量读必须**串行化**为多次读——这是 SIMT 语义下 OC 必须处理的特例。

### 4.6 派发方法（FIG. 9A / 9B）★对应另一条方法权项

SUMMARY OF THE INVENTION 中的方法描述（逐字）：

> Various embodiments of a **method of the invention for dispatching program instructions and operands for execution** include:
> - selecting a first program instruction and operands for execution by a first execution unit from a set of eligible program instructions to produce a value for storage in a first register that is specified by a first destination operand,
> - **determining if a writeback conflict exists** for the first register and any destination operands that are produced by a second execution unit **that has priority over the first execution unit**, and
> - **selecting a second program instruction and operands** for execution by the first execution unit from the set of eligible program instructions **when the writeback conflict exists**.

**写回冲突仲裁**：如果本执行单元要写的目标寄存器，正被一个**优先级更高**的执行单元占用，则**换一条指令**执行。这是"收集齐了却发不出去"的第二类阻塞源。

> **建模启示**：GPGPU-Sim 的 `opndcoll_rfu_t::writeback()` 只做了 bank 空闲检查（`bank_idle()`），**没有实现"换一条指令"的写回冲突避让**——这是 gpgpu-sim 与本件的一处建模差距。

## 8. 对 CppTLM 的可借鉴点

1. **scoreboard 与 bank 仲裁必须分层**（§4.1 原文并列）。CppTLM 现有 `HazardTracker` 只处理 RAW 数据可见性；应另建独立的端口/冲突仲裁器，**不要把端口延迟塞进 RAW 逻辑**。
2. **phase 错位分配是"零硬件成本消冲突"的可借鉴思想**（§4.4）。CppTLM 若引入 bank，可采用 `bank = (reg + warp_id) % num_banks`（gpgpu-sim 口径）或 `bank = (reg ^ phase) % num_banks`（专利口径）——两者都让同一条指令的多个源落到不同 bank。
3. **"收集齐了才输出"的中间态需要一个显式数据结构**（§4.2）。CppTLM 现有 `IssueUnitTLM` 直接产出 `IssueToExecBundle`，没有"已 issue / 未齐"的中间站。
4. **写回冲突"换指令"语义**（§4.6）在 gpgpu-sim 中缺失，CppTLM 若做 OC 口径建模，应补上（高优先级 EU 占用目标寄存器 → 该指令不能发射）。
