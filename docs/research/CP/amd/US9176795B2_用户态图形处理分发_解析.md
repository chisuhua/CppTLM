## 2. 发明背景与待解决问题

**应用场景**：GPU 通用计算（GPGPU）需求激增，OpenCL/DirectCompute 等标准 API 出现后，业界希望把 CPU 与 GPU 组合得像单独使用 CPU 一样顺畅。AMD 用 "accelerated processing device (APD，加速处理设备)" 作为比 GPU/APU/GPGPU 更宽泛的上位概念。传统路径下（FIG. 3 数据流模型 300、FIG. 4 Windows 环境模 400），用户态应用 302 只能把命令写入自己的 command buffer 304，再由内核态驱动 306（Windows 下经 WDDM/DXGKRNL）转写到全局唯一的 APD engine ring buffer 308。

**待解决问题**（按文本分条）：

1. **用户态/内核态切换开销**：每次向统一 ring buffer 308 提交命令都要陷入内核，"requires hardware privilege level transitions"，对低延迟提交不可接受；物理、AI 等计算类命令因 CPU 很快要结果，高 dispatch 开销加排队延迟使其"latency incurred ... often unacceptable"。
2. **统一 ring buffer 的锁竞争**：写单一 APD engine ring buffer 308 需要 lock，会阻塞其他 APD-bound 应用。
3. **提交前的地址修补（patching）开销**：APD 只被允许操作 APD memory 和 pinned system memory，故内核软件必须遍历 command buffer 中所有虚拟内存引用并 patch 为物理地址，缺失的数据须先换页并 pin 住；该检查对每条命令都要做，开销显著。
4. **完成通知低效**：统一 ring buffer 用"最后一个操作递增 timestamp"的方式通知完成，增加延迟、依赖硬件中断，且只能以 packet 为粒度判定完成，分辨率不足。
5. **异构系统固有难题**：分离内存系统、调度、QoS、编程模型、多 ISA 编译与功耗五项战（文本明确列举）。

**核心方案一句话**：内核态驱动仅在应用初始化时为该应用分配并注册一个用户态可写、APD 硬件可直接读的专属 ring buffer（work queue），运行期应用以用户态直接把命令写入该队列，由 compute process control block（计算进程控制块）+ 调度器 + doorbell（门铃）信号引导 APD 硬件直接取指执行，从而把提交路径上的内核态切换完全消除。

## 3. 核心方案

### 3.1 整体架构（FIG. 1A–2）

**附图清单**（据 Brief Description of the Drawings）：FIG. 1A 处理系统 100 框图；FIG. 1B APD 104 细化框图；FIG. 2 APD 104 更详细框图；FIG. 3 依赖内核态驱动提交的数据流模型 300；FIG. 4 FIG. 3 模型在 Windows 环境的实例 400；FIG. 5 系统栈 500 组件；FIG. 6 本发明的数据流模型 600；FIG. 7 运行时系统总览 700；FIG. 8 应用初始化流程；FIG. 9 应用提供命令流程；FIG. 10 调度器调度流程；FIG. 11 上下文切换状态保存流程；FIG. 12 软件调度器指导硬件调度器流程。（附图页 FIG. 1B–FIG. 5 的提取文本存在大面积乱码，参考标号以说明书正文为准。）

**系统 100（FIG. 1A）**：CPU 102、APD 104、memory 106、operating system 108、communication infrastructure 109（PCI/PCI-E/AMBA/AGP/以太网等）；软件侧含 kernel mode driver (KMD) 110、software scheduler (SWS) 112；硬件侧含 IOMMU 116（含 TLB 118）、memory controller 140、interrupt controller 148。CPU 与 APD 可单 die/单封装（非强制）。

**APD 104 前端结构（FIG. 1A/1B）**：
- **Command Processor (CP) 124**：控制 APD 内部处理，从 memory 106 中的 command buffers 125 取命令并协调执行；可实现为带微码的 RISC 引擎（含调度逻辑）。FIG. 1B 中 CP 124 含三条流水线：CP input 0（124a）驱动 graphics pipeline 162，CP inputs 1/2（124b、124c）向 compute pipeline 160 转发命令。（文本另提及 "controller mechanism 166 for controlling operation of HWS 128"，与下条 DC 166 标号重复，系原文标号瑕疵。）
- **Dispatch Controller (DC) 126/166/168/170**：dispatch 指 DC 利用上下文状态启动一组 work groups 在一组 compute units 上执行 kernel 的命令；graphics pipeline 162 侧的 DC 166 与 compute pipeline 160 侧的 shader DCs 168、170 接收输入 range，拆分为 workgroup 后送往 shader core 122；DC 可实现为 CP 124 的一部分。
- **Hardware Scheduler (HWS) 128**：从 run list 150 选择进程在 APD 上执行，支持 round robin、优先级（可动态）等策略；其 run list 管理逻辑又称 run list controller (RLC)。
- **Preemption and context switch logic 120**：抢占 shader core 122 中运行的进程，保存/恢复状态（shader core 状态、CP 状态）。interrupt generator 146 用于向 OS 上报 page fault 等中断。
- **执行后端**：shader core 122（compute units/SIMD 集合，可并行执行预定数量 wavefront 136，wavefront 即 work-group 中在同一 SIMD 上同时执行的 work-item 子集）；graphics memory 130。FIG. 2 细化：shader resource arbiter 204 仲裁对 shader core 122 的访问（分配 GPR 与线程空间），SIMDs 206A–206N 各耦合 local data store (LDS) 208A–208N。graphics pipeline 162 含 ordered pipeline 164（VGT 164a、PA 164b、SC 164c、shader-export/render-back SX/RB 176），为固定功能硬件流水线，难以保存/恢复状态，故上下文切换主要针对计算工作与 shader core 中的图形工作。
- **内存侧数据结构**：command buffers 125、run list 150、active list 152、process control blocks (PCB) 154；SWS 112 维护 active list 152 并选出子集交由 HWS 128 管理。

### 3.2 关键机制详解

**（1）初化：唯一需要内核参与的阶段（FIG. 6、FIG. 8）**：步骤 602：用户态应用经 runtime 502 调用函数分配自己的 work queue（ring buffer 或 FIFO）；系统栈 500（FIG. 5）以 IOMMUv2 driver 506 取代 DXGKRNL 504 的旧通道，并设 APD scheduler 508a / CPU scheduler 508b、APD memory management 510a / CPU memory management 510b 对称组件。步骤 604：应用调用内核态驱动的 kernel mode function，把 ring buffer 注册给 APD 访问。步骤 606/608：内核态驱动接受资源分配请求，分配 APD memory 或 pinned system memory，且可用虚拟地址分配（对应尚未落入物理内存的数据）。FIG. 8 对应：802 开始 → 804 应用初始化（含创建 compute process control block 710）→ 806 分配 ring buffer（compute command ring buffer）→ 808 分配内存资源 → 810 结束。

**（2）运行期用户态直接写入（FIG. 9、FIG. 7）**：步骤 902 开始 → 904 应用填充 command buffer 及 reference data buffers → 906 命令转发到本应用的 ring buffer（文本明确：command buffer 可选，可直接写 ring buffer 704）→ 908 命令就绪待 dispatch → 910 结束。运行时架构 700：每个 application 702 拥有自己的 ring buffer 704；内核空间对象包括 master compute process list 708（跟踪已注册应用）、compute process control blocks and run list entries 710、context switch blocks 712。**APD 通过 compute process control block 710 获取进程的 privilege state information（含 ring buffer 704 的位置），从而无需代价高昂的内核态切换即可直接读取 ring buffer 704 中的命令**。PCB 710 还保存优先级（low/medium/high/realtime）、timer reset value（下个调度窗口的 APD 处理时间，以时钟周期或指令数计）及对 context switch block 712 的引用。

**（3）内存保护与 page fault 支持**：ring buffer 704 保证 resident、不可被换出；借助 IOMMUv2 与 APD 硬件支持，user space 命令/数据缓冲 706 可发生 page fault，从而免除 pinning 开销——对比 FIG. 3/4 旧模型必须在提交前遍历修补虚拟地址引用。处理流程：APD 处理引用虚拟内存的指令时先判定有无物理映射（页表），无则触发 page fault 给 CPU，由 CPU 将数据调入 pinned system/APD memory；APD 可切换到另一应用上下文阻塞等待，或原地 stall；APD 还可在执行前 probe 指令预判是否将发生 page fault，如是则触发 CPU 的 page fault 中断机制。

**（4）doorbell（门铃）通知与调度（FIG. 10）**：1002 开始 → 1004 为应用分配 PCB 710 → 1006 分配 ring buffer 704 → 1008 调度算法（如 round-robin）确定下一个被调度应用 → 应用向 ring buffer 704 添加命令时用 **"door bell" signal** 通知 APD 自己可被选中执行；若某 PCB 未发 doorbell，APD 在 1008 跳过它 → 1010 APD 从 PCB 710 取得 ring buffer 位置 → 1012 直接从 ring buffer 704 服务命令（CPU 可同时继续自己的命令，两者异步，仅在依赖处同步）→ 1014 是否调度其他应用（可由应用终止、ring buffer 排空、或 timer 到期的抢占式 context switch 触发；timer 值与优先级存于 PCB 710）→ 无更多应用则 1016 结束、APD idle。**完成信号**：应用 ring buffer 中的 work packet 可完全在用户态内发出完成信号（替代旧模型 timestamp+硬件中断），成本更低、分辨率可配置。

**（5）上下文切换（FIG. 11）**：1102 开始 → 1104 将被换出应用的 APD 状态（寄存器值、下一指令等）存入其 context switch block 712 → 1106 经 PCB 710 识别下一被调度应用及其 ring buffer 704、context switch block 712 → 1108 APD 从 context switch block 712 恢复状态 → 1110 结束，换入应用从中断处继续。

**（6）软件调度器指导硬件调度器（FIG. 12）**：1202 开始 → 1204 软件调度器用启发式预测下一应获 APD 时间的应用 → 1206 将该应用的 runlist entry 710 注册给硬件调度器（而非自动调度全部上下文），实现细粒度控制 → 1210 结束。当 runlist entry 集合被增/删/改（如改优先级）时，整套 runlist entries 710 重新提交，使硬件调度器重新评估调度顺序。

## 4. 权利要求摘要

共 21 项权利要求，3 项独立权利要求（claim 1 方法、claim 8 非暂态计算机可用介质、claim 15 系统）。

**独立权利要求 1（方法）**：一种方法，包括：由调度器选择一个用户态应用进行调度；以及在用户态下，把命令从由内核态驱动为该用户态应用分配的 work queue 直接分发（dispatch）给加速处理设备（APD）；该 work queue 可被用户态应用与 APD 访问而无需切换到内核态。

**独立权利要求 8（非暂态计算机可用介质）**：记载上述同一方法（选择 + 用户态直接从 work queue 向 APD 分发命令、无需内核态切换）的指令。

**独立权利要求 15（系统）**：包括 memory 与 processor，processor 配置为执行同一"选择 + 用户态直接分发"动作。

从属权利要求按主题分组（方法/介质/系统三组对称：claim 2/9/16、3/10/17、4/11/18、5/12/19、6/13/20、7/14/21）：

- **command buffer 中转**（2/9/16）：命令先存入 command buffer 再转发到 work queue；
- **内存资源分配**（3/10/17）：为用户态应用分配 APD 可访问的内存资源；
- **队列形态**（4/11/18）：分配 work queue 包括分配 compute command ring buffer；
- **进程控制块**（5/12/19）：分配对应该应用的 compute process control block，其中存储标识 work queue 位置的信息；
- **APD 直读队列**（6/13/20）：分发命令包括 APD 基于 PCB 中的位置信息访问 work queue 读取命令；
- **进程列表**（7/14/21）：分配包含该 PCB 及一个或多个其他 PCB 引用的 compute process list。

## 5. 与专题主题的关系

本专利属于专题「AMD GPU 前端全链路（CP/IB/PM4 + doorbell/HQD + SPI/SQ wave 分发）」的最上游环节。

**(a) 在 AMD 前端链路中的位置**：本专利定义了链路起点到 CP 入口的一段——用户态软件（application 702 / runtime 502）→ 每应用专属硬件队列（ring buffer 704，即 direct dispatch 队列）→ KMD 注册 + PCB 710 / run list entry（特权态与队列定位）→ HWS 128（RLC）从 run list 150 选进程 → CP 124（124a/b/c 流水线）从队列取命令 → DC 166/168/170 拆分为 workgroup → shader core 122（SIMD 206、wavefront 136）。其中 ring buffer 704 + doorbell + PCB 的位置信息，正是后来 HSA/AMDKFD 中"用户态直接提交 + doorbell + HQD（hardware queue descriptor）硬件队列"机制的雏形：专利文本中的 "door bell" 是现代 AMD doorbell 通知机制的直接前身；每应用 ring buffer 对应由 HQD 管理的硬件队列；CP 124 对应解析 IB/PM4 包的 command processor；DC 对应 CP 内计算引擎（后来的 MEC）前端分发单元。

**(b) 与 NVIDIA 的对应关系**：本专利与 NVIDIA US20230153146A1（用户态直接工作提交：应用更新 put pointer 422、经 notifier 410 通知前端）在机制上直接对应——两者都让应用在不陷入内核的前提下把新工作写入硬件可见队列并以轻量信号（doorbell / notifier）唤醒硬件调度；AMD 以 2010-12-13 优先权日早约 10 年布局了同类机制，可视为该设计范式的最早专利化形态之一。

**(c) 同族关系**：本专利与 US20120229481A1（Accessibility of Graphics Processing Compute Resources，图形处理计算资源的可访问性）、JP6086868B2、EP2652614B1 同属以 2010-12-13 优先权日（临时申请 61/422,465）为基础的 user-mode dispatch 专利群：本案聚焦"分发/提交路径本身"（队列分配、doorbell、直读、调度），同族另案从"计算资源可访问性"等角度对同一发明构思做互补布局（说明书正文仅引用临时申请 61/422,465，其余同族关系依任务背景给出）。

## 7. 评价与启示

**技术重要性**：
- 本专利是 AMD 把 GPU 从"图形外设"改造为"一等公民（first-class citizen）计算设备"的奠基性专利之一：它确立了"初始化在内核、运行期全用户态"的提交模型，直接消除了提交路径上的特权级切换、全局 ring buffer 锁、逐命令地址修补三大开销；
- per-application ring buffer + doorbell + PCB/run list + HWS + context switch block 的组合，几乎逐一对应后来 HSA 软件栈与 AMDKFD/ROCm 硬件栈的要素（用户态队列、doorbell 通知、HQD 硬件队列描述符、计算引擎抢占/上下文保存），是理解现代 AMD 计算前端硬件（MEC、HQD、doorbell 页）起源的关键文献；
- IOMMUv2 + page fault 支持免除 pinning、允许按需调页，与"统一虚拟内存、按需迁移"的现代异构内存路线一脉相承；用户态完成信号替代 timestamp+中断，也预示了后来 fence/signal 的用户态轮询完成机制。

**局限性（基于专利文本可推断）**：
- 方案依赖 OS 与硬件配合（IOMMUv2、APD 硬件直读用户队列、page fault 上报），文本自述"其他机制也可替代"，但未给出无 OS 支持时的退路细节；
- 调度粒度与 QoS 描述偏概念（timer、优先级、round-robin、软件启发式指导硬件），未给出抢占延迟、上下文保存大小等量化指标；graphics pipeline 162 因固定功能难以上下文切换，纯图形负载不在本方案切换范围内；
- 文本未涉及多应用间对同一队列的共享/原子提交语义，doorbell 与 ring buffer 的具体寄存器/内存映射实现未公开；FIG. 1B 中 166 标号重复、附图页提取大面积乱码，个别标号以说明书正文为准。
