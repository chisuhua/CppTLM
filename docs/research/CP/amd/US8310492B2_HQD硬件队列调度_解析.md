## 2. 发明背景与待解决问题

**应用场景**：CPU+GPU 系统中，CPU 101 向 GPU 104 提供工作项（work item，即 command（命令）与数据）。图形应用天然是 SIMD（单指令多数据）并行负载；同时 GPGPU 计算兴起，CPU 把原本由自己完成的计算工作卸载给 GPU，GPU 利用率成为系统性能的关键因素。

**待解决问题**（按文本分条）：

1. 传统系统中，命令缓冲（command buffer）的优先级排序（prioritization）完全由 CPU 软件完成，GPU 只是按 CPU 指定的顺序被动执行已入队命令；
2. CPU 排序无法感知 GPU 的实时局部资源状态（哪些 SIMD/ALU 空闲、待处理负载多少），因此"仍有改进空间"（"leaves room for improvement"）；
3. GPU 处理能力快速增长、且被越来越多地用于通用计算，需要更有效地把 GPU 资源分配给工作项的手段，理想情况下让 GPU 利用率接近最大。

**核心方案一句话**：在 GPU 内设置 Ring List Controller 140（RLC，环形列表控制器）与 Command Processor 150（命令处理器），让 GPU 硬件基于动态测定的 workload profile（负载画像）自主选择、重排优先级并调度系统内存中的多个 ring buffer（环形缓冲区），必要时抢占（pre-empt）正在执行的环并把其上下文保存到 GPU 本地内存的 CSA（Context Save Area，上下文保存区），从而在不违背 CPU 指定优先级大框架的前提下做 GPU 侧第二级细粒度调度。

### 3.2 关键机制详解

**（一）CPU 侧数据结构（FIG. 1–2）**：

- Ring Buffers 110（环形缓冲区）：CPU 101 与 GPU 104 之间传递命令的队列结构，实现为 circular array（循环数组），每个元素容纳一个指向 indirect buffer 区位置的指针，并带 head/tail pointer（头/尾指针）等维护参数。CPU 可按优先级划分环，例如分别为 high priority、low priority、low latency 命令各设一个环；
- Indirect Buffers 111（间接缓冲区）：存放实际 command buffer（命令+关联数据，如 "draw" 命令连同待绘制图像），支持单级或多级间接；与环分离存放以提高内存利用效率；分配方式可按命令、按环或全局连续区；
- Ring Buffer Work Registers 112（环缓冲工作寄存器）：可位于 System Memory 102 或 GPU 104 内寄存器，承载 CPU→GPU 的队列元信息——write pointer / read pointer（写/读指针，标记最后写入项与最后读取项）、当前活跃环列表、CPU 101 指定的 priority ordering（优先级排序）、环到 GPU 各单元的分配等，也用作 CPU 检测命令是否被 GPU 消费的握手位置（GPU 处理后改写该位置的值，超时未变则 CPU 判定 GPU 异常）。

**（二）CPU 侧流程（FIG. 3）**：

- 301 Initialize Ring Buffer in System Memory（初始化系统内存中的环缓冲）：系统启动或应用启动时进行，含内存分配、数据结构初始化、相关寄存器初始化；环数量/大小可为配置参数或按应用特性动态确定；
- 303 Notify GPU of Ring Buffer Configuration（向 GPU 通告环配置）：通告内容包括环数量、每个环的位置与大小、CPU 确定的优先级排序；可通过写 GPU 监视的寄存器位置（如 ring buffer work registers 112）实现，也可经 graphics driver 103 发起；
- 305 Write Application Commands and Data to Ring Buffer（写应用命令与数据）：命令按优先级入对应的环——写命令缓冲到 indirect buffer 111、把其指针入队到对应环、更新 head/tail 指针；随后可更新寄存器/内存位置通知 GPU 有新数据，某些实施例中也可不单独通知，由 GPU 持续监视环本身。CPU 侧流程与 GPU 异步执行，允许应用在有大量待处理命令时继续运行。

**（三）GPU 侧硬件结构（FIG. 1）**：

- RLC 140（Ring List Controller，环形列表控制器）：协调对 ring buffers 110 的访问——确定待处理环列表、接收 CPU 指定的优先级排序、决定环在 GPU 上的调度，与 command processor 150 协同使 3D/CS complex 130 中各 SIMD 处理器保持接近最大利用率；RLC 140 负责监视环并把环搬入 GPU；功能可用硬件+微码（microcode）组合实现；
- Command Processor 150（命令处理器）：控制 GPU 104 内部处理——接收 CPU 命令并协调执行，可为每个收到的命令生成一个或多个 GPU 内部命令（如把一条渲染整图的命令切分为多个子区域指令）；一个实施例中被实现为带微码的 RISC engine（RISC 引擎），微码中实现含调度逻辑在内的逻辑；CP 150 与 RLC 140 共同实现 GPU 上的优先级排序与调度；
- 3D/CS Complex 130（3D/计算着色器复合体）：GPU 主计算部件，含多个 SIMD 处理器（vertex/pixel/geometry/unified shader 等），在实施例中被视为由 3D 计算部件、compute shader 部件与 low latency（低延迟）计算部件构成；
- GPU Memory 120 含多个 CSA 121（Context Save Area，上下文保存区）：保存未完成即被换出的工作项上下文。

**（四）GPU 侧总流程（FIG. 4，process 400）**：

- 401 Determine Ring Buffer Configuration（确定环配置）：系统启动和/或应用启动时获取环配置，可基于周期性监视或 CPU 信号；
- 403 Monitor Ring Buffers（监视环缓冲）：检测可供处理的环。通知有两种模式：CPU 更新 System Memory 中的寄存器/内存位置由 GPU 监视读取；或 CPU 在写入命令后**直接向 GPU 104 内部寄存器写入**（"directly write into a register within GPU 104 notifying GPU 104 that command buffers are available"）——这是后世 doorbell（门铃）提交机制的雏形；
- 405 Select Subset of Ring Buffer for Execution（选择环子集执行）：按 CPU 就绪清单或环中是否有待执行命令选择子集（如 FIG. 2 从 200 选 210），可用 DMA 把选中环搬入 GPU local memory 或 GPR（通用寄存器）；读取后 GPU 更新内存位置指示已读/已处理；
- 407 Select Processes for Execution（选择并排序待执行命令）：决定环如何分配到 GPU、命令如何分配到 GPU 内资源，确定环间与环内命令的优先级排序（细节见 FIG. 5）；
- 409 Execute Selected Processes（执行）：按 GPU 确定的优先级执行；CP 150 可将单条命令切分为多条子命令并调度到 SIMD/ALU；一条命令完成释放资源后按优先级执行下一条；也可动态评估待执行命令、选最可能最优利用当前资源者先执行；还可在若干命令完成后回到 405 重选环。执行期间 RLC 140 持续监视系统内存中的环，一旦高优先级环被 CPU 追加命令即可抢占低优先级执行（FIG. 6）。

**（五）两级优先级排序（FIG. 5，步骤 501–505）**：

- 501 Determine GPU Workload Profile（测定 GPU 负载画像）：由 RLC 140 和/或 CP 150 收集可用处理单元、各单元相对处理能力、待处理负载及其当前优先级排序，形成反映 GPU 状态的 workload profile；考虑的处理单元类型包括 SIMD 单元、ALU、3D 处理器件、compute shader 器件、low latency 处理器件；可连续或周期性动态测定（如命令/环执行完成时、从系统内存读入新环子集时）；
- 503 Determine Ring Buffer Ordering（确定环排序）：基于 workload profile 并参照 CPU 指定的排序——"substantially adhered to"（基本遵循）CPU 排序的同时按动态负载优化实际执行顺序，使 GPU 对处理单元的利用拥有 fine grained control（细粒度控制）；
- 505 Determine Command Ordering（确定命令排序）：在环内进一步排序并决定每条命令分配到哪个处理部件；文本举例：高优先级资源空闲时可把原低优先级命令提升执行、高优先级资源被占时可降级执行高优先级命令、或按部件可用性把原拟在 compute shader 上执行的命令改投 low latency 部件。

**（六）抢占与上下文切换（FIG. 6，步骤 601–609）**：

- 601 Determine Whether to Switch to a Second Ring（判定是否切换）：依据当前执行进程优先级、待执行进程优先级、time slice（时间片）值、各进程剩余执行时间等因素，由 CP 150 决定是否强制上下文切换；
- 603 Pre-empt Executing Ring（抢占）：保存被抢占命令/环的状态（pending 命令、数据、program counter 等执行参数）到 GPU Memory 120 中的 CSA 121；
- 605 Executing the Second Ring（换入执行）：换入者可以是首次执行的新命令/环，也可以是从 CSA 恢复的先前被换出者（如时间片用尽被保存者）；
- 607 Complete Execution of Process（命令完成）：同环内下一条命令可接着执行（环内顺序可由 GPU 决定）；完成后 GPU 可检查是否有更高优先级环或同环更高优先级命令；
- 609 Complete Execution of Second Ring（环完成）：环内全部 pending 命令执行完毕后，GPU 选择优先级顺序中的下一个环执行。（注：说明书正文两处段落均标为 "step 607"，后者按 FIG. 6 应为 609，属原文标号笔误。）

**实施例变体与说明**：memory buffers 不限于 ring buffer，其他适合高效排队的数据结构亦可；ring buffer work registers 112 可位于系统内存之外（如 GPU 内）；GPU 104 本身也可以是嵌入 CPU 101 或桥芯片（北桥/南桥）中的逻辑；实施例可用 Verilog/RTL/netlist 等 HDL 描述并经 maskwork/photomask 配置制造工艺（该点亦写入 claim 21/22）。提取文本存在若干笔误：如 "RLC 140 determines the list of ring buffers 140"（应为 110）、多处把 step 405/407 的功能写成 "step 403"、"RCL 140"、"system memory 103"（应为 102）、"hian embodiment"（应为 In an embodiment），均以语境复原。

## 4. 权利要求摘要

共 24 项权利要求，3 项独立权利要求（claim 1 方法、claim 12 系统、claim 20 非暂态计算机可读存储介质）。

**独立权利要求 1（方法）**：一种在 GPU 上处理工作项的方法，包括：改变（changing）CPU 写入内存的一个或多个缓冲区的优先级排序，以重排这些缓冲区的执行序列；按照改变后的优先级排序从中选择第一子集以在 GPU 上执行其工作项——其中"改变"与"选择"均响应于动态测定的 GPU workload profile；以及按重排后的执行序列在 GPU 上执行该子集的工作项。

**独立权利要求 12（系统）**：一种执行工作项的系统，GPU 被配置为执行与 claim 1 质相同的"改变优先级排序→按新序选择子集→按改变后的执行序列执行"动作。（原文误写 "graphics processing unit (CPU)"，经 Certificate of Correction 更正为 GPU。）

**独立权利要求 20（非暂态存储介质）**：存储指令的 non-transitory computer readable storage media，指令被执行时以与 claim 1 相同的方法处理 GPU 工作项。

从属权利要求按主题分组：

- CPU 优先级的接收（claim 2、13）：在"改变"之前先从 CPU 接收缓冲区的优先级排序；
- 抢占式执行（claim 3、14）：执行第一缓冲区工作项期间确定需执行第二缓冲区→抢占第一缓冲区→启动第二缓冲区；
- 上下文保存（claim 4、15、19）：抢占时把第一环缓冲的上下文保存到本地内存的 context save area；系统 GPU 本地内存配置一个或多个 CSA；
- 抢占触发条件（claim 5、6、16）：把已执行时长与预定 time slice 值比较；或监视缓冲区并检测到优先级高于当前环的工作项；
- 监视/通知机制（claim 7）：读取由第二处理器（CPU）写入的内存位置，并据读值检测命令写入事件；
- 子集选择依据（claim 8、11、24）：分析各缓冲区内工作项并确定其优先级后选择子集；为第一子集中每个缓冲区选择 CPU 写入的命令缓冲；选择动作由 GPU 执行；
- 负载画像内涵（claim 23）：workload profile 包括 GPU 处理部件的可用性，改变优先级排序以提高处理部件利用率；
- 结构形态（claim 9、10、17、18）：内存为耦合 CPU 与 GPU 的系统内存；至少一个缓冲区为 ring buffer；系统还包含 CPU 与该内存；
- HDL/制造实现（claim 21、22）：指令为硬件描述语言指令；指令用于经生成 maskworks/photomask 配置制造工艺以产生处理工作项的器件。

## 5. 与专题主题的关系

本专利属于专题「AMD GPU 前端全链路（命令处理器 CP / 间接缓冲 IB / PM4 包处理 + doorbell/HQD 队列提交 + SPI/SQ wave 分发）」。

**(a) 在 AMD 前端链路中的位置**：本专利覆盖了提交链路的最前端与调度中枢——CPU 写队列（ring buffer 110 + indirect buffer 111，对应后世的 IB（Indirect Buffer，间接缓冲）层级）→ 提交通知（更新 ring buffer work registers 112 的写/读指针，或 CPU 直接写 GPU 内部寄存器触发 GPU 处理，即 doorbell（门铃）写的前身）→ GPU 前端硬件读队列（RLC 140 监视环、经 DMA 取环、决定环列表与优先级）→ Command Processor 150 解析命令、切分子任务并调度到 3D/CS Complex 130 的 SIMD 处理单元（对应后世 CP→SPI→SQ 的 wave 分发路径）。其中"每队列（环）一组工作寄存器（指针、优先级、就绪状态）+ CPU 写寄存器触发 GPU 取数"正是后来 GCN 起每队列一个 HQD（Hardware Queue Descriptor，硬件队列描述符）+ doorbell 触发读指针这一范式的直接源头。需要说明：**本专利正文并未出现 "HQD" 与 "doorbell" 字面术语**，该对应系据机制功能的分析性判断。

**(b) 与 NVIDIA 上游模块研究的对应关系**：AMD 侧的 ring buffer + indirect buffer 提交对应 NVIDIA 侧的 pushbuffer（推送缓冲）提交（US9489763B2）；本专利的"CPU 直接写 GPU 寄存器通知命令可用"（claim 7 的"读取第二处理器写入的内存位置、检测命令写入事件"）与 NVIDIA 用户态直接提交 put pointer / notifier 机制（US20230153146A1）解决同一问题——降低提交路径上的软件往返开销；RLC 140 + CP 150 基于 workload profile 的硬件二级调度，则对应 NVIDIA 前端 Host Interface → Front End → TMU 的任务接纳与调度职能。差别在于：本专利以"环/缓冲区"为调度粒度且调度决策（重排、抢占、CSA 换出）全部落在 GPU 前端硬件，而 NVIDIA TMU 系列更侧重以任务描述符为单位的依赖与预取管理。

**范式延续**：本专利确立的"多队列并存 + 每队列硬件可见的状态（指针/优先级）+ CPU 写触发 + GPU 硬件按负载画像自主选择与抢占"范式，与后来 GCN/RDNA 架构中每队列一个 HQD、用户队列经 doorbell 写入触发 CP MEC（Micro Engine Compute）读取，以及 ROCm/HSA 软件栈中用户态 AQL 队列 + doorbell 直接提交的机制一脉相承（此延续关系为专题分析语境下的对照结论，超出本专利文本自身表述）。

## 7. 评价与启示

**技术重要性**：

- 这是 AMD/ATI 阵营把"GPU 工作调度权"从 CPU 软件移交 GPU 硬件的奠基性文献：首次以专利形式系统化描述了 GPU 前端硬件（RLC 140 + CP 150）基于动态 workload profile 对多队列做选择、二级优先级重排、时间片抢占与上下文保存的完整闭环，直接针对 GPGPU 时代 GPU 利用率问题；
- 它固化了 AMD 前端提交链路的三件套骨架：ring buffer（队列）+ indirect buffer（命令体分离，一级/多级间接）+ work registers（指针与队列元信息），其中"CPU 直接写 GPU 寄存器通知命令可用"是 doorbell 提交机制的概念原型；
- 抢占式环切换 + GPU 本地 CSA 121 的设计为后来 GPU 多任务/多进程上下文切换（compute context switch）提供了早期蓝本；CP 150"带微码的 RISC 引擎"实现方式也点明了 AMD CP 可编程微控制器（后世 ME/MEC 微引擎）的实现路线。

**局限性（基于文本可推断）**：

- 调度粒度以 ring buffer 为中心，未出现后来 HQD 那种"每队列一份完整硬件描述符（基址/大小/读写指针/调度属性集中存放）"的结构化定义，队列状态仍分散在系统内存的 work registers 中；
- workload profile 的测定与调度策略仅给出因素枚举（可用单元、相对能力、pending 负载），无具体算法、量化指标或硬件实现细节；
- 通知机制以 CPU 主动更新为主（轮询监视或直接写寄存器），未涉及用户态绕过内核驱动直接提交的路径（这是后来 HSA/doorbell 阶段才解决的问题）；
- 文本提取存在多处标号/文字笔误（见 3.2 末），且 FIG. 1 图内标号在提取文本中大面积乱码，附图细节以 PDF 原为准。

**对理解 AMD GPU 前端架构的价值**：本专利是理解 AMD 前端"CP/RLC 硬件调度"传统的起点文献——它解释了为什么 AMD GPU 前端从 TeraScale 后期到 GCN 一直维持"多硬件队列 + 微码化命令处理器 + 负载感知重排与抢占"的设计哲学；将其与 NVIDIA 的 pushbuffer/TMU 系列专利对读，可以清晰看到两家在"提交与调度硬件化"上的同题异答：AMD 选择把队列状态与调度决策前移到 GPU 前端硬件（演化为 HQD + doorbell + MEC），NVIDIA 选择把任务描述符与依赖解析做深（演化为 TMU 任务图引擎）。本专利正是 AMD 这条演化线的源头坐标。
