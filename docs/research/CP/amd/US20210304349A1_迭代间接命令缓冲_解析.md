## 2. 发明背景与待解决问题

**应用场景**：APD（Accelerated Processing Device，加速处理设备）116 即 AMD GPU。软件（application 402 / driver 122）向 APD 提交命令 406 的方式有两种（[0032]–[0033]）：

1. 直接提交模式：application 126 把命令逐条传给 APD，command processor 136（CP，命令处理器）边收边执行——但每条命令都占用 processor 102（CPU），CPU 被命令传输任务长期占用；
2. Indirect Buffer（IB，间接命令缓冲）模式：IB 410 预先存好命令 406，primary command buffer 404（主命令缓冲，CP 默认执行的"顶层"缓冲）中的 indirection command 408（间接命令）携带指向 IB 410 的指针；CP 136 遇到 408 后沿指针跳转到 IB、执行其命令、再返回主缓冲。好处：减轻 CPU 负担、命令组可复用（对同一 IB 重复下发 indirection command 即可，无需重复传输命令本体）。

IB 中可存放的命令类型与主缓冲相同：draw command（绘图命令）、compute command（计算命令）、resource command（资源命令，对作为输入/输出的内存缓冲进行创建/删除/拷贝/修改）（[0037]）。IB 可"异步"写入：应用可在启动/初始化阶段预先写好 IB，运行时再修改其中命令或新建 IB（[0041]）。IB 还可包含指向其他 IB 的 indirection command（嵌套间接，[0039]）。

**待解决问题**（按文本表述）：

1. CPU 重提交开销：对需要重复执行 N 次的同一命令组，传统 IB 复用仍需 CPU 重复下发 N 个 indirection command；直接提交模式下更是要把全部命令写 N 遍（[0051] 以立体渲染为例：不用迭代 IB 时，"渲染全部场景几何"的命令要由 processor 102 写两次、传两次）；
2. 重复执行中"每次迭代略有差异"的场景（每次换相机、换渲染区域、换 tile）无法靠单纯复用缓冲表达——要么 CPU 逐次提交不同命令，要么 CPU 介入每次迭代的状态切换。

**核心方案一句话**：在 IB 中附加 metadata（迭代标志 + 迭代次数 + 逐命令谓词掩码），CP 136 在 APD 内部对 IB 内容循环执行指定次数、并按谓词数据决定每次迭代执行哪些命令，整个"循环"无需 CPU 参与。

**执行模型要点**：CP 136 负责调度 workgroup（工作组）与 wavefront（波前）到 compute unit 132 / SIMD unit 138（[0020]）；work-item（工作项）在 lane（通道，示例为 16 lane）上并行构成 wavefront，wavefront 组成 work group（[0019]–[0020]）。CP 执行命令时完成的操作包括：向 graphics pipeline 134 提供任务、把 shader program 调度到 compute unit 132、组织各存储器之间的资源搬运等（[0045]）。primary command buffer 404 与 IB 410 均可存于 APD 116 内存储器和/或 system memory 104（[0043]）。

**FIG. 4 数据结构**（迭代控制结构）：
- Application 402：运行于 processor 102 的软件（可为 application 126 或 driver 122），向 primary command buffer 404 写命令 406；
- Primary command buffer 404：含 commands 406(1)–406(8) 与 indirection command 408；
- Indirect command buffer 410：含命令 406 与 **indirect command buffer metadata 412**（IB 元数据）；
- Metadata 412 三个字段：**iterative flag 414**（迭代标志，指示该 IB 是否迭代）、**iteration count 416**（迭代次数，指示对 IB 内容循环多少遍）、**predication metadata 418**（谓词元数据，指示 CP 136 在任一特定迭代中应执行哪些命令 406）；
- predication metadata 418 的替代存放位置：可存于 IB 内的命令 406 中，或存于 IB 410 之外（[0040]）。

### 3.2 关键机制详解

**（1）IB 如何携带迭代次数/条件**：application 402 以与写命令相同的方式把 metadata 412 写入 IB 410（[0042]）。iterative flag 414 是循环使能开关；iteration count 416 是静态写入的循环次数上限；predication metadata 418 是"迭代号 → 命令子集"的执行掩码——它为每条命令标注该命令在哪些迭代号下执行（[0040]、[0048]）。

**（2）CP 如何在不回 CPU 的情况下重复执行 IB**（[0046]–[0049]）：
1. CP 136 顺序执行 primary buffer 404 中的命令；
2. 遇到 indirection command 408，跳转到其所指 IB 410 的**起始处**，开始顺序执行；
3. CP 检查 **iterative flag 414**：未置位则执行 IB 一遍即结束；置位则把 IB 内容执行 **iteration count 416** 次；
4. 每一次迭代内，CP 依据**当前迭代号**（由 CP 136 自行跟踪）与 **predication metadata 418** 确定本迭代使能的命令，只执行被指定的命令、跳过其余命令（[0048]）；
5. 全部迭代完成后，CP 返回调用点——即触发跳转的那条 indirection command 408（它可位于主缓冲，也可位于另一 IB，支持嵌套），从其后一条命令继续执行。

由此，N 次重复 + 每次差异化的命令流被压缩为"一次写 IB + 一条 indirection command"，循环变量（当前迭代号）与逐迭代命令筛选全部在 CP 内闭环。

**（3）终止条件与状态更新**：终止条件是确定性的——完成的迭代数达到 iteration count 416（flag 未置位时为 1 遍），随后返回调用点（[0049]、FIG. 8 步骤 806）。文本未描述基于运行时数据（如收敛判定）的动态终止；谓词掩码本身是写入 IB 的静态数据。方法 800（FIG. 8）：802 从 IB metadata 获取迭代次数与谓词数据 → 804 对每个迭代执行谓词指定的命令（未指定者不执行）→ 806 达到指定迭代数后结束处理；各种情形下 APD 116 从迭代 IB 返回并继续在返回位置处理后续命令（若有）（[0058]–[0059]）。

**（4）三个应用示例**：
- **立体渲染（FIG. 5，technique 500）**：左眼相机 502、右眼相机 504 面向场景几何 506。iterative IB 510 含：set camera to left eye 512、set camera to right eye 514、render scene geometry 516；谓词 516(1) 令 512 只在第 1 迭代执行、516(2) 令 514 只在第 2 迭代执行、516(3) 令渲染命令两次迭代都执行；iteration metadata 518 指示迭代 2 次（[0050]–[0052]）。效果：渲染命令只写一遍，CPU 免于重复传输；
- **相机匹配渲染（FIG. 6，technique 600）**：同一图像不同区域用不同设置（如分辨率）渲染以模拟相机镜头特性；中央区域 602、周边区域 604。IB 610 含 612(1) 设渲染部分为周边区域、612(2) 设为中央区域、612(3) 渲染场景几何 606，配 metadata 614/615/616 与迭代信息 618（2 次迭代）（[0053]–[0054]）；
- **粗分块渲染（FIG. 7，technique 700）**：场景几何 706 划分为 4 个 coarse tile 702(1)–702(4)，APD 逐 tile 处理。IB 708 含 4 条 set rendered portion to tile N 命令 710(1)–710(4)，谓词 712(1)–712(4) 各指定其在不同迭代执行；render scene geometry 命令（说明书记作 715，图中标注 714，见下方笔误说明）在每个迭代按当前 tile 渲染；iteration number 718 = 4（[0055]–[0056]）。

**提取文本笔误/乱码标注**：[0033] "the command buffer 136 executes commands" 与 "the command buffer traverses the pointer" 均应为 command processor 136；[0041] "the application 410" 应为 402；[0043] 同句重复出现且 "ay memory" 应为 any memory；[0049] "ite ion" 为 iteration；[0054] "6123)" 应为 612(3)，且该段对第 2 迭代的描述 "rendering occurs for the peripheral region 604 but not the central region 602" 与语义矛盾（第 2 迭代应为中央区域渲染），疑为原文复制笔误；FIG. 5 中谓词元数据与渲染命令共用标号 516（原文标号冲突，以 516(1)/(2)/(3) 区分）；FIG. 7 渲染命令正文标号 715 与图内 714 不一致，图内另见 710(5) "Iterations 1–4" 标注。

## 4. 权利要求摘要

共 20 项权利要求，3 项独立权利要求（claim 1 方法、claim 10 命令处理器、claim 19 加速处理设备）。

**独立权利要求 1（方法）**：一种为加速处理设备执行命令的方法，包括：从迭代间接命令缓冲的 metadata 中获取迭代次数与谓词数据；对该迭代次数指示的每个迭代，按谓词数据执行该迭代间接命令缓冲中的命令；以及在处理了等于该迭代次数的迭代数之后，结束对该迭代间接命令缓冲的处理。

**独立权利要求 10（命令处理器）**：一种 command processor，包括一个 processor 与一个 memory interface（存储接口，配置为从迭代间接命令缓冲取回命令与 metadata）；processor 配置为执行与 claim 1 相同的"获取迭代次数与谓词数据 → 逐迭代按谓词执行命令 → 达数后结束"三步操作。

**独立权利要求 19（加速处理设备）**：一种 APD，包括 compute unit（计算单元）与上述结构的 command processor；其命令包含一条或多条在该 compute unit 上执行的命令；CP 的 processor 执行与 claim 10 相同的三步操作。

从属权利要求按主题分组：

- 谓词语义细化（claim 2、3 / 11、12 / 20）：谓词数据指示每个迭代应执行的命令；执行时"执行被指示者、不执行未被指示者"；
- 进入/退出控制流（claim 4、5 / 13、14）：响应于指向该迭代 IB 的 indirection command 开始执行；结束后返回控制流转入该 IB 的位置；
- 缓冲写入（claim 6 / 15）：把命令、迭代次数与谓词数据写入迭代间接命令缓冲（claim 15 表述为 CP 的 processor 写入）；
- 应用场景限定（claim 7–9 / 16–18）：IB 内含立体渲染技术、coarse binning 技术、相机匹配渲染技术的命令。

## 5. 与专题主题的关系

本专利属于专题「AMD GPU 前端全链路（CP/IB/PM4 + doorbell/HQD + SPI/SQ wave 分发）」，并与 NVIDIA TMU 上游模块研究对照。

**(a) 在 AMD 前端链路中的位置——CP 对 IB 的执行控制环节**：AMD 前端链路为：CPU 侧 driver 122 写命令 →（doorbell/HQD 队列机制提交）→ CP 136 取指执行 → 经 SPI/SQ 把 wavefront 分发到 compute unit 132。本专利全部新逻辑落在 CP 136 消费 IB 410 这一环节：IB/HQD 提供"命令在内存中、CP 自己取"的基础自治能力，而 iterative flag 414 + iteration count 416 + predication metadata 418 在 IB 层之上叠加了**迭代控制结构**，使 CP 的命令指针获得"回跳 + 条件执行"能力。它不触及 doorbell/HQD 提交机制，也不改 SPI/SQ 分发，纯粹扩展 CP 对命令流的解释能力——可视为 PM4/IB 命令体系上的一种"缓冲区级循环指令"。值得注意的是，CP 136 同时是 workgroup/wavefront 调度者（[0020]），因此该循环天然作用于其下游的全部图形/计算分发。

**(b) 与 NVIDIA 的对应关系**：迭代 IB 使命令流获得"循环执行"能力，对应 NVIDIA 侧两条线：

- **US 11,182,207 B2 的 Self-Reset Flag 446**：NVIDIA 把循环做在 task graph（任务图）层——任务描述符内嵌 dependency count 与 self-reset flag，任务完成后 TMU 自动把 dependency count 拷回 current count，使条件循环（Conditional Loop 610）的节点可反复就绪执行，无需软件重发初始化命令。两者共同目标一致：把"重复执行"的控制开销从 host 软件路径移入设备前端硬件；
- **US 2021/0149719 A1（可执行图修改）**：NVIDIA 允许对已实例化的可执行图做运行时修改，同样服务于"图结构在设备侧演化而无需 CPU 重建命令流"。AMD 侧的对应面是 [0041] 所述"运行时修改已有 IB 中命令/新建 IB"的异步写入能力。

**粒度与灵活性差异**：AMD 迭代 IB 是**命令流内迭代**——循环体是整个 IB（连续命令组），循环次数 iteration count 416 静态写入、终止条件即"计数到"，逐迭代差异靠静态谓词掩码（每条命令标注在哪些迭代号执行）表达；文本未提供基于运行时数据（收敛判定等）的动态退出或迭代间数据反馈。NVIDIA 是**任务图节点 + 依赖计数复位**——循环粒度是图中节点（任务），循环由节点间依赖边与 self-reset 支撑，文本还提及条件分支/收敛条件可由软硬件求值（如任务 C 未收敛则把任务 A 重新加入 Active List）。因此：AMD 方案实现简单、与既有 IB/PM4 体系无缝叠加，适合"固定次数、逐遍换参数"的图形/计算模式（立体、foveated、tile 渲染）；NVIDIA 方案粒度更细（单任务）、控制更动态（依赖驱动、可条件收敛），但需要任务描述符/任务图这一更重的执行模型。前者是"给命令缓冲加 for 循环"，后者是"给任务图加硬件循环边"。

## 7. 评价与启示

**技术重要性**：
- 精准解决"重复命令流"的提交开销：把 N 次重复 + 逐次差异压缩为一次 IB 写入 + 一条 indirection command，CPU 提交量从 O(N×命令数) 降为 O(1)；文本的立体渲染例（[0051]）直观展示了不迭代时渲染命令需写两遍的代价；
- 三字段 metadata（flag/count/predication）是最小完备的循环抽象：使能、次数、逐迭代命令掩码，使 CP 获得类似"带谓词的 for 循环"的命令流解释能力，且与既有 IB 嵌套机制（[0039]）正交兼容；
- 与 IB 的"异步预写"（[0041]）结合后，应用可在初始化期备好迭代模板，运行期近乎零 CPU 参与，是 CP 自治化执行（减少 CPU 往返）链条上的重要一环——它和 IB 复用、命令缓冲预取等特性共同构成 AMD 前端"少打扰 CPU"的设计主线。

**局限性（基于专利文本可推断）**：
- 迭代次数为静态元数据，终止条件只有"计数到"，文本未描述数据驱动的动态退出（如收敛判定、运行时条件跳转），与 NVIDIA 任务图侧可求值收敛条件的路径相比控制流表达力较弱；
- predication 是逐命令的静态掩码，粒度是"命令 × 迭代号"，文本未涉及迭代间状态传递或参数递增（如每迭代自动偏移地址），差异化仍限于掩码选择的离散命令；
- 三个实施例全部为图形渲染场景；虽然 compute command 在命令类型之列（[0037]，可覆盖视频/物理模拟/计算流体力学等计算任务），文本并未直接提及机器学习类迭代负载——该推广属合理外推而非原文明示；
- 提取文本存在多处标号/文字笔误（见 3.2 节末标注），且未给出 metadata 的具体编码、位宽与 PM4 命令格式等实现细节。

**对理解 AMD CP 自治化的价值**：本专利是观察 AMD CP 从"命令转发器"走向"命令流解释器"的典型样本：IB 机制早已把命令本体搬离 CPU 路径，本专利进一步把**控制流（循环）**也搬离 CPU 路径，使 CP 在不回 CPU 的情况下完成多遍执行与逐遍命令筛选。结合审查员引用的 Intel US 11,232,531 B2（图形前端循环处理）可见，"硬件前端原生支持命令流循环"是多家 GPU 厂商同期的共同演进方向；对研究者而言，本专利提供了 AMD 侧该方向最直接的公开证据与数据结构定义（iterative flag / iteration count / predication metadata）。
