## 2. 发明背景与待解决问题

**应用场景**（[0001]）：传统处理系统含 CPU 与 GPU（或集成为 APU）。GPU 上的处理由 CPU 处理的 API 调用（如 draw call，绘制调用）发起：draw call 调用 user mode driver（UMD，用户态驱动），UMD 生成命令写入 command buffer（命令缓冲区），命令再写入 queue（队列，或 ring buffer，环形缓冲区），随后**写一次与该队列关联的 doorbell（门铃）**以指示 GPU：队列中已有可执行的命令缓冲区。scheduler（调度器）监视映射给它的那组队列的 doorbell；某映射队列的 doorbell 被写入时，调度器把该队列头部的命令缓冲区调度到 GPU 执行。

**待解决问题**（分条）：

1. **队列数多于 doorbell 数**：任意时刻只有队列的一个子集被映射（mapped）到调度器，其余为未映射队列（unmapped queues）；调度器不监视未映射队列的 doorbell（[0001]、[0020]）。
2. **未映射队列对调度器不可见**：若命令缓冲区到达一个此前为空的未映射队列，调度器无从知晓，工作无法被调度（[0001]）。
3. **两难权衡**：对空的未映射队列持续轮询（polling）doorbell 开销过高；但完全不监视又导致命令缓冲区的调度延迟不可控。本专利开篇即声明其目标是"平衡对空的未映射队列 doorbell 的低轮询开销需求与对送达未映射队列的命令缓冲区的低调度延迟需求"这对竞争要求（[0009]）。

**核心方案一句话**：把多个未映射（空）队列以一对多方式映射到一个 aggregated doorbell（聚合门铃），由硬件 doorbell monitor（门铃监视器）监视聚合门铃，一旦被写入就向调度器发中断，调度器再轮询该聚合门铃下的队列集合找出变为非空的队列并调度其命令缓冲区。

**处理系统 100（FIG. 1）**：CPU 105（执行 draw call 等指令）、GPU 110、memory 115（DRAM/SRAM/非易失 RAM 等），经 interface 120（可为 PCI/PCI-E 总线，也可为桥接器/交换机/路由器等）互连。CPU 侧运行 applications 125、graphics API 130、user mode driver 135、kernel mode driver（KMD，内核态驱动）128。GPU 110 经 interface 120 接收 command buffer 140，其中存有供多条并发 graphics pipelines（图形流水线）141、142、143 执行的命令。queues 145、146、147 与流水线 141–143 一一对应，暂存各自的命令缓冲区；命令缓冲区按 round-robin（轮询）、随机或其他算法分发到各队列（箭头 150/151/152）。scheduler 155 把队列 145–147 头部条目的命令缓冲区调度到对应流水线执行。

**doorbell 集合 160**：指示队列 145–147 空/非空；一些实施例实现为 memory-mapped interrupts（内存映射中断）。驱动（KMD 128 或 UMD 135）用一个简单指针写 doorbell，无需库调用。集合 160 含两类：与队列一对一映射的普通 doorbell；与队列子集一对多映射的 aggregated doorbell（聚合门铃），分配给不含任何命令缓冲区的空队列。doorbell monitor 165 监视聚合门铃，并在其关联的空队列变为非空时产生中断。因这类中断预期相当稀少，轮询开销不会显著影响整体性能（[0016]）。

**调度系统 200（FIG. 2）**：scheduler 205 调度队列 210–220（共 11 个）中的命令缓冲区；doorbells 225–230（共 6 个，内存映射中断实现）划分为第一子集 235 与第二子集 240：
- 第一子集 235（一对一）：queue 210→doorbell 225，211→226，212→227，213→228；
- 第二子集 240（聚合，一对多）：空队列 214–217→聚合门铃 229，空队列 218–220→聚合门铃 230。
队列数（11）多于 doorbell 数（6），只有部分队列能享受一对一映射。系统另含 mapped queue list 250（映射队列列表，记录 210–213）、unmapped queue list 255（未映射队列列表，记录 214–220）与 pool 248（命令缓冲区池，供后续调度）。单个聚合门铃挂载的空队列数可多可少（[0020]）。

### 3.2 关键机制详解

**（1）映射队列路径**：scheduler 205 直接监视第一子集 235 的 doorbell 225–228；任一被写入，即调度其映射队列头部的命令缓冲区（如 doorbell 225 被写→调度 queue 210），或将命令缓冲区加入 pool 248 供后续调度（[0021]）。

**（2）聚合门铃的"编码"——一个 doorbell 如何标识多个队列**：聚合门铃本身**不携带队列标识**，其语义是"所挂子集中至少有一个空队列收到了命令缓冲区"。写 doorbell 229/230 只会触发硬件 doorbell monitor 245 产生中断，调度器不直接监视第二子集 240。到底是哪个队列变非空，由调度器收中断后**轮询子集内每个队列**（比较各队列 read/write pointer，读写指针）来判定（[0021]）。即用"1 bit 事件 + 软件/调度器索引扫描"替代"每队列一根信号线"，把 doorbell 从每队列一个虚拟化为多队列共享。

**（3）中断处理与轮询流程（FIG. 3，方法 300）**：305 硬件 doorbell monitor 以一对多关系监视映射到空队列子集的聚合门铃 → 310 检测到某聚合门铃被写（表明子集中某队列已收到命令缓冲区）→ 315 产生中断 → 320 调度器检测到中断，轮询该聚合门铃关联的未映射队列。轮询的细化步骤（[0025]）：先**清除（clear）聚合门铃**，遍历未映射队列找出收到命令缓冲区的队列，从该队列弹出（pop）命令缓冲区，然后**再遍历一遍**以捕获清除门铃之后又被写入的队列；若发现这样的队列，则重写聚合门铃并重复方法 300 → 325 调度非空队列的命令缓冲区执行，或加入命令缓冲区池。

**（4）映射/未映射状态的表示与迁移（FIG. 4，过程 400）**：每个队列有一个 index 418（索引）记录状态。第一状态 410（映射）：write pointer 420 与 read pointer 425 指向不同条目→队列非空，队列映射到第一子集 doorbell，其条目标识位于 mapped queue list 430，index 418="0"。第二状态 415（未映射）：写指针与读指针相同→队列为空，队列从 doorbell 解除映射，条目移入 unmapped queue list 435，index 418="1"，队列转而与聚合门铃关联（[0026]–[0028]）。队列通过在两个列表间增删条目（修改关联 index）实现迁移；调度器用 mapped queue list 250 决定监视哪些 doorbell；队列变空时从 250 移到 255，迁移前先禁用该 doorbell 的取数（disable fetching）（[0022]）。

**（5）解除映射的竞态防护（FIG. 5，方法 500）**：505 调度器检测到某个一对一映射的 doorbell 的队列为空 → 510 禁用该 doorbell 的取数，避免调度器试图从空队列调度 → 515 修改 index（如 "0"→"1"）把队列移出映射列表、移入未映射列表并关联聚合门铃 → 520 修改 index 后比较该队列的读/写指针，验证队列是否仍为空 → 525 若仍相等（仍为空）→ 530 完成解映射；若调度器希望在队列有工作时得到通知，则向 CPU 上的 KMD（如 128）发请求，挂起（suspend）该队列并让其 doorbell 在特权模式下切换到 aggregated mode（聚合模式）；若读写指针不等（解映射期间队列又被写入）→ 535 把非空队列重新映射到 doorbell。该"先改 index 再复核指针"的顺序用于避免解映射过程中命令缓冲区恰好写入造成的竞态（[0022]、[0030]–[0031]）。

**（6）挂起握手的另一视角（[0017]）**：调度器向 KMD 128 请求挂起队列后继续正常工作；host CPU（原文此处写作 "host CPU 150"，疑为 105 之笔误）把被挂起队列在集合 160 中的 doorbell 切换到特权模式的聚合模式，然后以中断或数据包应答；调度器收到应答后比较读写指针——相等则继续正常流程，不等则把队列切回 active mode（活动模式）并重新关联 doorbell。

**（7）时间片到期的入口（FIG. 6，方法 600）**：进程按 time quantum 拥有（"own"）队列。605 时间片到期 → 610 禁用 doorbell 取数 → 615 比较读写指针判断队列是否空：空→经 node 1 汇入 FIG. 5 的 block 515（走解映射流程）；非空→ 620 队列保持/重新映射到 doorbell（[0010]、[0032]–[0033]）。

**（8）双地址带与优先级变体（[0018]、[0010]）**：一些实施例提供两个地址带（address bands）监视 doorbell：default bands（默认带）与 alternate aperture bands（备用孔径带）；聚合门铃监视备用孔径而非默认带。当空列表中的队列收到工作时，调度器请求 KMD 临时挂起该队列，同时把其 doorbell 指针地址从备用孔径改回默认带，且无需等待确认即继续标准序列。另一些实施例中，多个聚合门铃各自具有不同优先级，或对应未映射队列的不同属性/特性，未映射队列据此分配到不同聚合门铃。

## 4. 权利要求摘要

共 20 项权利要求，3 项独立权利要求（claim 1 装置、claim 10 方法、claim 17 方法）。

**独立权利要求 1（装置）**：一种装置，包括：多个队列，用于在执行前存储命令缓冲区并供给对应的多条流水线；至少一个第一 doorbell，与至少一个第一队列一对一映射；第二 doorbell，与队列的一个子集一对多映射；doorbell monitor，在该子集中的空队列变为非空队列时产生中断；scheduler，响应中断轮询该子集，并把非空队列的命令缓冲区调度执行或加入池中以供后续执行。

**独立权利要求 10（方法）**：在映射到第一 doorbell 的一组（接收前均为空的）队列中的第一队列处接收命令缓冲区；响应第一 doorbell 被写（指示第一队列收到命令缓冲区）产生中断；响应中断轮询该组队列以识别第一队列；调度第一队列的命令缓冲区执行或加入池中供后续执行。

**独立权利要求 17（方法）**：响应在一组空队列之一处收到命令缓冲区而写第一 doorbell；响应该写入产生中断；响应中断轮询该组空队列以识别收到命令缓冲区的第一队列；调度其命令缓冲区执行或加入池中。

从属权利要求按主题分组：

- doorbell 写入语义（claim 2 / 11）：命令缓冲区加入映射队列时写第一 doorbell；加入子集中任一队列时写第二（聚合）doorbell；
- 轮询细化（claim 3）：子集含多个队列时，调度器逐一轮询以确定哪个队列变为非空；
- 双列表结构与迁移（claim 4、5 / 12、13 / 18、19）：存储部件保存第一列表（一对一映射关系）与第二列表（一对多映射关系）；队列变空时从一对一列表移到聚合列表（装置视角），或从一对一列表移入聚合门铃组（方法视角）；
- 解映射操作（claim 6、7 / 14、15）：队列变空或时间片到期时禁用 doorbell 取数并发起 unmap；通过修改指示映射/未映射的 index（或挂起队列）发起解映射，验证解映射完成后再迁移列表；
- 读写指针校验（claim 8 / 16 / 20）：修改 index 后写指针等于读指针，才把队列与聚合门铃关联（claim 20 未限定"修改 index 后"）；
- 多聚合门铃优先级（claim 9）：多个聚合门铃分别对应不同优先级、不同属性或不同特性的空队列子集。

## 5. 与专题主题的关系

本专利属于专题「AMD GPU 前端全链路（CP/IB/PM4 + doorbell/HQD + SPI/SQ wave 分发）」中的 **doorbell/HQD 提交环节**，位于用户态驱动写 doorbell 与 CP/HWS 调度之间。

(a) **在 AMD 前端链路中的位置**：AMD 前端的经典提交路径为 UMD 把命令写入 command buffer（对应 IB，indirect buffer，以 PM4 包格式编码）→ 写入队列（ring buffer，硬件上由 HQD，Hardware Queue Descriptor，硬件队列描述符承载）→ 用户态写 doorbell 页中的对应槽位通知 GPU。本专利正处该路径的"通知—调度"交界：它改造的是 doorbell 资源的分配与监视方式——doorbell 集合 160/225–230、doorbell monitor 165/245 与 scheduler 155/205（对应 AMD 架构中的 CP/HWS 硬件调度器一侧）；专利文本本身未使用 "HQD"、"doorbell page"、"PM4"、"CP" 等字样（其调度器为通用表述），队列即 AMD 语境下由 HQD 支撑的硬件队列，此为据公开资料的对应，非专利原文。

(b) **与 NVIDIA 上游模块研究的对照**：
- doorbell 对应 NVIDIA US20230153146A1 中的 put pointer（写指针提交）+ notifier（通知）机制：两者都是"软件更新队列指针后用一次轻量内存写通知硬件"的提交原语；AMD 用 memory-mapped doorbell 写，NVIDIA 用 put pointer + notifier 写。
- 本专利解决的"队列数远超硬件提交槽位（doorbell/监视端口）"问题，与 NVIDIA US10489056B2 中 SM 队列管理器面对的同类资源稀缺问题（硬件跟踪资源远少于软件队列/任务数）在结构上同构：二者都采用"少量硬件槽位 + 动态映射/解映射 + 空闲资源回收"的虚拟化策略。
- 聚合门铃的本质是把 doorbell 从"每队列一个"虚拟化为"多队列共享 + 软件索引"：doorbell 写退化为一个共享事件信号，队列身份由调度器轮询读写指针恢复；配合 mapped/unmapped 双列表与 index 418，AMD 用一对多映射 + 中断 + 懒轮询，在不增加 doorbell 硬件数量的前提下把可服务队列数扩展到远超 doorbell 数。

## 7. 评价与启示

**技术重要性**：
- 精准命中 GPU 多任务/多租户场景的结构性矛盾：硬件 doorbell（及其背后的 HQD 取数端口、调度器监视资源）数量有限，而软件层队列数随进程/上下文/优先级膨胀。聚合门铃以极小的硬件增量（一个 doorbell monitor + 中断线）把 doorbell 语义从"点对点"升级为"共享总线式"，是可扩展队列管理的典型虚拟化手段；
- 工程细节完整：中断后"清门铃→扫描→pop→再扫描"的双遍历设计（[0025]）处理了解除映射窗口内的竞态写入；"先禁用取数、改 index、再复核读写指针"的顺序（FIG. 5）与 KMD 挂起握手（[0017]）体现了对 host 侧并发写入的防护意识；
- 多聚合门铃按优先级/属性分组（claim 9）与时间片到期触发解映射（FIG. 6）表明该机制可直接服务于 QoS 与多租户调度策略。

**局限性（基于专利文本可推断）**：
- 聚合门铃不携带队列标识，中断后必须扫描整个子集，子集越大轮询代价越高；文本仅以"中断预期稀少"论证开销可接受，未给出量化分析；
- 映射/解映射依赖 host CPU 侧 KMD 配合（挂起请求、doorbell 模式切换、地址带切换），跨 CPU–GPU 的握手时延未讨论；备用孔径/默认带切换路径"无需等待确认"（[0018]）的正确性依赖特定顺序假设；
- 提取文本存在若干笔误：FIG. 4 图题"from a list of unmapped queues to a list of unmapped queues"（应为 mapped→unmapped）、[0017] "host CPU 150"（应为 105）、[0016] "assigned to empty queues that are not include any command buffers"（语法残缺），均以正文语义为准；
- 文本未涉及 doorbell 页的物理布局、doorbell 写的地址编码细节，也未提及 CP/HWS/HQD 等 AMD 具体实现名词，属于与实现解耦的机制层专利。

**对理解 AMD doorbell 虚拟化/多租户 GPU 的价值**：本专利是观察 AMD 如何在硬件资源受限下支撑"海量队列"的关键文献：它揭示了 doorbell 并非静态的一对一信号，而是可被动态重分配、聚合、按优先级分组的虚拟化资源；mapped/unmapped 双列表 + index 的状态机为理解 AMD KFD/ROCr 运行时中大量队列（每进程多队列、多进程共存）如何复用有限 doorbell/HQD 资源提供了硬件侧依据。与 NVIDIA 侧 TMU/SM 队列管理专利对照阅读，可以看出两家前端设计的共同范式：稀缺硬件提交槽位 + 软件可见的更大队列空间 + 硬件/驱动协同的动态映射，差异仅在通知原语（doorbell vs put pointer/notifier）与执行主体（CP/HWS vs TMU/SM queue manager）。
