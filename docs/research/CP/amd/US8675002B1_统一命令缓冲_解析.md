## 2. 发明背景与待解决问题

**应用场景**：multi-GPU（多 GPU）渲染系统。ATI/AMD 已提供 CrossFire 接口把两块及以上 display adapter（显示适配器）互联，由多个 GPU 同时执行 3D rendering（三维渲染）等复杂程序，并在多处理器间做负载均衡（load balancing）。GPU 的操作由 command buffer（命令缓冲）驱动——其中存放指定 GPU 如何渲染场景的 instruction（指令），复杂场景下缓冲可以非常大。

**待解决问题**（按文本分条）：

1. **命令缓冲重复**：现有多 GPU 方案中每个 GPU 指向自己独立的 command buffer，各缓冲之间存在大段重复内容；CPU 为每个 GPU 生成独立缓冲少要付出双倍工作量（"at least twice as much work"），且重复不止于初始写入，还包括 kernel 内对每个缓冲的 patching（打补丁）及相应 cache flush（缓存刷新）；
2. **负载分配僵化**：传统系统无法按各 GPU 能力与屏幕各区域的实际渲染需求动态分配负载。文本以飞行模拟器截图 400（FIG. 4）为例：下半部分 402 是 2D 静态仪表，负载小；上半部分 404 是快速变化的 3D 世界，负载大——传统方案只能均分（如 FIG. 3A 的四等分）；
3. **驱动栈复杂**：传统多 GPU 系统要求专门设计的 "multi-GPU aware"（多 GPU 感知）驱动，且该感知贯穿整个驱动栈，增加代码复杂度与开发成本。

**核心方案一句话**：让多个 GPU 共享同一个 unified command buffer（统一命令缓冲），用 predication（谓词化/条件标记）给每条指令打上目标 GPU 标签，配合 VRAM 同址布局、remap table（地址重映射表）一致性与共享的 command retirement（命令退休）时间戳，使 CPU 只需写一次缓冲、各 GPU 只读取属于自己的指令。

### 3.2 关键机制详解

**（1）统一命令缓冲与谓词标记（FIG. 2A）**：system memory 202 中只有一个 unified command buffer 204，GPU A 206 与 GPU B 208 各自带 command ring buffer 210、212 并共同访问该缓冲。缓冲内使用 conditionals（条件），核心是 predications（谓词化指令）：它为每条指令提供 tagging（标记），指明该指令是 designated for（指定给）GPU A 206 还是 GPU B 208。所有 GPU 都会"收到"全部指令，但只有被标记的处理器真正 read（读取）该指令；若指令关联 GPU A，则取第一组命令执行第一组任务，关联 GPU B 则取第二组。方案不限于两个 GPU，也不限于 GPU（可为 CPU 或 CPU/GPU 混合）。

**（2）VRAM 同址布局与识别标签（kernel 层实现）**：统一缓冲实现在 system memory 的 kernel driver layer（内核驱动层），应用与客户端 3D 驱动无需感知多 GPU 配置。kernel 驱动保证 VRAM 中的对象在所有 GPU 上位于完全相同的位置——仅 frame buffer（帧缓冲）与 address-remapping table（地址重映射表）例外；master GPU 上的所有 allocations/frees/reserves（分配/释放/预留）都在 slave GPU 上复制。具体做法：为每个 GPU 预留一段 VRAM 范围，每段含一个大小为 N（GPU 总数）的 boolean array（布尔数组）GPU0…N-1，每个位置 4 字节（一个整数）代表一个 GPU，仅一个位置为 true(1)，其余为 false(0)——"GPU i = 1 当且仅当 GPU index 是 i"。例中 GPU A 206 对应 location 0，GPU B 208 对应 location 1。这些布尔数组即权利要求所称 identification tag（识别标签），谓词机制直接引用它。同址预留还保证纹理等资源共享同一虚拟地址（如石墙纹理在所有 GPU 上存于同一位置），消除多缓冲中的重复内容。

**（3）Remap table（重映射表）一致性**：remap table 是"每个 GPU 的系统内存视图"，remap table entry（表项）在所有 GPU 的 remap table 中映射到相同位置，且指向 system memory 而非 GPU local memory。例：GPU A 从 remap table 地址 10000 读纹理，该表项指向系统内存物理地址 0x1234ABCD；同一命令在 GPU B 上执行时，GPU B 的表项 10000 必须写入相同内容，否则 GPU B 会读到不同纹理。

**（4）命令退休与时间戳共享**：所有 GPU 实例共享 command buffer retirement information（命令缓冲退休信息），依托 synchronized commands（同步命令）的 command retirement 概念——完成的命令被打上 timestamp（时间戳）标记完成时刻；缓冲复用前先检查时间戳确认命令已完成。所有 GPU 收到相同的命令时间戳值，实现方式为：(a) GPU i 把自己的 retirement timestamp 写入 retirement buffer entry i；(b) client（客户端）在所有时间戳都退休（即所有 GPU 都处理完该命令缓冲）之前不退休该命令缓冲——即使系统只有单个 GPU 实例也如此。

**（5）虚实页映射（FIG. 2B / 2C）**：virtual to physical page mapping configuration 220 支持"单一命令缓冲、单一虚拟地址、底层物理资源位于不同物理地址"：GPU 222 的内存请求经 memory controller 224 查询 virtual mapping table 226，虚拟项 V0–Vn 映射到 physical memory 228 的页 P0–Pm，页无需连续、顺序也可不同。在 multi-GPU VM scenario 240 中，每个 GPU 有自己的 VM table（242 属 GPU 0，244 属 GPU 1）：凡被 command buffer B 246 引用的地址（如 Virt_i 指向命令缓冲 B 246、Virt_k 指向 texture A 248），两表的第 i 项必须映射到同一物理对象；未被引用的项（Virt_m）可各指各的（random X 250、random Y 252，可为 vertex buffer、纹理、其他命令缓冲等）。进一步放宽：物理位置不必相同，只要内容相同即可（如同一纹理分别载入两块 GPU 的 local memory）。这一机制使统一缓冲"以尽量少的 predication"工作。

**（6）命令类型：direct vs. indirect 环（FIG. 2D）**：direct command buffer ring 260 在环内包含全部指令与数据（instruction list 261 中的直接命令 cmd0–cmdn）；indirect command buffer ring 262 的 instruction list 263 除直接命令 cmd0–cmdn 外还含 indirect references（间接引用）ind0–ind1，它们进一步指向 indirect command buffer 264、266、268，每个还可含间接引用，形成多级间接（multiple levels of indirection）。文本明言：间接缓冲是简化统一命令缓冲实现的一种途径。

**（7）GPU 读取与执行流程（FIG. 2E）**：multi-GPU ring buffer configuration 270 中，system memory 272 旁设 GPU 1 的 buffer ring 274 与 GPU 2 的 buffer ring 276，另有 system resources 278（如附加命令缓冲）。CPU（未画出）向环中填充新命令并更新相应 write pointer（写指针 WPTR1/WPTR2）；GPU 1、GPU 2 分别从各自的环 274、276 取指（fetch）并更新自己的 read pointer（读指针 RPTR1/RPTR2）。由于 predication，同一命令缓冲下各 GPU 实际工作量可能不同，故每个 GPU 必须维护自己的读指针，两 GPU 异步运行。使用间接命令时，环 274/276 中的不同表项可指向 system memory 272 内的同一资源（如 resource 280）；不同物理位置只要内容相同即视为等价。

**（8）其余两个实施例（简述）**：
- **Dynamic Feedback Load Balancing（动态反馈负载均衡）**：基于反馈动态调整 Scissor orientation（裁剪方向）与 coverage/rendering ratio（覆盖率/渲染比）。组件包括：按时间窗测量各 GPU 渲染时间；预定义 "optimal"（最优）配置（可按应用识别后作为起点）；static region analysis（静态区域分析，屏幕 500 划分为 16×16 像素块，用 SAD（sum of absolute differences，绝对差之和）识别低变化区域 504 与高变化区域 502）；scene change analysis（场景变化分析，场景剧变时放弃渐进微调、直接切换到已知最优配置，渲染配置可用 XML 形式保存，含应用名与 SAD 特征哈希签名）；history buffer/table（历史表，记录边界调整轨迹，游戏结束后统计出主导配置存为预定义配置，并可学习每个用户的游玩风格）。方法 600（FIG. 6）：602 判定有无预定义配置→无则 604 做静态区域/场景变化分析定初始配置，有则 606 按用户优先级应用→608 实时收集渲染统计（FPS/flip 数、GPU 负载率、每秒空闲时间、每秒退休命令数）→610/611 检测大幅场景变化，是则换新分区配置，否则 612 微调并 614 记入历史表→616 游戏结束则 618 保存主导配置。
- **Seamless Integration of Multi-GPU Rendering（无缝集成）**：系统 700 中，OS render engine 702（OpenGL/Direct3D 等）之下设置 abstraction layer 704（抽象层），把传统"multi-GPU aware"驱动的智能全部下沉于此；每个 GPU 都以为自己是唯一在渲染该场景的 GPU，从而可复用非多 GPU 感知的 turn-key（现成）驱动。模块包括 initial set-up 706（保证各 GPU memory map 基本一致，并支持 Scissoring）、application profile 708、scene analysis 710、render statistics 712、optimize configuration 714。Scissoring（FIG. 8）：master GPU A 802 与 slave GPU B 804 各自实际渲染整幅 image 806，但经 mask（掩蔽）各只写出半幅 808/810 再合成；Scissor 命令直接置于命令缓冲中，配合条件执行——文本示例："Set scissor for GPU0 coverage / If (isGPUi()==1) Set scissor for GPUi coverage / …"，因每个 GPU 有唯一 boolean identifier（布尔标识），任一 GPU 实例只有一个条件成立。文本明确指出："the command processor should be able to handle conditionals in the command stream"（命令处理器必须能处理命令流中的条件）。Scissoring 还可实现不同渲染比率，类似 AFR（alternative frame ratio，交替帧比率）：快 GPU 渲染两帧、慢 GPU 渲染一帧。最优搜索在测量窗内增量调整三类参数：(i) Scissor Rectangle（裁剪矩形，水平/垂直）；(ii) 每个 GPU 实例的覆盖率百分比；(iii) 每个 GPU 的 AFR 比率（1:1:1:1、2:1:1:2…），并可用"上次最优值邻域限定搜索"或按应用知识限定参数来加速。

## 4. 权利要求摘要

共 16 项权利要求，6 项独立权利要求（claim 1、2 方法；claim 9、15 计算系统；claim 11、13 计算机可读介质设备）。

**独立权利要求 1（方法）**：为第一处理器分配的第一 VRAM 区预留第一范围、为第二处理器分配的第二 VRAM 区预留第二范围，两范围在各自 VRAM 区中位置相同；在两 VRAM 区各预留第三范围并存入相同数据；在第一 VRAM 区第一范围存入标识第一处理器的 identification tag（识别标签）；向命令缓冲发送指令，其中至少一条指定给第一处理器，且该指令携带使用上述识别标签的 designation tag（指定标签），以指明应由第一处理器读取。

**独立权利要求 2（方法）**：与 claim 1 类似的预留/同数据/识别标签步骤外，增加执行侧动作：第一处理器从 CPU 侧访问该命令缓冲（缓冲也为第二处理器可访问）；第一处理器接收其中指定给自己的指令（第二处理器同样会收到该指令）；且只有第一处理器读取该指令——读取依据即使用识别标签的指定标签。

**独立权利要求 9（计算系统）**：系统内存含命令缓冲，配置为接收中央处理器指令并在收到预留请求时预留第一/第三范围……；第一处理器可访问该缓冲（第二处理器亦可），至少一条指令含用识别标签指明仅由第一处理器读取的指定标签。

**独立权利要求 11 / 13（计算机可读介质设备）**：分别承载 claim 2（含访问/接收/只读步骤）与 claim 1（含发送指令步骤）的操作集合。

**独立权利要求 15（计算系统）**：系统内存含接收中央处理器指令的命令缓冲；第一、第二处理器耦合并访问该缓冲，至少一条指令被指定仅由第一处理器读取；第一 VRAM 区第一范围（应预留请求分配）存识别标签；第二 VRAM 区第二范围与第一范围位置相同；两 VRAM 区第三范围存相同数据；指定标签使用识别标签指明读取者。

从属权利要求按主题分组：

- 执行语义与条件机制（claim 3、4、5 / 依附 claim 2）：指令被唯一处理器读取后执行预定任务集；命令缓冲使用 conditionals（条件）；条件包括 predications（谓词化）；
- 缓冲与地址组织（claim 6、7、8）：命令缓冲包含第一/第二 VRAM 范围；缓冲与两处理器之间存在 virtual to physical page mapping scheme（虚实页映射方案）；缓冲位于两处理器均可访问的系统内存中；
- 处理器类型限定（claim 10、12、14、16）：处理器为 GPU。

## 5. 与专题主题的关系

本专利属于专题「AMD GPU 前端全链路（CP/IB/PM4 + doorbell/HQD + SPI/SQ wave 分发）」，与 NVIDIA TMU 上游模块研究对照如下：

**(a) 在 AMD 前端链中的位置**：本专利的 command buffer 即 AMD 术语中的 pushbuffer（推送缓冲）——它是 CP（Command Processor，命令处理器）读取的命令流容器。图中各要素与 AMD 前端概念一一对应：GPU A/B 的 command ring buffer 210/212（FIG. 2A）与 buffer ring 274/276（FIG. 2E）即 CP 取指的 ring buffer（环形缓冲）；RPTR/WPTR 读/写指针是 ring buffer 的经典控制寄存器对（CPU 写 WPTR 投递命令、GPU 推进 RPTR 消费命令）；FIG. 2D 的 direct ring（直接环）与 indirect ring（间接环，ind0–ind1 指向 indirect command buffer 264/266/268、支持多级间接）正是后来 GCN "ring buffer + IB（Indirect Buffer，间接缓冲）" 两级取指结构的雏形表述；而说明书"命令处理器必须能处理命令流中的条件"一句，直接对应 PM4 命令包集中的条件执行/谓词类包——本专利把 predication 用作多 GPU 间的指令分发过滤手段。换言之，本专利位于前端链路最上游：命令流的组织、投递与筛选，先于 CP 解析与 wave 分发。

**(b) 与 NVIDIA 的对应关系**：NVIDIA pushbuffer（US9489763B2 中"存指向命令数据结构的指针的命令流缓冲"）在 AMD 侧的功能对应物即本专利的命令缓冲/环缓冲；尤其 FIG. 2D 的 indirect command buffer ring（环内主体是 indirect references，指向挂在 system memory 中的次级命令缓冲）与 NVIDIA "pushbuffer 存指针、命令数据另存" 的形态几乎同构，FIG. 2E 进一步说明不同环表项可指向系统内存中的同一资源（resource 280），即"指针共享、内容等价"的组织原则。两者的差别在于：NVIDIA 方向以指针间接化换取命令流的紧凑与可复用；本专利则以"单一缓冲 + 布尔识别标签 + 谓词筛选"换取多 GPU 间命令流的零复制共享。

**(c) "统一"思想与 GCN ring + IB 两级结构的关系**：本专利（申请 2010-06，早于 2012 年的 GCN）的"统一"是指多个 GPU 共享同一条命令流、靠 predication 分工——是"多执行主体共享一个缓冲"；GCN 则走向反面形态：每个引擎/队列拥有各自的 ring buffer + IB、经 doorbell/HQD 触发，是"多缓冲分属单引擎"。但两者共享同一技术基座：ring buffer 读写指针模型、indirect buffer 多级间接、命令流内条件执行。本专利可视为 AMD 在 CrossFire 多卡时代对命令流共享与筛选机制的系统性探索，其中"间接缓冲简化统一命令缓冲实现"的表述，是 ring+IB 两级结构在前 GCN 时期专利文献中的明确早期记录。

## 7. 评价与启示

**技术重要性**：
- 直击多 GPU 渲染的命令流供给瓶颈：把"每 GPU 一份缓冲、CPU 双倍写入 + 重复 patching + 重复 cache flush"压缩为"一份统一缓冲 + 硬件谓词筛选"，收益随缓冲规模线性放大；
- 配套机制成体系：VRAM 同址预留 + 布尔识别标签解决"指令归属"，remap table 一致性 + VM table 映射解决"同一虚拟地址落到不同物理资源"，共享 retirement timestamp 解决"缓冲何时可复用"，三者闭环才能使统一缓冲正确运转；
- FIG. 2D/2E 对 direct/indirect 环与读写指针模型的描述，是 AMD 命令处理器前端（ring + IB、RPTR/WPTR）在专利文献中的少见公开表述，且明示"命令处理器须支持命令流内条件"，为理解 PM4 谓词机制的应用动机提供一手材料；
- 动态反馈负载均衡（时间窗测量 + 静态区域/场景变化分析 + 历史表学习）与抽象层无缝集成（让每个 GPU 以为自己是唯一 GPU）构成完整的驱动侧方案，其中 Scissor 命令直接嵌入命令缓冲、由命令处理器条件执行的做法，把负载均衡决策下放到了命令流本身。

**局限性（基于专利文本可推断）**：
- predication 筛选意味着每个 GPU 都要接收并遍历整条命令流，被过滤指令仍占用取指带宽与解析开销；文本自身也承认"to utilize a unified command buffer with as little predication as possible"是设计目标，说明谓词密度是成本项；
- 统一缓冲要求各 GPU 的 VRAM 布局（除 frame buffer 与 remap table 外）严格镜像、master 上的每次分配/释放都复制到 slave，内存灵活性受限；
- 方案面向渲染型多卡分工（Scissor/AFR），未涉及计算负载或片内多引擎（图形/计算/DMA 引擎）共享命令流的场景——后者正是 GCN 时代 doorbell/HQD 多队列模型要解决的问题；
- 提取文本质量限制：13 张附图页全部乱码，附图内文字（如 FIG. 5/6 中的 "SDI"、"CTZ" 等残片）无法复原，参考标号全部依赖说明书正文转述；首页受让人、审查员姓名及部分引用文献分类存在 OCR 错误，已在正文标注。

**对理解 AMD 前端的价值**：本专利是 ATI/AMD 在 2010 年前后对"命令缓冲是什么、如何被多个执行者共享"的一次完整阐述。它确认了 AMD 前端的基本事实：命令缓冲是 CPU 与 GPU 之间的唯一工作契约，其组织形式为 ring buffer（读写指针驱动）+ 可选多级 indirect buffer，命令流内建条件执行能力。把本专利与后来 GCN 的每引擎 ring + IB、doorbell 触发、HQD 队列硬件对照，可以清楚看到 AMD 前端从"多 GPU 共享一条命令流（谓词分工）"到"多引擎各持一条命令流（队列分工）"的演化轨迹，也为对照 NVIDIA pushbuffer/TMU 体系（命令流缓冲存指针、任务描述符化执行）提供了 AMD 侧的锚点。
