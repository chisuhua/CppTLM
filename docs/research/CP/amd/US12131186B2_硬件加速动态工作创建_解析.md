## 2. 发明背景与待解决问题

**应用场景**：GPU kernel 在执行中动态产生新工作（device-side dynamic work creation，设备侧动态工作创建）：如父任务遍历图时发现新节点需 spawn 额外工作、递归/不规则并行、以及 C++ future/executor 式异步编程模型下的 CPU/GPU 任务混合调度——即 work graph / dynamic parallelism（动态并行）类需求。

**待解决问题**（据 BACKGROUND 与 col.4）：

1. 现有 device-side enqueue 技术（点 CUDA dynamic parallelism、OpenCL/ROCm 的 device enqueue）把子任务表示为 full kernel（完整内核），必须走一遍由 CPU 执行的完整 kernel launch 流程；
2. device-side enqueue 需把请求信息写入 memory 105 才能启动入队，GPU 与存储器逻辑/物理分离带来显著延迟；
3. 传统模型通常要求 parent task 先执行完毕才能 launch 子任务，无法与父任务并发 spawn；
4. 子任务以 kernel 为粒度，不能以 workgroup（工作组）或线程等更细粒度任务化。

**核心方案一句话**：在 GPU 内增设专用 coprocessor 160/210（协处理器）维护任务数据结构，直接接收正在 GPU 上执行的父任务的动态工作创建请求，在片上硬件完成子任务生成、事件等待、资源检查与分发，绕过 CPU 的完整 kernel launch 路径。

### 3.2 关键机制详解

**工作请求注入与传统路径绕过**：正在 processing elements 125 上执行的 parent task 通过由 coprocessor 服务的 API 调用（如 fork()）请求 spawn 新工作（805）；coprocessor 160/210 在父任务并发执行期间即响应请求生成 child task。此绕过两条传统路径：(a) 无需把入队请求写回 memory 105 等 CPU 做完整 kernel launch；(b) 子任务不必是 full kernel，可以是被加入父任务执行上下文的 workgroup 或更细粒度。coprocessor 甚至可以运行 OS microkernel（操作系统微内核）来调度任务、管理任务状态（code/data pointer、register state）、按时间片中断运行任务，支持阻塞系统调用与 demand paging。

**任务池与事件驱动分发（FIG. 2–5）**：父任务在 coprocessor 上注册 task pool 225/305（405）；coprocessor 创建池与 event queues（410）并把队列与信号关联（415）——completion object 330/335/340 可为 HSA signal（Heterogeneous System Architecture 信号，opaque 64-bit handle，实质写预定内存位置）、interrupt 或内存地址 polling。coprocessor 持续监视 completion signal（420），事件发生即检查 event queues 310/315/320 中被触发事件（425）、按优先级检查 tasks 325（505）、判断资源（510，计算单元数/空闲内存等），不足则释放资源（520，可抢占运行任务）后 dispatch（515）。分发形态即把 packet 260（AQL packet）入队 queue 235 并打 doorbell：scheduler 240（实施例为微控制器集合）检测到 doorbell 后提取包信息、经 SPI 245 调度到 shader 250；kernel 完成后 GPU 通知 SPI 245，其处理 EOP（end of pipe）包并把任务移出 queue 235。——coprocessor 正是以"反向注入"方式复用 AMD 标准前端（AQL queue + doorbell + scheduler + SPI），使子任务与 CPU 提交的工作进入同一条分发流水线。

**父子同步与父任务 deschedule（FIG. 8–9）**：spawn 请求（805）后 coprocessor 判断是否需同步（810）；需要则分配 completion signal（HSA signal）关联到父 kernel 执行上下文并更新 kernel 数据结构（815）。再决定是否 deschedule 父任务（820）：是则保存父上下文并释放资源（825，实施例以 CWSR，compute context wave save-restore 抢占机制实现）；否则父子并发。随后资源判定（830）→分配资源并分发子任务（905，coprocessor 与 SPI 协商创建新 workgroup、分配 register state、LDS space、GDS space、wavefront slots）；若需子同步（910）则子完成后 wake/reschedule 并向父发完成信号（915）；父未被 deschedule 则继续执行（925），已被 deschedule 则分配资源重新调度父（930）。

**future 与 self-enqueue（FIG. 6–7）**：为支持 C++ futures 式异步模型且避免 coprocessor 线程在 completion signal 上 spin，future 600 定为"function pointer 605 + argument pointer 615"（argument 内含 completion object 指针），实现为入队 continuation queue 的 continuation packet 625。coprocessor 把 future task 加入 continuation queue（705）、监视 function argument 指示的 completion object（710）；预定时间内未检测到（715-NO）则挂起该 future task（720）并 self-enqueue：生成带相同函数/参数指针 635/640 的 continuation future task 重新入队（730），迭代直至某实例检测到 completion object；检测到（715-YES）则把 future task 指示的任务加入 task queue（725），该任务可执行于 GPU 或 CPU。

**executor 编程模型**：coprocessor 可实现 C++ executors——thread pool executor、loop executor（维护 loop table）、serial executor、system executor（singleton + oldest-first 单队列保证 forward progress 防死锁）——并提供 spawn(Func&&) API；队列按 process/kernel identifier 虚拟化以避免 head-of-line blocking。说明书另引 continuation task 在先申请 Ser. No. 15/607,991（AMD IDF 160352，2017-05-30，"CONTINUATION ANALYSIS TASKS FOR GPU TASK SCHEDULING"）。

## 4. 权利要求摘要

共 20 项权利要求，3 项独立权利要求（claim 1 方法、claim 13 处理单元、claim 18 处理系统）。

**独立权利要求 1（方法）**：一种方法，包括：与处理器核上正在执行的 parent task 并发地 spawn 一个 child task；以及响应于识别父子任务之间需要同步，把强制执行该同步所指示依赖的 signal 关联到 parent task 的执行上下文。

**独立权利要求 13（处理单元）**：一种处理单元，包括：多个处理元件；存储任务的 queue；从 queue 调度任务到处理元件的 scheduling circuit；以及 coprocessor，用于与父任务并发执行期间 spawn 子任务，并在识别需要同步时把 signal 关联到父任务执行上下文。

**独立权利要求 18（处理系统）**：一种处理系统，包括：以发送 packet 向第二处理单元分发工作的 CPU；第二处理单元（GPU）含：对 CPU 包入队的 queue、从包中提取信息并向处理元件分发任务的 scheduling circuit、以及具备与 claim 13 相同 spawn/信号关联功能的 coprocessor。

从属权利要求分组：

- 子任务粒度与同步判定（2、3 / 14、19）：子任务加入父执行上下文；spawn 后判定是否需同步；
- 信号实现形式（4、15）：interrupts 或 monitored memory addresses；
- 父任务数据结构更新以反映子任务执行（5）；
- 父 deschedule 决策与上下文保存（6、7 / 16）：deschedule 或并发之决策；保存父上下文使其资源可供其他任务；
- 资源检查与分发（8、9、10 / 17、20）：资源充足性判定、不足时延迟分发、充足时分配资源并分发；
- 父任务恢复（11、12）：子完成后唤醒并重调度被 deschedule 的父，或让并发父继续执行。

## 5. 与专题主题的关系

本专利属于专题「AMD GPU 前端全链路（CP/IB/PM4 + doorbell/HQD + SPI/SQ wave 分发）」，并与 NVIDIA TMU 上游模块研究对照：

(a) **在 AMD 前端链路中的位置**：coprocessor 160/210 是 GPU 内部新增的前端代理。CPU 侧传统链路保持不变——CPU 215 写 AQL packet 入 queue 235、打 doorbell、scheduler 240（微控制器集合，CP 谱系）提取包、经 SPI 245 分发到 shader 250；但如今 shader 侧正在执行的 wavefront 可通过 coprocessor 服务的 API（fork()/spawn()）反向提出工作请求，coprocessor 把子任务以 packet 260 写回同一条 AQL queue 235 并触发 doorbell，或直接与 SPI 协商分配 wavefront slot/LDS/GDS——形成"shader → coprocessor → 前端队列/SPI"的反向注入，打破"CPU→CP→SQ"单向链路，把工作生成、依赖（completion object/HSA signal）与调度闭环在片上。

(b) **与 NVIDIA 的对应关系**直接对应 NVIDIA 的 work graphs/可执行图路线——US20210149719A1（可执行图修改）、US20230093254A1（任务图/work graph 执行）与 US11182207B2（TMU 硬件任务图、依赖描述符预取）：都让 GPU 在执行中动态生成后续工作而不回 CPU。两条路线差异：AMD 是"wavefront 直接请求 + coprocessor 写回队列"——子任务仍以 AQL packet/queue/doorbell 形态进入既有分发流水线、复用 HSA signal 机制，且可挂载 OS microkernel 与 C++ executor，通用性强；NVIDIA 是"任务描述符 + TMU 依赖解析"——TMU 在描述符内维护 dependency count/current count 与 Active List 并预取消费者描述符/指令/常量，以图节点硬件闭环为中心。AMD 的 event queue/completion object 对应 NVIDIA 的依赖计数，AMD coprocessor 分发对应 NVIDIA TMU+WDU；AMD 粒度更细可达 workgroup（加入父执行上下文），NVIDIA TMU 以 task/CTA grid 为粒度。

## 7. 评价与启示

**技术重要性**：

- AMD 动态工作创建路线的核心专利之一：在 GPU 内放置通用 coprocessor 作为工作创建硬件代理，使运行中 wavefront 能直接 spawn workgroup，粒度细于 CUDA dynamic parallelism 的"子 kernel"，且父子可并发执行；
- 巧妙复用既有前端机制：子任务以 AQL packet + doorbell + scheduler 240 + SPI 245 形态进入分发流水线，HSA signal 充当 completion object，实现成本低并与 HSA 架构自洽；
- future/self-enqueue 与 C++ executor（thread pool/loop/serial/system）组合表明该 coprocessor 瞄准"GPU 侧 OS 微内核 + 异步编程模型"的硬件底座，前瞻性高（与其 DOE PathForward/LLNL 超算资助背景一致）。

**局限性**：

- coprocessor 多为"coprocessor 上运行线程 + microkernel"的软硬混合形态，而非 NVIDIA TMU 式纯硬件状态机，延迟下界依赖实现；
- self-enqueue 以"重新入队"替代 spin，预定时间间隔设定与入队开销成为新权衡点；
- 子 workgroup 加入父执行上下文需 SPI/SQ 支持动态 workgroup 分配，说明书仅概述"与 SPI 协商分配 register state/LDS/GDS/wavefront slots"，硬件细节不足；
- 扫描件视觉阅读：个别标号有小疵（如 col.5 "parent task executing on the GPU 210" 应为 205；FIG. 5 流程在文中偶称 method 500），以正为准。

**对理解 AMD 动态工作/硬件任务图路线的价值**：结合同目录 US8310492B2（HQD）、US9176795B2（用户态分发）等可见 AMD 前端从"CPU 主导队列分发"到"片上代理自主生成/分发工作"的演进：CP/doorbell/HQD 解决 CPU→GPU 分发，本专利解决 GPU→GPU 分发；coprocessor 实质是 GPU 内部的"第二个 CP"，为理解 AMD 后续 work graph 类硬件底座提供了专利级注脚。
