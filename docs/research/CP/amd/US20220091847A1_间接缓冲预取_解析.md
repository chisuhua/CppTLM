## 2. 发明背景与待解决问题

**应用场景**：现代处理系统用 CPU 执行通用操作、GPU 执行图像生成/向量处理等操作，CPU 向 GPU 发送命令（[0001]）。为增强程序安全性，GPU 采用 Indirect Buffer（间接缓冲，IB）把与单个程序或设备驱动相关的命令隔离存放（[0001]）：Kernel Mode Driver（内核态驱动，KMD）用位于 memory 110 的 Command Packet Ring Buffer（命令包环缓冲）106 存储管理 GPU 整体操作的命令；User Mode Driver（用户态驱动，UMD）用 IB 存储与执行中的应用相关的命令。要调用某个 IB 中命令的执行，KMD 把一个 Indirect Buffer Execution Command（间接缓冲执行命令，又称 indirect buffer command，即 IB 命令包）写入 ring buffer 106，该命令携带指向对应 IB 的指针，GPU 执行到它时即开始执行该 IB 中的命令序列（[0002]）。IB 机制把不同驱动/应用的命令隔离在不同内存区域，提升安全性与可靠性（[0002]）。

**待解决问题**（分条）：

1. **IB 取数的"on demand（按需）"延迟**：传统 GPU 在 command processor 104 执行到指向某 IB 的 indirect buffer packet 时，才把该 IB 的命令从 memory 110 取到 command queue 109，取数完成前无法执行 IB 命令序列（[0011]、[0022]）。
2. **命令处理器停顿/前端低效**：等待 IB 取数期间 command processor 104 会 stall（停顿）或低效运转（[0022]）。
3. **时延敏感性**：这种执行延迟常常落在程序执行的时延敏感阶段，例如程序正在生成待显示的图像（渲染帧的关键路径）（[0011]）。

**核心方案一句话**：在 ring buffer 中定义一种 Indirect Buffer Prefetch Packet（间接缓冲预取包，IB prefetch packet）105，command processor 104 在执行到 IB 执行命令之前，就指示 fetch control module 107 把目标 IB 的命令预取进 command queue 109，并用 prefetch counter 325 记录预取状态，以便随后遇到 IB 执行命令时抑制重复取数、立即执行。

## 3. 核心方案

### 3.1 整体架构（FIG. 1–5）

**附图清单**（据 Brief Description of the Drawings，[0004]–[0008]）：

- FIG. 1：支持 IB 预取的处理系统 100 框图；
- FIG. 2：GPU 102 对单个 indirect buffer 执行预取的示例（prefetch executed 224 → IB exec 220 → draw 221）；
- FIG. 3：基于 prefetch counter 325 状态抑制 IB on-demand 取数的示例（increment counter / read non-zero value at counter / fetch suppressed）；
- FIG. 4：单个预取命令对多个 indirect buffer 预取的示例（IB 114 与 IB 116，对应 IB exec 420、422）；
- FIG. 5：indirect buffer prefetch packet 105 的条目与字段格式（entries 542/543/544；fields 545–548）。

**系统组成（FIG. 1，[0015]–[0021]）**：Processing System 100 含 GPU 102 与 Memory 110（可为 DRAM 等系统内存，CPU/GPU 共享访问；另有未图示的 CPU、内存控制器等）。GPU 102 内含若干 Compute Unit（计算单元，CU，图中未示出），每个 CU 含 SIMD 模块等处理元件（[0017]）。

GPU 102 前端三件套（[0018]）：

- **Command Processor 104**（命令处理器）：遍历 command queue 109，逐个解码并顺序执行命令；把命令解码为一串 command operations 并在 CU 上执行；基于命令包序列把操作调度为 **wavefronts（波前）**交付 CU 执行（[0018]）；
- **Fetch Control Module 107**（取数控制模块）：负责从 memory 110 取命令并存入 command queue 109，也是预取动作的执行者；
- **Command Queue 109**（命令队列）：片上缓冲，含与 ring buffer 106 对应的区域和与各 indirect buffer 对应的区域（[0020]；注：原文此处把 indirect buffers 误标为 "109"，应为 108，属原文明文瑕疵）。

Memory 110 中两类命令结构（[0019]）：Command Packet Ring Buffer 106（KMD 写入）与 Indirect Buffers 108（UMD 等写入，图中示例含 IB 114、IB 116）。

**command pointer 与 IB 跳转语义**（[0020]–[0021]）：command processor 104 用寄存器保存 command pointer（命令指针），指向 command queue 109 中下一个待处理命令包；初始化时指向 ring buffer 区域的起始条目，每处理一个包即递增。当队列某条目是 indirect buffer packet 时，command pointer 被重定向到该 IB 对应区域的起始条目；执行完该 IB 区域末条目后，command pointer 回到 ring buffer 区域中 IB 包之后的下一条目，从而返回 ring buffer 命令流。这正是"ring buffer 解析 → IB 命令流执行 → 返回 ring buffer"的前端跳转模型。

**IB 层级（indirect buffer hierarchy）**（[0014]）：command processor 的 command packet buffer 构成最顶层；顶层的 IB 包启动第一级 IB；第一级 IB 内的命令又可启动第二级 IB，依此类推；本方案支持对多级 IB 层级预取（单个 prefetch packet 可同时预取第一级与第二级 IB 的数据）。

### 3.2 关键机制详解

**（1）预取触发条件——显式 IB prefetch packet**（[0022]–[0024]）：ring buffer 106 中存放一种显式的 Indirect Buffer Prefetch Command Packet，即 IB prefetch packet 105。fetch control module 107 把 ring buffer 包取入 command queue 109 后，command processor 104 在队列中识别到 IB prefetch packet 105，即指示 fetch control module 107 把一个或多个 IB 108 的数据预取进 command queue 109。触发完全由驱动在命令流中显式插入该包驱动；预取发生在后续 indirect buffer execute packet 220 被执行之前（FIG. 2：entry 224 处识别 IB prefetch packet 105 → 预取 IB 114 的 data 112 → 之后才遇到 IB packet 220）。

**（2）预取抑制与兼容机制——prefetch counter**（[0012]、[0026]–[0028]，FIG. 3）：GPU 102 含 Prefetch Counter 325（计数器或其他存储元件）。数据从 IB 114 预取后，prefetch counter 325 递增，指示该 IB 已有预取数据。之后 command processor 104 处理 indirect buffer execute packet 220 时读取计数器：非零 → 判定已预取，**抑制（suppress）**对 IB 114 的 on-demand 取数（一种实现是阻止 fetch control module 107 取该包指定的数据，[0025]），直接从 command queue 109 开始执行命令序列（如紧随的 draw command 221）；为零 → 说明驱动未实现预取（ring buffer 里没有 prefetch packet 105），回退为传统 on-demand 取数。该机制使 GPU 同时兼容"用预取"与"不用预取"的驱动，无需修改既有编程模型（[0012]、[0028]）。

**（3）预取粒度与批量策略——单包多 IB**（[0013]、[0029]–[0030]，FIG. 4）：单个 IB prefetch packet 105 可携带多个 IB 的列表/标识，处理该包时 GPU 对每个 IB 执行预取；针对"一个程序使用多个存放短命令序列的 IB"的场景特别有效。FIG. 4 示例：同一 prefetch packet 105 指明预取 IB 114 与 IB 116 的数据；随后 ring buffer 中的 IB packet 420、422 分别被识别时，command processor 104 均因数据已预取而抑制取数，立即执行各自预取进来的命令序列。

**（4）预取包格式（FIG. 5，[0031]–[0033]）**：IB prefetch packet 105 含多个条目 entries 542、543、544，每个条目对应一个 IB 并含四个字段：

- Identifier Field 545：该条目对应 IB 的标识符；
- Addresses Field 546：指明 memory 110 中待预取数据位置的一个或多个内存地址；
- Indirect Buffer Size Field 547：对应 IB 的大小；
- Virtual Memory Identifier（VM ID）Field 548：对应 IB 所处的虚拟内存（地址空间）标识。

处理方式：command processor 104 用 addresses field 546 指示的地址从 memory 110 预取数据；维护一张 IB 表（table），把 identifier 545 与 VM ID 548 存入表中供后续使用；用 IB size field 547 定位 IB 的末条目，预取到该末条目即停止——即以 IB size 界定预取深度/边界。

**（5）间接列表变体**（[0022]、[0034]）：条目也可不放在 prefetch packet 105 本体中，而由驱动等模块放入 memory 110 的一个 list（列表）数据结构，prefetch packet 105 只存指向该列表的指针；command processor 104 经指针访问列表，fetch control module 107 依列表对各 IB 108 预取。

**（6）多级层级预取**（[0014]，结合 claim 4/5、11/12、16/17）：预取可覆盖多个间接层级；例如 claim 11 场景中 prefetch packet 本身来自第一级 IB，却触发对另一个（更深层级）IB 的预取。

**提取文本瑕疵标注**：[0022]/[0034] 中 "D3 prefetch packet 105"、"D3 packet 105" 系 "IB" 的 OCR 误识；[0023] "does fetch ... on demand" 依上下文应为 "does not fetch"；[0033] 出现 "entries 540, 541, and 542"（与前文 542/543/544 不一致）与 "indirect buffer size field 147"（应为 547），属原文参考标号笔误；[0025] "command packet buffer 106" 应为 ring buffer 106；首页附图标签区存在乱码（如 "18 114"、"AXAXXXXXX" 等），不影响正文理解。

## 4. 权利要求摘要

共 20 项权利要求，3 项独立权利要求（claim 1 方法、claim 10 方法、claim 13 处理单元）。

**独立权利要求 1（方法）**：一种方法，包括：在处理单元的 command processor 处接收第一间接缓冲预取包（first indirect buffer prefetch packet）；以及响应于接收到该预取包，在为该 indirect buffer 执行 indirect buffer packet 之前，把第一预取包所指示的第一 indirect buffer 的数据预取到 command queue。

**独立权利要求 10（方法，列表语义）**：一种方法，包括：在处理单元的 command processor 处接收指示一个 indirect buffer 列表的预取包；以及响应于该预取包，把该列表所指示的多个 indirect buffer 中每一个的数据预取到与该 command processor 关联的 command queue。

**独立权利要求 13（处理单元）**：一种处理单元，包括：command queue；command processor，用于从 command queue 接收第一 indirect buffer 预取包；以及 fetch controller（取数控制器），用于响应该预取包，在 command processor 执行该 indirect buffer 的 indirect buffer packet 之前，把该包所指示的第一 indirect buffer 的数据预取到 command queue。

从属权利要求按主题分组：

- **多 IB 预取**（claim 2、3 / 9 / 14、15）：预取包指示多个 indirect buffer；对其中每一个执行预取（claim 9 与 claim 2 主题实质重复）；
- **多级间接层级**（claim 4、5 / 16、17）：处理单元实现多个 indirection levels（间接层级），预取包指示所选层级；预取该所选层级上的 indirect buffer 数据；
- **取数抑制与指示器**（claim 6、7 / 18、19）：command processor 识别到该 IB 的 indirect buffer packet 时抑制对它的取数；预取完成后设置 indicator（指示器），识别到 indicator 已置位才抑制取数；claim 19 进一步以 storage element（存储元件，对应说明书的 prefetch counter 325）保存该 indicator；
- **IB 大小字段**（claim 8 / 20）：预取包指示第一 indirect buffer 的大小；
- **跨层级嵌套预取**（claim 11、12）：prefetch packet 本身接收自第一 indirect buffer，预取对象是不同于它的第二 indirect buffer；第一 IB 属于第一间接层级、第二 IB 属于第二间接层级。

## 5. 与专题主题的关系

本专利属于专题「AMD GPU 前端全链路（CP/IB/PM4 + doorbell/HQD + SPI/SQ wave 分发）」。

**(a) 在 AMD 前端链路中的位置**：本专利正落在 CP（Command Processor，命令处理器）的 IB 读取/预取环节，位于 ring buffer 解析之后、IB 内 PM4 命令执行之前。按专利自身描述的前端流水：KMD 把命令包写入 memory 中的 command packet ring buffer 106（对应实际产品中的 ring buffer + doorbell/wptr 通知机制，本专利未展开 doorbell 细节）→ fetch control module 107 取包入 command queue 109 → command processor 104 顺序解码执行（即 PM4 命令处理；文中 "indirect buffer execution command" 对应 AMD 公开的 PM4 Indirect Buffer 类 opcode）→ 遇到 IB 执行包时 command pointer 跳转到 IB 区域执行 IB 命令流 → 完成后返回 ring buffer。传统路径在"遇到 IB 包才取 IB 数据"这一步产生停顿，本专利在 ring buffer 命令流中显式插入 IB prefetch packet 105，把 IB 取数提前到 IB 执行包之前完成，因此它是前端取数阶段（fetch control）与命令执行阶段（command processor）之间的延迟优化，下游的 wavefront 调度（command processor 把操作调度为 wavefronts 交付 CU，[0018]）因前端不停顿而获益。注意：本专利未披露 CP 内部 ME/PFP 微引擎划分、doorbell/HQD、SPI/SQ 等 AMD 特有术语，它把前端抽象为 command processor 104 + fetch control module 107 + command queue 109 三组件。

**(b) 与 NVIDIA TMU 任务描述符预取（US11182207B2）的对照**：两者在功能思想上同构——都用"在当前工作执行期间并行取回下一工作的元数据/命令"来掩盖依赖解析/取数延迟：

- **预取对象**：AMD 预取的是 IB 内容，即命令流片段（一段 PM4 命令序列），落点是片上 command queue 109；NVIDIA 预取的是下一任务的 task descriptor（任务描述符，落 Consumer Task Descriptor Cache 480）以及指令与常量（落指令/常量缓存）。AMD 的对象是"命令本身"，NVIDIA 的对象是"工作描述+程序体"。
- **触发时机与方式**：AMD 为**软件显式触发**——驱动在 ring buffer 中插入专用 IB prefetch packet 105，CP 解析到该包即发起预取，时机由驱动决定（通常安排在当前 IB/命令流执行期间、目标 IB 执行包到达之前），并靠 prefetch counter 325 保证与未启用预取的旧驱动兼容；NVIDIA 为**硬件自动触发**——由生产者任务描述符中的 Descriptor/Instruction/Constant Prefetch Flag 驱动，描述符预取搭生产者 task launch 的空隙、指令/常量预取搭生产者 memory flush 的空隙，无需软件逐次发命令。
- **粒度**：AMD 以整个 IB（或多 IB 列表）为粒度，用 IB size 字段界定预取边界，支持单包批量多 IB 与多级 IB 层级；NVIDIA 以单个消费者任务为粒度、按描述符/指令/常量三类分别预取，且描述符内预取标志按"每个消费者"配置。
- **依赖语义**：NVIDIA 方案与依赖计数（dependency count）硬件解析耦合；AMD 方案不涉及任务依赖，纯粹掩盖"ring buffer → IB"的取数跳转延迟。

## 7. 评价与启示

**技术重要性**：

- 直接命中 AMD CP 前端的结构性停顿点：ring buffer → IB 的跳转取数。IB 跳转在图形/计算负载中极其频繁（每个 draw/dispatch 的提交块通常就是一个 IB），每次跳转若 on-demand 取数都会让 command processor 空转，本专利用"提前预取 + 计数器抑制"把该延迟从执行关键路径上移除，对帧率敏感的渲染时延阶段（[0011] 明示的图像生成场景）收益直接；
- 公开了 AMD CP 前端取数子系统的少见细节：fetch control module 107（独立于 command processor 的取数执行者）、command queue 109 按 ring buffer/IB 分区、command pointer 重定向语义、IB 表（identifier + VM ID）与 prefetch counter 325，这些是还原 CP 微架构的珍贵一手材料；
- 兼容性设计务实：计数器非零/零的双路语义使新硬件对旧驱动透明回退，预取完全由驱动选择性启用，符合驱动生态渐进演进策略；
- 单包批量多 IB 与多级 IB 层级预取（claim 11/12 的"IB 中嵌套预取另一 IB"）与现代图形 API 的多级命令缓冲（如 Vulkan secondary command buffer、链式 IB）高度契合。

**局限性（基于专利文本）**：

- 预取完全依赖驱动显式插入 prefetch packet，文本未描述任何基于运行时队列深度/命令流特征的动态/自适应预取策略，驱动未优化则无收益；
- prefetch counter 325 的语义较粗（文本仅描述递增与非零/零判定），未说明何时递减/清零、多 IB 并发预取时如何区分各 IB 的预取状态，这些属未公开的实现细节；
- 未量化 command queue 109 容量、预取带宽占用与 IB 大小的关系；IB size 字段作为唯一预取深度控制，对超大 IB 可能造成队列压力，文本未讨论节流；
- 文本抽象层级较高，不含 ME/PFP、doorbell、HQD、PM4 opcode 编码等 AMD 惯用术语，与产品实现的映射需结合公开寄存器文档/开源驱动推断；提取文本存在多处 OCR 误识与标号笔误（见 3.2 末尾标注），均以正文语义为准。
