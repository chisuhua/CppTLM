## 2. 发明背景与待解决问题

**应用场景**：多处理器系统同时包含 fixed-function（固定功能）与 programmable（可编程）处理单元，二者以各自的 native width（原生宽度，文本定义为并发度这一固定设计特征）并发执行命令；命令与数据通过连接 source 与 target 处理单元的 command queue（命令队列）传输（数据处理流水线的各级之间以驻留在本地缓存/本地存储/系统内存中的队列传递命令与数据）。

**待解决问题**（按文本表述）：

1. 传统命令队列按源处理单元的固定原生宽度接收、按目标处理单元的固定原生宽度交付，把整个多处理器系统的可编程性约束死在"特定处理单元之间的固定、预定义连接"上——源/目标原生宽度不匹配时无法高效互联；
2. 单条命令可能携带大量数据，若命令与数据混存于同一队列，查找/求值新命令必须跨越（traverse）大段数据，导致 data cache 利用率低下，降低系统效率与性能；
3. 环形队列若不加控制会因 push 使 head/tail 指针交叉而溢出、损坏数据需要显式的接收/拒绝机制。

**核心方案一句话**（摘要）：queue manager（队列管理器，下称 QM）把第一宽度的入站命令（inbound command）转换为 scalar format command（标量格式命令）入队，再把队列中的标量命令组装为第二宽度的出站命令（outbound command）发出，从而在原生宽度可能不匹配的任意处理单元之间提供"高效且可编程的命令传输"。

### 3.2 关键机制详解

**QM 的位置**：QM 718 不在 front end，也不在 host interface，而在 GPC 内的 TPC 层级——FIG. 7B 明确"QM 718 的一个实例实现于 FIG. 3A 所示 TPC 320 的对应实例内"，与 L1 712、SM 720、MPC 722 通信，管理 SM 720 与 MPC 722 之间传递命令的命令队列；替代实施例可放在多处理器系统架构的其他部位。QM 可实现为专用逻辑电路，也可实现为执行微码/程序指令的微码处理单元。注意与两级"前端"区分：PPU 级的 Front End Unit 215 负责读取 host 命令流（command stream）；TPC 内另有 front end（FE）单元 723，负责 SM 720 的上下文与上下文切换（从 MPC 722 接收 launch 指令与上下文，向 MPC 722 产生 finish 指示）。

**队列组织：命令队列 + 数据队列成对**。一个 queue 由 metadata、命令队列（环形）与数据队列（环形）构成；数据队列存放与命令关联的任意长度数据，命令队列只存紧凑的命令/载荷，从而"小到足以被 QM 本地基本完整缓存"，避免命令与数据混存产生的长跨距遍历。metadata 包括：queue ID、命令/数据队列各自的 base address 与 size、push/pop 指针（head、tail、extended head/xhead、extended tail/xtail，可为相对或绝对地址）、full flag、入站命令到动作的查找表（LUT，提供间接索引）、drain（告知 QM 应优先弹出哪个队列及调度优先级）、以及 in-order ticketing system 的状态。

**环形队列指针语义（FIG. 9C/9D）**：Base 940 指队列起始地址；Head 944 与 Tail 946 界定全部有效条目，其间为 Queue Body 954（ready body）；Tail 946 与 Xtail 948 之间是 Push Pending Zone 956（已接受但数据尚未写完的入站命令预留区）；Xhead 942 与 Head 944 之间是 Pop Pending Zone 952（已弹出待读走的出站数据区）；Size 958 定容量，指针推进越过尺寸后绕回，形成概念上的环形空间。命令队列与数据队列的对应指针同步推进（命令队列按命令条目尺寸、数据队列按数据尺寸），使两队列的预留/释放空间同步收拢。有标志与配套电路在 head/tail 相等时区分"满"与"空"。

**标量命令格式**：标量命令宽度为一，示例为 2 字节命令 + 2 字节整数倍的可选 payload；2 字节命令内部含 keep bit（1 位）、命令尺寸位（2 位）、命令类型位（3 位）、命令位（3 位）、数据计数位（7 位，可被队列元数据缩放）；整体命令尺寸被约束为 2 的幂字节（2B/4B/8B/16B…）。命令类型包括 THREAD、QUADTHREAD、WARP（单元原生宽度）、CTA（任意尺寸线程块）。FIG. 9B 条目示例：2B 命令仅 Cmd 920 + Data Count 922（如 Pixel Quad、Thread）；4B 增加 1 个 Payload 924（Pixel Quad + Cmd State）；8B 含 Payload 924(0)-(2)（Pixel Quad + Cmd State, CTA）；更大尺寸类推（16B/32B/64B）。命令字段指定动作或 barrier；payload 是执行前需由 QM 处理的命令设置数据（如 shader 索引、CTA 维度），也可作为命令的一部分传给执行单元。

**入队路径（方法 100/120）**：步骤 102 QM 从第一处理单元接收第一宽度的入站命令（push 请求，命令含 queue ID，可经专用硬件通道送达）→ 103 判断能否接受（实现为方法 120：122 依命令位字段算命令队列空间需求并比对空闲空间；124 依数据计数位算数据队列空间需求并比对空闲空间；125 两者都够→126 接受，否则→128 拒绝并回到 104，源单元重试）→ 110 把入站命令拆成若干标量命令（保留嵌入命令的执行顺序；若嵌入命令间无顺序要求则不必保留）→ 112 原子地压入所选命令队列（仅 QM 或其指定代理可以 push/pop 命令队列，且原子地按合适命令宽度进行）→ 114 把指向数据队列 push pending zone 的指针发回第一处理单元，由其写入数据并在写完后通知 QM，QM 随即关闭 push pending zone、更新 tail 指针使命令可被弹出。

**出队路径**：步骤 116 QM 从所选命令队列头部弹出尽可能多的标量命令，按 packing 规则（如相同 command 字段）组装成宽度不超过目标单元原生宽度（第二宽度）的出站命令——目标宽度 8 时可聚合最多 8 条标量命令，不足处补 null 命令保持语法兼容；目标宽度 1 时逐条发送；出站命令不必尊重入站命令边界（例：宽度 4 的入站命令遇宽度 8 的目标可两条合一；遇宽度 1 的目标则一条拆四发）。步骤 118 发给第二处理单元，同时 QM 把指向 pop pending zone 的数据指针交给目标单元读数据；目标读完后通知 QM，QM 更新数据队列 head 释放空间。

**QM 718 内部结构（FIG. 7B）**：

- Address Scrubber 740：校验客户单元对数据队列条目的读/写地址是否落在预定义地址范围内——写请求必须落在发起客户端所持的开放 push pending zone 内，读请求必须落在其开放 pop pending zone 内，越界即拒绝；也负责地址绕回，使客户端无需自行处理环形绕回；
- Queue Scheduler 742：含 QPush[] 数组 743 与 QPop[] 数组 744（记录 valid bit、done bit、客户端标识、active mask、开放队列的有效地址范围）、prefix-sum 加法器 746（从 tail 起累加各标量命令的命令尺寸/数据尺寸，算出总尺寸、各标量命令的累积数据偏移与结束地址，结束地址可用作新的 xtail；尺寸计算方式为 data/command count 左移尺寸位域再乘 command count，pop-count 单元 748 辅助）、state queue metadata array 750（存储/更新各队列 base 与 head/xhead/tail/xtail 指针，对成对队列同步更新）、L0 Command Queue Head cache 752（QM 内本地缓存各命令队列头部，每队列至少 64 字节，即最多 32 条 2 字节命令）；
- Queue Chomper 754：从所选命令队列读取连续标量命令组装出站命令 756——先看队首命令尺寸，按尺寸偏移逐条比对，直到达到 packing 上限、遇到不同命令、队列耗尽或检查上限；只合并"兼容"（尺寸与功能相同）的命令，不兼容者留到下一个出站命令；队首内容假定已缓存在 L0 Command Queue Head 752 中（如前 64 字节），命令比较可并行完成。

**调度与流控**：不同命令队列有不同优先级，queue scheduler 742 据此选择弹出哪个队列，可实现格优先级或防饥饿（anti-starvation）策略；队列可被客户端经 metadata 标志阻塞 push/pop。引用多个 queue ID 的命令由 QM 内部串行化——每次重放源命令、只处理一个 queue ID，直至全部处理完。

**keep bit 机制**：命令中的 keep bit 指示 QM 在名义弹出（nominal pop）后把该命令保留在队首，实现"非破坏性弹出"的迭代操作而保持流水线状态；队列指针可压栈以支持 keep bit 命令的循环执行；命令仅当处理单元显式要求 QM 将其标记为可移除时才移除。FIG. 8 示例：setup/raster HW unit 842 产生的 fragment 带 keep bit 压入 PixelQuad Queue 824，SM HW Unit 840 非破坏性弹出做着色（用 TRAM Queue 826 中的三角形数据），把 fragment 颜色写回 PixelQuad Queue 并清除 keep bit，随后 quad 弹给 ROP HW Unit 844 合成。替代实施例可用中间队列代替 keep bit。

**流水线级数据流（FIG. 8）**：Host 810 产生工作流 → Vtx/Geom Queue 820 → SM HW Unit 840（顶点/几何处理，产出几何图元）→ Setup/Raster Queue 822 → Setup/Raster HW Unit 842（产出 fragment）→ PixelQuad Queue 824 → SM HW Unit 840（着色）→ ROP HW Unit 844 → FB 846；四条队列均由 QM 830 按命令/数据队列对管理。因为入站任意宽度→标量→出站任意宽度的转换，QM 830 可把出站命令从一个目标单元动态重定向到另一个（如改由 SM HW Unit 840 代替 Setup/Raster HW Unit 842 做光栅化）——这正是"可编程性"收益的体现。

**SM 侧产生命令**：SM 720 执行 warp 命令时，每个线程生成 resulting command（可含写为 Data 704(1) 的数据），经命令互连 706(1) 送 QM 718，由 QM 以标量命令入队到后续处理单元对应的命令队列；通用计算配置下，"SM 340 还能写入供 scheduler unit 220 用来在 TPC 320 上启动新工作的命令"。LD/ST 单元 721 负责在数据队列与 SM 之间搬运线程/warp/CTA 执行状态等数据，并可经 Cmd 783 与 QM 交换命令；数据队列访问可经 QM 地址校验，也可在另一实施例中直达 L1 712 不校验。MPC 722 内含 Scheduler 764 与工作队列 760–763：Queue Manager Queue 760（QM 管理、可面向任意处理单元的工作）、Subtile Queue 761（fragment 工作）、Compute Queue 762（通用线程计算）、Geom Queue 763（几何工作）；MPC 可经 VAF 772 与 PE 770 收发工作，也可从 GPM 774（GPC manager）接收工作。

## 4. 权利要求摘要

共 19 项权利要求，3 项独立权利要求（claim 1 装置、claim 18 方法、claim 19 计算机程序产品）。

**独立权利要求 18（方法）**与 **claim 19（计算机程序产品）**：与 claim 1 对应的动作序列（接收→标量化→写缓存入队→发数据指针→选队列→读标量命令→组宽→发出→发数据指针）。

从属权利要求按主题分组：

- 标量化语义（claim 2）：读出的标量命令包含由入站命令转换而来的命令；claim 3：第一与第二处理单元可为同一单元；claim 4：处理单元可含 SM、texture module 或 ROP pipeline；
- 可编程重定向（claim 5）：动态把出站命令目的地从第二处理单元改到第三处理单元；
- keep bit（claim 6）：置位后出站命令发出后标量命令仍保留在命令队列中复用；
- 队列优先级（claim 7）：队列带优先级，决定其中命令被处理的优先次序；
- 指针计算（claim 8、9）：指针由 prefix-sum adder circuit 基于第一数据尺寸计算；该数据尺寸与标量命令关联；
- 环形队列结构（claim 10、11、12、13）：数据队列与命令队列为成对的环形队列，各有 base/head/xhead/tail/xtail 指针；指针可引用 tail 与 xtail 之间的 push pending zone；state queue metadata array 存储并更新全部八只指针；
- 安全与缓存部件（claim 14、15、16）：address scrubber 依预义地址范围接受/拒绝数据队列访问；command queue head cache 存储含标量命令的队首条目；queue chomper 只把顺序且兼容的标量命令并入出站命令；

## 5. 与 TMU 上游模块的关系

**在任务前端链路中的位置**：按本专利 FIG. 2，host 提交路径为 pushbuffer（host 程序把命令流编码进主机/设备共享的 buffer）→ I/O Unit 205（PCIe 等）→ Host Interface Unit 210（解码报文并路由命令）→ Front End Unit 215（管理命令流：从流中读取命令并转发给 PPU 各单元）→ Scheduler Unit 220（按流定义的任务配置各 GPC，跟踪任务分配到哪个 GPC、活跃/非活跃、优先级等状态，管理多任务在 GPC 上的执行）→ Work Distribution Unit 225（每 GPC 维护 pending task pool（如 32 槽）与 active task pool（如 4 槽），经 XBar 270 向 GPC 250 派发任务）→ GPC 250 → SM 340。本专利的 QM 718 不在这条 host 命令流路径上，而是位于 GPC 内 TPC 层级，负责流水线级/SM 级的细粒度命令队列数据流。

**与 TMU 的对应关系**：本专利实施例中的 Scheduler Unit 220 与 WDU 225，在职能与链路上的定位与 US 11,182,207 B2 中的 Task Management Unit 234 / Work Distribution Unit 236 一致（Scheduler Unit 220 位于 Front End Unit 215 与 Work Distribution Unit 225 之间，负责任务状态跟踪与执行管理），可视为同一前端任务管理硬件在不同代际/文本中的命名；本专利全文未出现 "TMU" 字样。

**QM 是否为 CP/IB（command processor / indirect buffer）概念在 NVIDIA 侧的对应物**：从本专利文本看，答案是"分层对应"——host 侧 CP 职能（读 pushbuffer、取指针、分发命令）由 Host Interface Unit 210 + Front End Unit 215 承担；QM 718 则是其下游、位于 TPC 内的又一层命令队列结构，且与 IB 有共同的机制基因（内存中的环形命令队列、head/tail 指针语义、命令打包/拆包、准入控制），但有三点超越：(a) 标量化宽度适配，解耦源/目标原生宽度；(b) 支持设备自产命令——SM warp 的每线程可生成 resulting command 经 QM 入队，SM 还能写命令供 scheduler unit 220 启动新工作，即命令流可在设备内部生成与转发，而非仅 host 单向注入；(c) QM 可把出站命令在目标单元间动态重定向（FIG. 8 的 SM 替代固定光栅化单元示例）。

**队列提交路径与 TMU 任务表的关系**：二者工作在不同粒度层级。Scheduler Unit 220/WDU 225 一路是"任务级"（task→GPC→TPC→SM 的 CTA/warp 派发，池化槽位管理）；QM 718 一路是"命令级"（标量命令在 L1 映射的命令/数据队列间流动，服务于 MPC 722 的 subtile/compute/geom 等工作队列与 SM/TEX/setup-raster/ROP 客户单元之间的数据流）。两级在 MPC 722 处汇合：MPC 的 Scheduler 764 从各工作队列 760–763 选工作发给目标单元，并可从 GPM 774（GPC manager，对应上游 WDU/pipeline manager 一路的任务分发）接收工作。

**与 libsmctrl 实验观测的互证**：第三方微基准实验（libsmctrl 一类）观测到 SM 侧存在按队列提交、per-SM 工作排队的行为；本专利披露的 per-TPC QM 实例、命令/数据队列对、SM 自产命令经 QM 入队等机制，为该观测提供了专利层面的结构解释，二者方向一致（此处仅作指认，不展开论文细节）。

## 7. 评价与启示

**技术重要性**：

- 本专利把 GPU 内部各级处理单元之间的命令传输抽象为一个可编程的"宽度无关"队列结构：标量命令作为统一中间表示（IR），入站/出站宽度自由伸缩，直接消解了固定功能单元与可编程单元之间原生宽度不匹配的硬连线约束，FIG. 8 中"SM 替代固定光栅化单元"的动态重定向即其红利，可视为 NVIDIA "把固定功能搬上 SM"战略的前端基础设施；
- 命令队列与数据队列分离是关键工程决策：命令队列小到可整体驻留 QM 本地（L0 head cache 每队列 ≥64B），检查/调度命令无需遍历数据；数据经指针 + push/pop pending zone 由客户单元直写直读，address scrubber 提供地址合法性护栏——这是"控制面小而快、数据面大而直通"的经典拆分；
- 准入控制（命令/数据空间同时够才接受，否则拒绝重试）+ xhead/xtail 双扩展指针 + 原子 push/pop，构成环形队列防溢出的完整方案；prefix-sum 加法器并行计算指针与空间需求，是为高吞吐入队所做的硬件级优化；
- keep bit + 指针压栈的"非破坏性弹出"机制，使 fragment 等需要多阶段迭代处理的工作无需反复入队；SM 自产命令经 QM 入队则把命令流的生成权部分下放给设备侧，是理解 NVIDIA GPU 内部命令自治化（device-side command generation）的重要文本证据。

**局限性（基于专利文本可推断）**：

- 实施例以图形渲染流水线为主要载体（vtx/geom、setup/raster、PixelQuad、TRAM、ROP），对通用计算场景的队列组织着墨较少（仅 compute queue 762 与 SM 写命令启动新工作的简短描述）；
- QM 以 per-TPC 实例描述，跨 GPC/全芯片的队列层次与一致性未展开；文本未给出队列数量、深度、位宽等量化实现参数；
- 提取文本存在 OCR/原文小瑕疵需留意：首页 CPC 中 "GO6F 37067"/"GO6F 370659" 应为 G06F 3/067、G06F 3/0659；Brief Description 中 "FIG. 7B illustrate a queue manager..."（缺 s）；FIG. 9A 图内标记提取为 "Commando"（应为 Command0）；FIG. 1C 正文提及标量命令 152(0)-(3)，而图内标记提取为 153(0)-(3)，以正文编号体系理解即可。

**对理解现代 NVIDIA GPU 前端的价值**：本专利补全了 NVIDIA 前端研究中"host 命令流之下"的一层：pushbuffer → host interface/front end → scheduler/WDU 属于任务级前端（与 TMU 专利族衔接），而 QM 揭示了任务到达 GPC/TPC 之后，命令如何以标量队列的形式在 SM、MPC、TEX、setup/raster、ROP 之间继续流动、排队与重定向。它与 TMU 专利（任务描述符、依赖计数）、WDU 专利（任务池派发）共同构成"任务前端 → 工作分发 → 命令队列"三级前端的完整证据链；本申请被放入 14_Front_End_and_Task_Graphs 目录正源于此——QM 层是理解后续 device-side 任务图/图启动类特性硬件基础的必经环节。
