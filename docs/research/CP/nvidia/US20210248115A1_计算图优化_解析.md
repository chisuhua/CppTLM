## 2. 发明背景与待解决问题

**应用背景**：图形处理、深度神经网络训练、科学模拟等计算任务普遍具有"同一工作流反复执行"的迭代结构（[0048]）。图编程模型（graph programming model）把工作表示为图：CUDA 操作构成节点，依赖构成边；节点可以是 kernel launch、内存拷贝、memset、CPU 函数调用，甚至其他图（嵌套）；图是定义节点与边的数据结构（[0051]）。图按"定义一次、优化、反复执行优化后指令"的模式使用（[0048]）；kernel 定义为编译到处器上执行的函数，经 buffer/array 传回结果，关联线程层次或线程块（[0051]）。

**图执行的收益**（按文本）：

1. kernel launch 开销可占 kernel 总执行资源的显著部分，以图整体提交降低 CPU 成本（[0049]）；
2. CPU 单次 invocation 即令 GPU 执行图中全部 kernel 操作，降低 CPU/GPU 间切换开销（[0052]）；
3. 图的整体工作流——执行、数据搬移、同步交互——对优化过程完全可见，优化模块据此提升性能（[0050]、[0056]）。

**待解决问题**：图的实例化/优化消耗大量计算资源（处理器时间、内存），且优化是"适应于参数"的——考虑 data locality、data transfer rate、memory availability 等因素（[0057]、[0058]）。迭代负载每次迭代的操作数（operands，如输入/输出缓冲区）通常不同；若每次换参都要重新实例化/重新优化，则优化成本反复发生，抵消图模式的全部收益。

**发明目的**：允许修改已实例化图的参数，使图可"独立于其操作数"被多次执行（[0047]、[0104]）；替换操作数时不重新优化，或仅在优化开销低于阈值时才做优化（[0047]）。

### 3.2 关键机制

**graph code 的实例化（instantiation）**。经 graph API 定义图：`add` 函数添加节点并指定节点间关系，把节点关联到 kernel 函数、把边关联到条件；一个 `add` 即定义节点与边，可向图添加 CUDA kernel 操作或其他 CUDA 函数（[0079]）。也可用 `begin stream capture` / `end stream capture` 捕获一段操作流：被导向 stream 的操作不立即执行，而是被捕获并转换为图（[0080]）。

参数经 `set parameters`（关联整图）/ `set node parameters`（关联节点）绑定（[0082]）；参数与节点的关联体现为节点函数引用对应参数（[0053]）。参数形态包括 CUDA kernel launch 参数、global/shared memory 区域、buffer、内存区域引用、标量/多维数组，以及位图/纹理/线框模型等二进制资源（[0054]–[0055]）。FIG. 1 示例中 PA1 关联节点 {A,B}、PA2 关联 {C}、PA3 关联 {D,E,F}。

随后 `graph instantiate` 函数实例化图：生成表示实例化图的一个或多个数据结构（实例化 CUDA graph 数据结构），并对执行指令做优化（[0083]–[0084]）；文本明确 "instantiating of a graph is computationally expensive"。API 另提供合并的 `execute` 函数：**首次调用时实例化并执行，后续调用仅执行**（[0085]）——这是"实例化一次、执行多次"的入口。

**参数化再执行（避免 reinstantiation）**。实例化图先用 parameters 106（PA1–PA3）执行，再换用 updated parameters 108（PB1–PB3）执行（FIG. 1，[0059]）。对已实例化图调用 `set parameters` / `set node parameters` 改参（[0090]），再用同一 `execute` 函数（FIG. 7 中标号 716）再执行——改参前后通用（[0096]）；实例化图也可以同一参数集连续多次执行（串行或并行）（[0088]）。

改参被允许/拒绝的判据是**该改动涉及再优化的程度**：不涉及再优化的改动直接生效；涉及但再优化成本低于阈值（threshold amount）的改动同样允许（[0090]）。graph API 在被指示改参时执行相应的分析与计算以判定成本是否超阈（[0062]）。

FIG. 3/4 以阈值 T0 演示逐区域判定：对区域 {A,B} 分析 PA1→PB1 是否触发再优化，不触发则直接替换（[0067]）；region 310 需再优化但成本 < T0 → 仅对该 region 做**部分再优化**（parameter-updated optimized graph 104 中只有 {C} 110 被重做，{A,B}、{D,E,F} 原样保留，[0061]）；region 410 成本 > T0 → 整个替换被拒绝（[0070]）。阈值的选择目标是：与"实例化一个新图"相比，复用该图仍能保住预期的性能收益（[0103]）。

**避免 reinstantiation 的具体约束手段**（本专利的实质边界条件）：

1. **锁定处理单元绑定**：把区域重分配给不同 processing unit 的成本被估计为超过阈值，参数集替换时禁止重分配；可基于"重分配后重优化"的预定估计成本直接禁止（[0065]）。FIG. 5：510→512 的新关联被拒（[0073]）。execution topology 明确包含"分配到所选处理器"与"内存与处理单元的邻近性"（[0102]）。processing unit 可为 GPU、CUDA core、RT core、tensor core、general processing cluster、OpenCL compute device、compute unit 或 processing element（[0064]）。
2. **禁止结构变更**：会导致 structural change（如 610）的参数替换一律不允许（[0075]；FIG. 6）；API 只允许非结构性改动（[0094]）。当不重分配处理单元会使现有优化失效或低效（性能劣化超阈）时，视为需要重分配并随之被拒（[0072]）。
3. **节点/参数级白名单**：仅允许修改 GPU kernel 节点，其他节点类型不可改（[0091]）；可改 kernel argument，但不可改底层 kernel 本身（[0092]）；可改 kernel 节点的 launch configuration（[0093]）。
4. **in-place 语义**：改动与图"独立"——现有优化指令保持原位或仅做最小修改，执行拓扑不受扰动（[0101]）；优化结果在不同操作数下保持 in-place（[0105]），图保持针对同一处理单元优化（[0106]。
5. **API 强制**：API 禁止与执行拓扑变更相关的修改，也禁止关联再优化成本超过阈值的修改（[0115]–[0116]）。

**流程图 700/800**。700 = 702 定义图（add / stream capture）→ 704 关联参数（set parameters）→ 706 实例化（graph instantiate，含优化执行指令）→ 708 执行（execute 执行各 kernel 操作）→ 710 修改参数 → 712 以新参数再执行。

800 = 802 接收图定义（stream capture 或显式定义；CUDA/HIP/OpenCL API）→ 804 针对所选处理单元优化（GPU/GPGPU/parallel processor/processing cluster）→ 806 执行优化图（完成图定义的计算任务，含多个 kernel 操作）→ 808 接收改图/改参请求（经 CUDA/OpenGL/HIP API；保持执行拓扑不变）→ 810 禁止会改变执行拓扑的修改 → 812 执行修改后的图。

文本强调图可"独立于优化时所用操作数"被再次执行：第一次用第一 buffer、第二次用第二 buffer，电路可先判定"换操作数执行不改变拓扑"或"部分再优化低于阈值计算能力"（[0104]、[0107]–[0108]）。

**关于 "doorbell"**：全文仅出现 1 次，位于样板段落 [0197]（FIG. 20A parallel processor 2000 描述）：host interface 2006 经 I/O unit 2004 收到 command buffer 后把工作交给 front end 2008；front end 2008 耦合 scheduler 2010（由微控制器上的固件逻辑实现，分发前保 processing array 2012 配置正确且处于有效状态），把命令/工作项分发给 processing array 2012；"host software can provide workloads for scheduling on processing array 2012 via one of multiple graphics processing doorbells"，随后工作由 scheduler 2010 逻辑自动分发。即 doorbell 是主机软件向 GPU 前端投递工作、触发调度的"门铃"通知机制，属通用 PPU 样板描述，**不属于本专利发明实质**；发明实质（改参不重实例化）完全落在 API/runtime 层。

## 4. 权利要求摘要

共 31 项权利要求，4 项独立权利要求（claim 1 处理器、claim 9 机器可读介质、claim 17 系统、claim 25 带双缓冲区的系统）。

**独立权利要求 1（处理器）**：一个或多个电路（circuits），用于独立于图所操作的一个或多个操作数（operands）多次执行该图；不同次执行中至少一个操作数不同。

**独立权利要求 9（机器可读介质）**：存储指令，使一个或多个处理器执行与 claim 1 相同的"独立于操作数多次执行图"。

**独立权利要求 17（系统）**：一个或多个处理器执行与 claim 1 相同的动作。

**独立权利要求 25（系统）**：内存包含第一与第二缓冲区；至少一个处理器多次执行图，操作数第一次为第一缓冲区、第二次为第二缓冲区——把"同一图先后操作不同 buffer"写成结构性限定。

从属权利要求按主题分组（四组独权下的对应项）：

- **图类型**（claim 2 / 10 / 18；28）：CUDA、OpenCL 或 HIP 图；claim 10 另列 OpenGL graph；claim 28–29：CUDA 图、含多个 CUDA kernels；
- **优化保持/针对性**（claim 3–5 / 26–27 / 30–31）：不同操作数下优化保持 in-place；首次执行前已针对处理单元优化且换参后保持优化；图至少部分基于第一缓冲区优化、该优化用于第二次执行；图在首次执行前的实例化时优化；针对所选处理单元优化；
- **双缓冲区操作数**（claim 6 / 11 / 19）：第一次执行操作第一 buffer、第二次操作与之不同的第二 buffer；
- **拓扑不变判定**（claim 7 / 12 / 20）：电路确定用不同操作数执行图**无需改变执行拓扑**；
- **阈值内再优化**（claim 8 / 13–14 / 21–22）：确定图的部分可用低于阈值的计算能力再优化；基于第一组操作数生成优化指令、再以第二组操作数用该优化指令第二次执行；确定优化指令可低于阈值成本再优化；
- **API 禁止条款**（claim 15–16 / 23–24）：API 禁止与执行拓扑变更相关的修改；API 禁止再优化成本超过阈值的修改。

（说明书 [0104]–[0120] 以 "In at least one embodiment" 句式给出与上述权利要求逐一对应的实施例条款，可视为权利要求的支持文本。）

## 5. 与 TMU 上游模块的关系

**graph code 由哪一级提交**。发明实质的全部动作（定义、实例化、改参、再执行）都由 graph API / software runtime 完成（[0076]、[0084]），即驱动/运行时层；GPU 侧只见"一次 invocation 执行图内全部 kernel"（[0052]）。实例化产物如何进入 GPU，本专利未给出专门硬件机制，仅由样板段落给出通用提交路径。

FIG. 20A（[0196]–[0197]）：command buffer 经 I/O unit 2004 → host interface 2006 → front end 2008 → scheduler 2010 → processing array 2012，主机软件经多个 graphics processing doorbells 之一投递工作。

FIG. 25 PPU 2500（[0256]–[0260]）：主机程序把 command stream 编码进缓冲区（即 pushbuffer），front-end unit 2510 接收指向 command stream 的指针、管理并读取命令、转发至各单元；scheduler unit 2512 跟踪任务状态（分配到哪个 GPC、active/inactive、优先级）并配置各 GPC；work distribution unit 2514 维护每 GPC 的 pending pool（32 slot）/ active pool（4 slot），经 XBar 2520 向 GPC 2518 派发任务，活跃任务因等待数据依赖而空闲时会被换出回 pending pool。

因此 graph code 的实例化结果最终以命令流/命令队列形态经 front end 进入 GPU，TMU 级任务图执行机制是其下游消费者。全文未出现 "task management unit" 字样，本专利不新增片上任务管理硬件。

**与 US11182207B2（TMU 依赖任务描述符预取）的关系与分工**。两案共享发明人 Stephen Jones，是同一"硬件任务图"布局的前后两端：US20210248115A1 管"图的生命周期前端"——捕获/实例化生成优化后的执行表示，并以阈值 T0、拓扑锁定、结构禁改等策略保证该表示在参数漂移后仍然有效、不必推倒重来；US11182207B2 管"图的生命周期后端"——TMU 234 以任务描述符（dependency count/current count/消费者指针/预取标志位）在片上解析依赖、预取消费者描述符/指令/常量并自复位计数，低延迟地硬件执行任务图。前者降低"实例化/重优化"这一 host 侧成本，后者压缩"依赖解析延迟"这一 device 侧成本，合起来才构成 CUDA Graphs 类特性相对逐 kernel 提交的完整收益。

**与 US20210149719A1（可执行图修改）的关系**。该案早 6 周提交（2019-12-31 提交，2021-05-20 公开），题录为 "Techniques for modifying executable graphs to perform different workloads"，发明人与本件同一班底（另含 Jason Gaiser），主题是把 task graph 转换为 executable graph 并修改它以执行不同的工作负载。分工可理解为：US20210149719A1 走"可改"路线——允许对可执行图做修改以适配新工作；US20210248115A1 走"尽量不改"路线——当变化仅是参数/操作数时，用成本阈值与白名单把修改限制在不破坏既有优化的最小范围内，改不动（超阈值/改拓扑/改结构）时拒绝。两者构成 "executable graph update" 能力的一对互补专利。

**对 CUDA Graphs 硬件化路径的意义**。本专利摘要是 NVIDIA 专利文献中直接使用 "graph code" 一词并给出 "instantiate → execute → re-parameterize → re-execute without reinstantiation" 完整语义的文本；说明书点名的 API 函数（graph instantiate、execute、set parameters、set node parameters、begin/end stream capture）与图捕获/实例化执行模型一一对应。它表明 NVIDIA 把图执行的软件能力（捕获、实例化、参数更新）沉淀在驱动/runtime 层并设专利护栏，而把实例化图的高性能执行交给 US11182207B2 一类 TMU 硬件机制；"首次调用实例化、其后仅执行"（[0085]）与"换参不重实例化"正是硬件化任务图反复低开销重放的前提。

## 7. 评价与启示

**技术定位**：本专利不碰硬件，是对"图实例化昂贵"这一软件瓶颈的正面回应——把优化结果的复用性提炼为三条可执行规则：改参不涉及再优化则直接生效；涉及但成本 < T0 则仅局部再优化（FIG. 3 的 region 310 / FIG. 1 的 {C} 110）；涉及拓扑/结构/处理单元重绑定则拒绝（FIG. 4–6）。这三条规则恰是深度学习训练等迭代负载（参数按迭代轮换、拓扑恒定）能持续享受图模式收益的关键。

**权利要求策略**：独权措辞高度抽象（"perform a graph multiple times independently of one or more operands"），未把实例化、阈值判定写入独权 1/9/17，仅以从属项与独权 25 补充，保护面宽；处理器、介质、系统、双缓冲系统四类独权覆盖硬件、软件与整机侵权形态。

**局限（据文本可推断）**：1) T0 与再优化成本的估算方法未给出任何具体算法，全由 API runtime 裁量；2) 未描述实例化图在 GPU 内部的表达与调度（命令流/描述符格式），需与 TMU 族专利拼图；3) CPC 被分入 G06F 16/212（数据库/数据结构更新类）而非任务调度类，提示审查中该申请按"数据结构就地更新"被检索，其与 GPU 前端硬件族的关联在审查层面被淡化；4) 文本含多处笔误（claim 4 "perfamce"、claim 16 "whoses"、[0197] "prove"），不影响文义。

**启示**：与 US11182207B2、US20210149719A1 合读，可还原 NVIDIA CUDA Graphs 的完整专利链条：**捕获/实例化（本案 + 719A1）→ 参数漂移下的优化持久性（本案）→ 可执行图修改（719A1）→ TMU 硬件任务图执行与预取（US11182207B2）**；前端负责"少重做"，后端负责"快执行"——这是理解现代 GPU 前端（front end）/任务图硬件化路径的一条主线。
