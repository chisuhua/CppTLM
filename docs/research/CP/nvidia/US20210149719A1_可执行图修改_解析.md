## 2. 发明背景与待解决问题

**应用场景**：Task Graph（任务图）是并行计算工作负载的建模工具——计算任务建模为节点（node），任务间依赖建模为有向边（directed edge）。但任务图本身不能直接驱动计算资源，必须先转换为可执行图（executable graph）；随后"按可执行图配置一个或多个计算资源执行任务、必要时传输数据、取回结果"（[0003]）。可执行图可被反复启动（launch）以多次执行同一工作负载。

**待解决问题**（对应 CUDA Graphs 的软件侧痛点）：

1. **卸载开销大**：把任务逐个卸载给计算资源涉及资源选择、指令配置/下发、数据传输、结果取回，若不整体管理，开销会显著侵蚀加速收益（[0283]）。任务图的价值正在于"把多任务作为整体考虑"——利用依赖关系与资源适配性做全局优化（[0284]）。
2. **实例化（instantiation）开销**：任务图转可执行图时因"可访问整个任务图"而能做各种优化（重排、资源分配等）以降低总执行时间（[0285]），但该转换本身是"oftentimes substantial overhead"（[0302]）。
3. **一图一负载的僵化**：现有可执行图"typically usable for only a single workload"（[0003]、[0286]）——工作负载稍有变化（如推理 batch 尺寸、参数指针变化）就必须修改任务图并重新实例化，每次修改都重复支付全部实例化开销。这就是本专利要消除的开销。

### 3.2 关键机制

**两层图表示**：软件层 Task Graph（节点=任务，边=数据依赖/执行依赖/其他依赖）→ 经 instantiation（或 compilation，[0290]）生成 Executable Graph（可执行图）。方法 3200 五步：3210 构建任务图 → 3220 实例化生成可执行图 → 3230 启动（launch）一次或多次 → **3240 就地修改可执行图节点的参数** → 3250 判定修改是否成功。

**任务图构建（3210，[0288]）**：两种方式——(a) 显式 API/库调用：逐个创建节点并关联计算任务，再用调用添加有向边（依赖可因数据依赖间接产生）；(b) 隐式流录制（stream recording）：把普通任务流转换为录制流、提交任务、再完成到任务图的转换。节点对应的任务类型：**kernel task（计算核任务）、host task（host CPU 上的回调 callback）、memory set task、memory copy task**。FIG. 33 的 task graph 3300 含 8 个节点 A–G 与 End：A→B、A→F（B、F 无依赖，可任意顺序/并发/交错执行），B→C、B→D，C、D→E（join），F→G，E、G→End；到达 End 时控制权返回 host CPU；每个任务可递归地是一个子图。文中明示 task graph 3300 兼容 **CUDA graph / HIP graph**（[0289]）。

**实例化（3220，[0290]–[0291]）**：为每个节点分配计算资源（graphics processor、fragment processor、core、execution unit、cluster、multiprocessor、compute unit、streaming multiprocessor）或其子集；选择依据包括任务类型、任务的计算量与所需 threads/warps 数、任务间依赖。实例化期优化：(1) 重排任务以利用并行性（决定用多少资源、在资源间挪动任务）；(2) 重分配任务以降低数据依赖开销——把有数据依赖的任务放到同一计算资源上，免去跨资源传数并加快完成检测；(3) 按各资源可用的 threads/warps/compute thread arrays/cores/SMs 做负载均衡。

**启动（3230，[0292]）**：经 API/库调用启动；对每个节点执行：把该任务的 executable code 送至关联资源、按任务属性下发配置、必要时传输数据、任务完成后把结果传回 host CPU 或下游任务所在资源。同一可执行图可启动任意多次。

**就地修改（in-place modification，3240，[0293]–[0298]）**——核心发明点：不重新实例化，直接用 API/库调用修改已生成可执行图中节点的参数。可行性的判据是**该修改不得破坏实例化期优化、不得改变节点在关联资源上执行的"功能本身"**。各节点类型允许修改的参数：

| 节点类型 | 可修改参数 | 明确不可修改 |
| --- | --- | --- |
| host task（[0294]） | host CPU 上回调函数的标识（指针）；传给回调的参数数据 | — |
| memory set task（[0295]） | 内存块起始位置、块大小（1D 字数或 2D 行列）、填充值（fill value） | 块类型（1D↔2D）、内存类型（global/local/texture/constant/shared/register 之间互改）——因涉及不同实现 |
| memory copy task（[0296]） | 源位置、目的位置、拷贝大小 | 同上（块类型、内存类型） |
| kernel task（[0297]） | 线程数；作为计算任务参数的数据指针 | 计算任务的起始地址、所执行的计算任务本身、指向下一任务的指针——因改变底层任务/破坏依赖 |

待修改节点用**节点专属标识符**定位，该标识符可在 3210 创建节点时即记录下来"以备日后修改"；不同节点类型可用不同 API 调用，参数亦可逐个以标识符指定（[0298]）。

**成功判定与回退（3250，[0299]）**：修改被视为失败的情形——破坏了实例化期优化、修改了不允许修改的参数、或导致可执行图不可启动；可依据每次 API 调用返回的 status/error code 判定。成功→回到 3230 启动修改后的图执行新负载；失败→把修改施加到任务图并回到 3220 重新实例化；若涉及任务本身/依赖结构等更深层修改，则回到 3210 重建任务图（[0299]）。**性能权衡**（[0300]）：即使修改后的图因优化被部分破坏而执行得比"全新实例化"更慢，省下实例化开销仍可使总处理时间更短。技术效果（[0302]）：单个可执行图可服务多个不同工作负载，免去每次改图都重新实例化的开销。

**是否披露硬件消费机制**：**未披露。** 本专利实质部分（[0282]–[0302]）完全在 host CPU + API/库调用层面描述，执行主体是泛化的 "computing resource"；全文没有任何关于 front end / TMU / pushbuffer 如何读取执行图的披露。FIG. 1–31 样板段落里虽有通用 PPU 前端描述（如 [0120]：host interface 1206 收到命令缓冲后经 I/O unit 1204 把 work 命令交给 front end 1208，front end 1208 耦合 scheduler 1210 分发到 processing array 1212，且 front end 1208 保证命令缓冲（batch-buffers、push buffers 等）启动前阵列处于有效状态；[0178]–[0180]：host 把 command stream 写入缓冲并把指针交给 PPU 1700，front-end unit 1710 管理命令流并转发，scheduler unit 1712 → work distribution unit 1714 → GPC 1718），但这些均为样板背景技术，与发明点无连接。因此**本专利属纯驱动/运行时层技术**。

## 4. 权利要求摘要

共 20 项权利要求，3 项独立：claim 1（计算机可读介质）、claim 10（方法）、claim 14（方法）。

**独立权利要求 1（非暂态计算机可读介质）**：存储指令，指令被一个或多个处理器执行时使处理器执行至少一个 API 调用，以**修改任务图的可执行版本（executable version of a task graph）**。

**独立权利要求 10（方法）**：一种修改可执行图的计算机实现方法，包括修改任务图的可执行版本。

**独立权利要求 14（方法）**：从任务图生成可执行图，其配置一个或多个计算资源执行第一工作负载；修改可执行图中一个节点的参数以生成修改后的可执行图，其配置计算资源执行不同于第一工作负载的第二工作负载。

从属权利要求分组：

- 修改对象细化：修改的是可执行版本中某节点的参数（claim 2/11）；节点对应启动时由计算资源执行的任务（claim 3/12）；
- 任务类型限定：kernel/host/memory set/memory copy task（claim 4/13）；
- 分类型参数限定：host task 的回调指针/回调参数（claim 5/17）；memory set 的块位置/块大小/填充值（claim 6/18）；memory copy 的源位置/目的位置/块大小（claim 7/19）；kernel 的线程数/参数（claim 8/20）；
- 修改后启动：执行额外 API 调用启动修改后的可执行版本，使其配置资源执行与修改前不同的第二工作负载（claim 9）；
- 手段与平台限定：修改经 API 调用完成（claim 15）；可执行图为 executable CUDA graph 或 executable HIP graph（claim 16）。

（说明书 [0303]–[0322] 另以 clause 1–20 给出实施例条款，与权利要求实质对应。）

## 5. 与 TMU 上游模块的关系

**执行图如何进入命令流**：本专利没有描述这一衔接。其样板段落提供了 NVIDIA 通用的前端通路背景（[0125]、[0178]–[0180]）：host 处理器把 command stream 编码进 host 与 PPU 均可访问的缓冲（pushbuffer），把流首地址指针发给 PPU；front-end unit 1710 接收并管理命令流、逐条读出命令转发给 PPU 内各单元；scheduler unit 1712 配置 GPC 1718 处理命令流定义的任务并跟踪任务状态（assigned GPC、active/inactive、priority）；work distribution unit 1714 维护每个 GPC 的 pending/active task pool 并派发执行。按此通用模型可推断：driver/runtime 把实例化后的 executable graph 展开为命令流（kernel 启动、memcpy、memset、callback 等命令）经 front end 消费；但该"展开"环节不在本专利权利要求与实质披露范围内——本专利只负责图的生命周期管理（构建/实例化/启动/修改/回退）。

**与 US11182207B2（TMU 依赖任务描述符预取）的异同**：

| 维度 | US20210149719A1（本专利） | US11182207B2 |
| --- | --- | --- |
| 层次 | 软件/驱动层（API 调用、host CPU） | 硬件层（TMU 234 内 Dependency/Prefetch Unit 410） |
| 图的表示 | task graph + executable graph，节点为 kernel/host/memset/memcpy 任务，边为依赖 | task descriptor 链：Dependency Count 442、Current Count 444、消费者指针 470、prefetch flags 460 |
| 依赖解析 | 由驱动在启动图时按图结构处理，专利未披露硬件机制 | 硬件计数递减 + Active List 420 就绪判定，全片上闭环 |
| 优化点 | 实例化期全局优化（资源分配/重排）+ 就地修改免实例化 | 依赖析延迟掩盖（描述符/指令/常量三类预取）+ Self-Reset 自动复位 |
| 循环/变更 | 修改节点参数重放图，失败回退重新实例化 | Conditional Loop 靠 self-reset flag 446 硬件自动复位 |

两者互补而非重叠：本专利解决"图的生命周期与变更开销"（host 侧、每次迭代/变体之间），US11182207B2 解决"图内任务间切换延迟"（片上、每次依赖边触发时）。软件层的 executable graph 最终仍需落到硬件任务调度路径（命令流 → front end → scheduler/work distribution），两专利分别覆盖这条路径的两端。

**在 CUDA Graphs 专利族中的位置**：本专利是 NVIDIA 围绕 CUDA Graphs 的一日多案布局（2019-12-31 提交，均主张 2019-11-15 印度临时优先权）中的一员，且是族内最早明确写出 "CUDA graph / HIP graph" 字样（[0289]、claim 16）并把"实例化后免重建修改"作为主题的公开文本；其姊妹申请（US16/732,014，US20210149734A1）把主题推进到"修改执行图以执行与新任务图关联的工作负载"，后授权为 US12443449B2（2025-10-14）并有延续案 US20260079755A1。本专利可视为该族中定义"图执行体（graph executable）可变性边界"的基础案。

## 7. 评价与启示

**技术重要性**：

- 本专利把 CUDA Graphs 的核心生命周期——build → instantiate → launch → **modify-in-place** → (fallback) reinstantiate——写入权利要求，形式化了"图执行体与图定义分离"的关键设计：实例化是昂贵的一次性全局优化，修改被刻意限制在"不破坏优化结论"的参数子集内（各节点类型的可改/不可改清单即此边界的具体化），使绝大多数迭代场景（换参数、换指针、换尺寸）免走重建路径。
- 节点标识符"创建时即记录以备修改"（[0298]）暗示了句柄化 API 设计（先捕获节点句柄，后按句柄更新参数）；3250 的成功/失败回退机制保证了正确性底线。
- [0300] 的权衡陈述（修改后的图即使次优也值得用）是典型的"用一次性开销换每次迭代开销"的系统设计论证，正是 CUDA Graphs 在小 kernel、重复负载（深度学习训练/推理循环）上获益的逻辑。

**局限性（据文本可推断）**：

- 不披露 executable graph 的任何数据结构布局（节点记录字段、内存组织、设备侧表示），也不披露启动时如何把图转化为设备命令；对理解 front end/TMU 如何消费图无直接帮助——这部分需依赖 US11182207B2 等硬件专利与 CUDA 文档互补；
- 修改面保守：依赖边、任务身份、块/内存类型均不可改，结构性变化只能回退重建（姊妹案 US12443449B2 即针对该缺口）；
- 全文 78 页中实质内容仅 [0282]–[0322] 约 40 段，其余为 PPU/CUDA 平台样板，检索与阅读成本高；CPC 标注中混入 H04W 4/80 等噪声。

**对理解 CUDA Graphs 的价值**：本专利是 NVIDIA 公开文献中少数正面描述"executable graph"这一中间形态的文本：它确认实例化（instantiation）是独立且昂贵的阶段、确认执行图可脱离原任务图被反复修改与重放、并给出可修改性的工程边界。结合本地研究目录中的 TMU 硬件专利（US11182207B2 等），可完整还原 CUDA Graphs 的软硬分工：驱动层负责图的构建/实例化/修改（本专利），片上硬件负责任务级依赖解析与调度加速（TMU 专利族），二者之间的命令流接口则由通用 front end/pushbuffer 通路（样板段落 [0125]、[0178]–[0180]）衔接。
