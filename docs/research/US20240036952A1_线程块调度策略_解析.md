## 2. 摘要与权利要求分析

**摘要（Abstract）逐句拆解**：
1. "a processor comprising one or more circuits to perform an application programming interface (API) to determine which of two or more blocks of threads are to be scheduled in parallel" —— 核心：用 API 决定哪两个或更多线程块被并行调度（即把"并行共驻"这件事变成可编程接口）。
2. API 可提供"一个或多个线程块组"的维度；组内块是软件 kernel 的多个块组之一；各块组构成 kernel 网格（grid）的块划分（partition）；组是多个带索引子集（indexed subsets）之一。
3. API 带参数指示组的维度（可多个参数分别指示不同维度）。
4. 两个或更多线程块将使用**不同的 multiprocessor** 并行执行 —— 摘要层面即锚定"跨 SM 并行"语义。

**权利要求布局（36 项，4 组镜像）**：

| 独立权利要求 | 类别 | 核心限定 |
| --- | --- | --- |
| 1 | 处理器（processor） | 电路执行 API，以确定两个或更多线程块中哪些被并行调度 |
| 10 | 计算机实现的方法 | 执行上述 API |
| 19 | 计算机系统 | 存储器 + 处理器执行上述 API |
| 28 | 机器可读介质 | 指令执行上述 API |

从属权利要求（以 claim 1 组为例，其余三组镜像）：
- 2：API 提供块组的一个或多个**维度**；
- 3：API 提供块组的**大小**；组是 kernel 多个块组之一；
- 4：块组是 grid 块划分的**一个划分**（partition of a partitioning）；
- 5：块组是 kernel 的多个**带索引子集**之一；
- 6：API 含参数指示组维度；
- 7：API 含**多个参数**，各指示一个不同维度；
- 8：块将使用**不同 multiprocessor** 并行执行；
- 9：API 提供组内**单个块**的信息。

**解读**：独立权利要求的边界极宽——只要求"执行 API 以确定哪些块并行调度"，不限定 API 形状、不限定硬件如何实现调度；维度/大小/划分/索引子集/多参数/跨 multiprocessor 等全部下沉到从属项。这是典型的"API 表面专利"写法：只要竞品编程模型暴露了"查询/设置哪些 workgroup 可并发"的接口，即落入字面范围。

## 4. 关键机制分析

### 4.1 调度策略：spread 与 balance（FIG. 10/11）

- **spread scheduling policy 1004**（[0140]，FIG. 10）：block cluster 1002 的线程块被**分布到尽可能多的 compute unit**——例中 4 个块 1006/1008/1010/1012 一一落到 4 个不同 compute unit 1014/1016/1018/1020。语义＝"最大化分散"，利于并行度/吞吐。
- **balance scheduling policy 1104**（[0141]，FIG. 11）：block cluster 1102 的线程块在**可用 compute unit 间均衡负载**——例中 1106→空闲的 1114；1108+1110→1116；1112→1120；而已有外来块 1124+1126 的 1118 **不再接收**。语义＝"考虑既有负载的均衡放置"，利于延迟/公平。
- 两政策的法律-技术姿态（[0140]–[0141]）：均为 **preferred（首选）策略，硬件可满足也可违反**（如 spread 下多块仍可能同置一个 compute unit）；二者均可为**默认策略**。这是"hint 而非 mandate"的设计——软件表达放置意图，硬件保留最终裁量权。

### 4.2 调度策略的 set/get API（FIG. 12/13）

- **set scheduling policy API 1202**（[0142]–[0148]）：参数＝scheduling policy attribute 1204 + scheduling policy value 1206（spread 或 balance 或 default）+ kernel identifier 1208；返回 return value 1218（success/failure 1216）。执行时校验属性 1210、为 kernel 1214 设置策略 1212、再 launch 1214。
- **get scheduling policy API 1302**（[0149]–[0154]）：参数＝cluster identifier 1304；内部 determine 1306；未设置时返回 **default 1308（例：spread）**；已设置则返回 policy 1310；经 return value 1312 回传。
- 对应现实 CUDA：即 CUDA 12 的 cluster scheduling preference 接口（`cudaLaunchAttributeClusterSchedulingPolicyPreference`，取值 Default/Spread/LoadBalancing）的专利覆盖。

### 4.3 cluster 尺寸/维度 API 与硬件上限查询（FIG. 7–9、14–21）

- **set block cluster dimension API 802**（FIG. 8，[0127]–[0133]）：dimension attribute 804 + dimension value 806（可三维，如 (2,2,2)/(2,4,1)/(8,1,1)）+ kernel identifier 808；校验 810、设置 812、launch 814；返回 818/816。FIG. 7 显示 size 与 dimension 可互推（指定 size=8 可由硬件推算维度，反之亦然）。
- **get cluster dimension API 902**（FIG. 9，[0134]–[0139]）：cluster identifier 904；未设置返回 default (0,0,0) 908。
- **硬件上限的软件暴露**：number of blocks supported API 1502（FIG. 15，[0158]–[0163]）——processor 1402 向 graphics processor 1406 请求"硬件支持的最大发 cluster 数"1404；GPU 基于 **kernel 参数、kernel 配置、硬件能力、可用资源** 确定 maximum number of clusters 1408 并返回 1410（stored number of clusters 1504、launch configuration 1508、determine 1510、value 1512、success/failure 1514/1516）。同源还有 maximum cluster size supported API 1902（FIG. 19）、indicate cluster parameters API 1702（FIG. 17）、get attributes API 2602（FIG. 26）、"cluster size must be set at launch" attribute 1602（FIG. 16）、launch kernel with block clusters API 2102（FIG. 21）。
- 设计哲学：**硬件资源是约束，API 是暴露面**——软件在 launch 前查询上限、据此选择 cluster 形状或回退到无 cluster 启动，把"occupancy 试算"部分前移给用户态。

### 4.4 配套机制：cluster 内同步与共享内存

- barrier 三件套：kernel barrier **arrive** API 3002（FIG. 30）、**wait** API 3102（FIG. 31）、**sync** API 3202（FIG. 32），[0093]–[0095]——cluster 内跨块线程的 arrive/wait/sync 语义（对应 PTX `barrier.cluster`）。
- map shared memory API 3402（FIG. 34，[0096]）：使第一 cluster 的内存位置可被第二 cluster 访问——跨 cluster 共享内存的软件入口。
- shared memory 304 位于 compute unit 内（FIG. 3；亦见 FIG. 66 的 6660(1)/(2)），是 cluster 协作的片上载体。

### 4.5 WDU→Crossbar→GPC→SM 硬件对应（FIG. 52/53/54，[0412]–[0428]）

本专利硬件样板段给出了 NVIDIA 前端分发链的完整元件链：

```
host (driver kernel, API calls → tasks/streams, [0418])
 → I/O unit 5206 → front-end unit 5210 ([0413])
 → scheduler unit 5212：配置各 GPC 5218、跟踪 task 状态/优先级 ([0414])
 → work distribution unit 5214：每 GPC 维护 pending task pool（例 32 slots）+ active task pool（例 4 slots）；
   active 任务因数据依赖停顿时被 evict、由 pending 替补 ([0415])
 → XBar 5220（work distribution crossbar：互连网络，把 WDU 5214 耦合到特定 GPC 5218；hub 5216 亦挂接）([0416])
 → GPC 5218/5300：pipeline manager 5302 → MPC 5310 路由 packets → DPC 5306primitive engine 5312 / SM 5314）([0424])
 → SM 5314：SIMT，warp=32 线程，每 warp 维护 PC/call stack/execution state ([0425]) → SM 5400 (FIG. 54)
```

**本专利在该链路中的位置（关键分析）**：
1. 这是一件 **API 层专利**：它不改动 WDU/XBar/GPC 的内部结构，而是把"CTA/cluster 放置意图"（维度、大小、spread/balance 偏好、优先级）从纯硬件黑盒决策**部分开放给应用软件**。宿主 driver kernel（[0418]：应用以 API call 形式生成指令、driver kernel 生成 task 入 stream）消费这些 hint，最终仍由 scheduler unit 5212 / WDU 5214 在 pending/active pool 调度时落实或违反。
2. spread/balance 直接对应 WDU 5214 的放置目标函数：spread≈"每 GPC/SM 最多放一个同 cluster 块、铺满尽量多的 SM"；balance≈"在考虑各 SM 既有负载（如 1118 已占用）的前提下均衡放置"。即**把 WDU 的负载均衡策略参数化、可查询化**。
3. "哪些块并行调度"的硬件实质是 WDU 的 active pool 共驻决策：claim 1 的 "determine which of two or more blocks are to be scheduled in parallel" 在硬件上即 WDU 5214 决定哪 4 个（例）task 同时 active 于某 GPC、以及 cluster 的块是否被 co-resident 地铺到不同 SM。
4. 与同主题硬件专利的分工：cluster 共驻的**硬件保证**（all-or-none、speculative launch）在 US12,333,311（CGA）；crossbar 的**动态路由**在 US2024/0356866；本件只覆盖**策略与属性的 API 表达层**——三层合起来才是 Hopper cluster 的完整专利网。

## 7. AMD 映射分析

- **workgroup = thread block、CU = SM** 是稳定映射；本专利的 compute unit 302 在非 CUDA 实施例（FIG. 65，[0540]–[0544]）中直接落到 SIMD unit 6550 + shared memory 6560 的 AMD 式 CU 描述，说明说明书本身按"CUDA/AMD 双栖"撰写。
- **SPI = WDU、SQ = pending/active pool**：AMD 的 SPI 负责把 workgroup 分发到各 CU，其 per-SE/per-CU 的 SQ 队列在功能上对应 WDU 5214 的 pending task pool（32 slots）/active task pool（4 slots）；spread≈SPI 默认的"找最空 CU 放置"balance≈考虑 SE 间既有占用的均衡——但 AMD **从未把该策略参数化暴露给用户**：HIP/ROCm 无 workgroup 维度之上的 cluster 维度 API，也无 scheduling policy set/get 接口。
- **cluster 层缺失**：AMD 侧最接近的对偶思路是 EP3785113B1 的 split workgroup（把 workgroup 拆分到多 CU 协同）与 EP3803583B1 的多 kernel wavefront 调度——方向是"拆/混以适应资源"，而非 NVIDIA 的"整组共驻 + 策略 hint"。因此本专利的 API 表面（cluster dimension、spread/balance、max-clusters 查询）在 AMD 编程模型中**没有字面对偶物**，这既是其专利杀伤力的来源（HIP 若补齐 cluster 语义即触线），也是跨厂商移植 cluster 代码（CUDA→HIP translation tool 6320，FIG. 63C）的语义鸿沟。

## 8. 边界与局限

1. **API 层而非硬件层**：全部独立权利要求限定为"执行 API 的电路/方法/介质"，不覆盖 scheduler/WDU 内部实现；硬件竞品只要不暴露同形 API 即不侵权。
2. **hint 语义弱保证**：spread/balance 均为"preferred、可违反、可为默认"（[0140]–[0141]），软件拿不到放置结果的反馈闭环（get API 只回读自己设置的策略，不回读硬件实际放置）。
3. **定性而非定量**：说明书对 spread/balance 只给示例性放置图，无负载度量、阈值、仲裁算法；cluster 与 GPC 域的绑定（同 GPC 共驻等）在本案中**不主张**，由同族/关联专利（US12,333,311 等）覆盖。
4. **上限只读**：max clusters / max cluster size 由硬件决定、API 仅查询（1502/1902），软件不能超额请求，资源紧张时只能回退。
5. **文本形态**：通篇 "In at least one embodiment" 式 boilerplate 巨量重复，实质技术内容集中在 [0077]–[0170] 与 FIG. 36–54 硬件样板；无独立 SUMMARY 节；扫描件小字（如 FIG. 6 流程块号）以原文为准。

## 10. 工程启示

1. **"hint + 查询"是软件意图与硬件裁量的最优妥协面**：软件最懂通信模式（cluster 内块需要共驻、需要 spread 还是 balance），硬件最懂实时资源（pending/active pool、SM 占用）；本件把前者写成可 set 的 preference、把后者写成可 get 的 limit，两侧各自保留弹性。国产 GPGPU 设计 workgroup 调度 API 时可直接借鉴该"参数组 = size/shape/policy/priority/sync"的切分（[0115]）。
2. **把 occupancy 试算前移给用户态**：1502/1902 类"硬件支持多少并发 cluster"查询让 runtime 在 launch 前做形状选择与回退，避免 launch 后死锁/序列化——对无硬件共驻保证的架构尤其重要。
3. **策略可查询化利于性能可移植**：get scheduling policy API 1302 的"default=spread"回退语义，为跨代/跨厂商二进制提供了"查询-适配"范式，比硬编码放置假设更稳健。
4. **API 表面专利的防御价值**：独立权利要求只钉住"执行 API 以确定哪些块并行调度"，任何在编程模型层引入 cluster/workgroup 并发语义的竞品（含 HIP 未来扩展）都难以绕开字面范围——做兼容层设计时需把"维度/策略/上限"三组接口的侵权面单独评估。
5. **对 SPI/SQ 研究的映射**：本件证明 NVIDIA 把 WDU 的负载均衡目标函数（spread vs balance）做成了可编程参数；AMD 侧若要在 SPI/SQ 上做对等研究，切入点是为 workgroup 分发策略增加用户可见 hint 位与上限查询寄存器，而非改动 CU 微架构。
