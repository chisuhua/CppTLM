## 1. 背景

### 1.1 两条路线

| 路线 | 代表 | 描述 |
|------|------|------|
| **DSL + 代码生成** | Oswald *Gen 族(ProtoGen / HieraGen / HeteroGen)| 用 **SSP 描述语言**(PPL)写协议的**稳定状态**部分,工具生成并发协议(含瞬态态) |
| **C++ 插件手写** | CEP 现状 | 每个协议实例手写一个 ProtocolEngine 插件 |

调研 F15 / F21 / F23 已给出大量一手事实,本 ADR 需回答:**CEP 走哪条?边界在哪?何时可能切换?**

### 1.2 一个必须先纠正的直觉

"CEP 拒绝 DSL"常被理解为"DSL 不好"。一手依据显示**两个来源、两种理由**:

| 来源 | 反对对象 | 理由 |
|------|---------|------|
| ArchForge 09 §4.4(per ADR-SOC-01)| **slicc DSL 的语言载体** | "slicc 是 gem5 特定语言、5000+ 行不可读" |
| ProtoGen ISCA 2018 p.7 局限 L4 | **协议/互连耦合**(不是 DSL) | "requires the user to manually define virtual channels and assign messages to channels" |

→ **两者互补不重叠**。前者说"不要把一门语言搬进框架",后者说"协议语义与互连必须分离"。CEP 同时满足两者。

## 2. 决策

### 决策 1:Stage 1-3 **纯手写插件路线**,不引入 DSL / 代码生成

**决策**:CEP 在 Stage 1~3 **不依赖任何协议生成器**。

**理由(工程量,一手)**:

| 工具 | 论文口径(纯算法行) | v0.3 实测(全仓 Python,含 vendor) | 对应 CEP 需要的能力 |
|------|------------------|-----------------------------------|-------------------|
| ProtoGen | 8,849 | 16,110 | 单层并发协议生成 |
| HieraGen | 15,771 | 25,727 | + 分层组合 |
| HeteroGen | 30,413 | 37,198 | + 异构组合 |
| **ProtoGen+** | **45,000+** | (未落地) | 全部算法 + Rumur/SLICC 后端 |

> **口径说明**:论文数字是**纯算法实现行数**;实测是**全仓行数**(含 `antlr3/`、`CMurphi/` 等 vendored 依赖)。两者**不可直接比较**,引用须注明口径。

**对照 CEP 的实际需求**:`07 号 §5.1` 现为 **2 来源族 / 16 adapter 实例**(§5.1.4 的 5 个候选语义落地后为 20)。为 16~20 个实例建一个 30k~45k 行 Python 的编译器,**投入产出严重倒挂**。

**License 事实(降低障碍但不改变结论)**:三仓均 **MIT**(UoE 2018)→ **无 copyleft 义务**,CEP 可自由借鉴其**设计思路**(保留版权声明);但**借鉴 ≠ 移植**。

### 决策 2:不承诺复刻 *Gen 族工具链

- 不承诺 Stage 1~3 交付任何 DSL、解析器、IR 或代码生成器
- 不承诺产出 Murϕ FSM(CEP 的产出是**插件 + 实验产物**,per `ADR-CEP-06` 4 件套)
- **理由**:CEP 的目标是**在统一实验床上运行 / 对比协议**,不是**生成协议**(per `ADR-CEP-17` 决策 10)

### 决策 3:竞合定位 —— **互补,非替代**

| 事实 | 证据 | 对 CEP 的含义 |
|------|------|--------------|
| *Gen 族**已能直接产出 gem5 Ruby 协议源文件** | 源码 `gem5_HeteroGen_protocols/`(E1) | **gem5 协议空间可被自动扩张** ⇒ **CEP 需要探索的协议空间变大** ⇒ CEP 的价值**上升** |
| 但运行需 `alloy-gem5`(定制 fork)+ 外部 docker 参考系统 | 源码 `setup.sh` + README(E1) | 该路线**尚非开箱即用** ⇒ 短期内 gem5 侧仍以手写 `.slicc` 为主 |
| 学术侧计划的 SLICC / Rumur 后端**至今未落地** | 三仓后端目录只有 Murphi(E1) | "自动生成 gem5 协议"这条路**已通**(直出 `.slicc`),但"从任意 SSP 生成 SLICC"**未通** |
| *Gen 工具**已被学界和工业界采用** | 博士论文 §9.1(E1) | 该研究线**活跃** ⇒ 长期须关注 |

**结论**:CEP 与 *Gen 族**互补** —— *Gen 族**生成** gem5 协议,CEP **在统一实验床上运行 / 对比协议**。CEP **不与** *Gen 族竞争"谁生成协议"。

**对 CEP 自身规划的影响**:若 gem5 协议空间被自动扩张,CEP 的**协议实例来源**将来可能是"gem5 上由 *Gen 族生成的 `.slicc`" —— 故 `ADR-CEP-12` 的 schema 需能描述**来源**(`family: ruby-slicc` 已覆盖)。

### 决策 4:长期演进位 —— **SSP 描述 → 插件生成**(不是 → Murϕ FSM)

**保留的演进方向**:若未来引入描述路线,输入是 **SSP 描述**,输出是 **ProtocolEngine 插件**(而非 Murϕ FSM)。理由:

1. **直接对接 CEP 架构** —— 插件是 CEP 的一等公民(per `ADR-CEP-07` 决策 3 的注册机制);Murϕ FSM 不是
2. **与 ArchForge 09 §4.4 同向** —— "用 C++ `switch` 表而非 slicc",生成的产物应当是 C++ 侧可用的东西
3. **避免第二个真源** —— 若产出是 Murϕ FSM,则 CppTLM 侧仍需手写插件,描述只是冗余中间层

**该路线的前置层(必须先有)**:博士论文 Ch5 的 **SSP Pre-Processing** —— 依赖提取 + SSP 正确性验证(SSC / MSD)+ 状态空间最小化(E1)。

**CEP 侧的对应物**:
| *Gen 族层 | CEP 对应 |
|---------|----------|
| SSC(状态空间检查) | `ADR-CEP-14` 的 **Stub 可验证性合同测试** |
| MSD(消息停滞检测) | 暂无对应(可选) |
| SSP 状态空间最小化 | `ADR-CEP-12` 的 schema 归一化 |

### 决策 5:引入生成路线的**判据**(何时切换)

**触发条件(须同时满足)**:

| # | 条件 | 判据 |
|---|------|------|
| **T1** | **规模** | 待实现协议实例数**显著超过**手写成本拐点(初值:同一协议族内实例数 > 8,且跨 ≥3 个族) |
| **T2** | **表达力** | 目标协议的**全部协议私有状态**可被 SSP 表达(瞬态辅助状态、token 等);**不可表达者仍走手写** |
| **T3** | **前置层就绪** | `ADR-CEP-14` 的合同测试体系可覆盖"生成插件 ↔ 手写插件"的一致性 |
| **T4** | **产出定位明确** | 生成物的消费者是 CEP 平台(插件),而非外部工具链 |

**T2 的具体判据**:一个协议实例能否走生成路线,取决于其协议私有状态能否被 SSP 表达 —— 参照 ProtoGen 的做法,瞬态辅助状态(如"记得该把响应发给谁")在 SSP 里是**显式状态**,故 SSP **需要**能表达辅助状态;而 HTM 的 read-set / write-set、token 的权限携带**超出**缓存一致性 SSP 的表达力(per `ADR-CEP-17` 决策 5 的 HTM 排除)⇒ 这类协议**永远**手写。

### 决策 6:显式排除

| 排除项 | 理由 |
|--------|------|
| Stage 1~3 **不**交付 DSL / 解析器 / IR / 生成器 | 决策 1 |
| **不**承诺复刻 *Gen 族工具链**(30k~45k 行 Python) | 决策 1 |
| **不**承诺产出 Murϕ FSM | 决策 2 |
| **不**做"从 SSP 生成 SLICC" | 学术侧该后端**至今未落地**(E1);CEP 不做生成器 |
| **不**承诺"全部协议都可生成" | T2 表达力判据 |

## 3. 不变量

**无新 invariant**(本 ADR 是纯 trade-off ADR)。

**但须写死一条约束**:
> **Stage 1~3 的任何 Stage DoD 不得包含"协议生成器"相关交付物**;若实现中出现生成器,视为超出本 ADR 边界,须重新评审。

---

## 4. 抓取点

1. **无生成器**:Stage 1~3 的 DoD 与实现产物中**不得**出现 DSL / 解析器 / 代码生成器(per 决策 1 + §3)
2. **产出物形态**:插件是 CEP 的一等公民;任何"生成 Murϕ FSM"的路径须重新评审(per 决策 4)
3. **竞合监控**:`*Gen` 族若落地 SLICC / Rumur 后端,须重新评估决策 1 的 T1 规模判据(per 决策 3)
4. **License 追溯**:若借鉴 *Gen 族源码(MIT),须保留版权声明
